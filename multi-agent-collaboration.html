为什么是代码常量而不是数据库配置表？订阅条件是带业务语义的谓词（如"归因降级的诊断不转营销"），不是能塞进 SQL 的标量比较。改动频率极低（加 Agent 才动），每次改动都该配一次回归测试——正是代码而非配置的适用场景。

5 协作 Worker 内部流程 (run_once)

6 共享上下文：双向经验回流

参谋的诊断结论通过两条路径流通：① 向上注入卖家画像（店主下次开口时读到）；② 转化为买家侧应答提示（客服下次遇到该商品时更谨慎）。

为什么不能直接把诊断注入买家上下文？
诊断里的 conclusion 是 LLM 写给店主的经营判断（如"退款率 30%，主因尺码不准"）。如果直接注入买家 prompt，客服可能说出"我们这款鞋退款率确实偏高"——把内部经营数据泄露给顾客。

解决方案：buyer_hints 走确定性映射——按异常 kind 查固定文案表，产出的提示里没有任何数字、不含诊断结论原文。泄露风险从"靠模型自觉"变成"结构上不可能"。
