# 深度范例：测量完整性（M10）

> **这是"吃透级"的深挖样板，也是这个项目最强的面试故事。**
> 学其它模块时，用同样的方式现读代码、追到同样细的权衡。
>
> 为什么选它当主线：它一个故事同时体现**可观测意识**、**对自己系统的怀疑**、
> **根因分析**、**系统性修复**，而且**有两组具体数字**。功能类亮点谁都能讲，
> "我发现我的自动化差点因为我自己的测试流量把一个好功能撤下线"——这个别人讲不出来。

---

## 一、90 秒版本（背到脱口而出）

> 我的系统会按成功率自动回滚表现差的 skill。有天我看到 `track-order` 成功率 **28%**，
> 按规则该回滚了。但我去查了那 53 条轨迹的**来源** —— **41 条是我自己压测和走查造的**，
> 真实买家只有 17 条，成功率 **88%**。
>
> 也就是说，这套自动化随时可能因为我自己的测试流量，把一个完全正常的 skill 从线上撤掉。
> 而在那之前，表里**没有任何字段能把真实流量和合成流量分开**。
>
> 所以我给每条轨迹和每条归档会话加了 `source` 标记，并且把口径拆成两套：
> **判定只认真实流量**（回滚是不可白做的动作），**语料采样可以放宽但排除压测和评测**
> （拿自己生成的对话当真实语料去蒸馏，等于学自己的回声）。

**讲完停住，等追问。** 面试官几乎一定会问下面某一条。

---

## 二、追问预案（每条都要能接住）

### Q1「全量 23% 和 live 88% 差这么多，那些失败到底是什么？」

`skill_traces` 1433 轮的真实构成（2026-09-06 实查）：

```
dev  走查 / 测试固定用户(u1 等)   871 轮
live 真实买家(hmdp 数字 id)       474 轮   ← 只有这些是真的
loadtest 压测(ab*)                 41 轮
eval 评测沙箱(ev* / trk* / nat*)   47 轮
```

而 `track-order` 失败的主体（归因样本 44 条里占 37 条），**全是同一句「未找到订单 ORD-20240115-001」**。查库：
那单**存在，属于「小明」**，而发起请求的是 `ab0`/`ev3`/`trk5` 这些压测账号。
`auth_enabled=True` → 归属校验返回 None → 工具复用"未找到订单"话术（**刻意不泄露订单存在性**）。

**所以那不是失败，是安全机制在正确工作。**（这里可以自然带出 M6 归因）

### Q2「这个字段到底值多少钱？会不会是过度设计？」

给构造的对照，说明**它防住的不是理论问题**：

```
一份真实表现 90% 的 skill（40 轮）
  + 同规模压测 40 轮 10%（打的是别人的订单号，归属校验按设计拒绝）
  ─────────────────────────────────────────
  混在一起  → 成功率 0.50 → ROLLBACK   ← 把好 skill 撤下线
  只认 live → 成功率 0.90 → PROMOTE
```

0.50 正好落在 `AB_SANITY_FLOOR = 0.3` 与 `ABSOLUTE_MIN_RATE = 0.6` **之间**——
可信下限那道创可贴挡不住的一段。这条已经钉成测试。

### Q3「为什么默认值是 live？不应该更保守吗？」

反直觉但是对的：**真实请求走的是默认路径，而合成流量的每一个产生点都是我自己写的代码**
（压测脚本、评测沙箱、多轮模拟），由它们显式标注自己。

反过来把默认设成 `unknown`，会让真实流量因为某处忘了标注而被判定层**整批丢掉** ——
那时看门狗永远样本不足，自动收口彻底停摆。**默认值要放在"漏标的代价最小"的那一侧。**

### Q4「判定和采样为什么用两套口径？不是越严越好吗？」

因为**两类用途的错误代价不同**：

| | 认什么 | 错了会怎样 |
|---|---|---|
| 判定（看门狗回滚） | 只认 `live` | **回滚一份好 skill，立刻生效、不可白做** |
| 采样（语料/门禁用例） | `live` + `unknown` | 多学一段不该学的，后面还有校验/门禁/风险分级/人工审批四道关 |

所以采样容得下 `unknown`（否则既有 87 条历史归档语料全部作废），判定容不下。

但 `loadtest`/`eval`/`simulated` **两边都排除** —— `simulated` 尤其危险：
阶段三的多轮模拟本身就是拿 skill 生成的，再喂回去合成门禁用例就是**闭环自证**。

### Q5「历史数据怎么办？」

一律标 `unknown`，**不是 `live`**。补成 live 等于凭空断言"这些都是真实流量"，
而看门狗会拿这个断言去做自动回滚 —— 那正是这个字段要防的事。

要给历史行分类走**独立脚本**：显式规则表、每条规则写清依据、**默认只打印方案**、
`--apply` 才写、命不中规则的保持 `unknown`。
（启发式不该藏在一次静默的 schema 迁移里，它得有人看过、认过。）

### Q6「请求头能不能被伪造？」

只能往"**非真实**"方向标。默认已经是 `live`，所以这个头唯一的合法用途是让脚本给自己降级。
若允许请求方把任意流量标成 `live`，这个字段就成了一个**可以被伪造的"真实性证明"** ——
而它正是自动回滚的依据。

## 三、三个"静默失效"的坑（行为面素材，讲一个就够）

### 坑① contextvar 传不到干活的地方 —— 首选

`/api/chat` 返回 `StreamingResponse` + **同步**生成器，Starlette 用
`iterate_in_threadpool` 驱动它：**每次 `next()` 都在一份新拷贝的上下文里跑**，
生成器体内 `yield` 之前设的 contextvar，下一次恢复时已经没了。

后果：带 `X-Traffic-Source: loadtest` 打一轮，轨迹照样落成 `live`。
**我自测五种取值全部落 live，那个头等于不存在，而且不报任何错。**

**修法**：改成显式参数传给 `run_agent_streaming`，由真正写轨迹的那个 worker 线程自己设。
与同文件里 `set_current_token` / `set_current_item`（标着 P0-1）是同一类问题的同一种解法 ——
**跨执行边界的东西，显式带过去，别指望隐式上下文。**

### 坑② 设了不还

`Sandbox.run` 裸设 `eval` 不恢复。生产上看不出（每个请求一个上下文），
但全量测试是**同一个线程串着跑的** —— 评测沙箱跑过之后，6 个看门狗 CLI 用例集体变红，
而它们单独跑全过。修法：`traffic_source_scope` 上下文管理器 + conftest 再兜一道。

### 坑③ CRLF 让多行锚点没匹配上

批量改文件时用 `\n` 拼的多行锚点，在 CRLF 文件上匹配不到，**静默跳过**，
`import contextvars` 没插进去 → 60 个用例 `NameError`。
**教训：多行文本替换必须 assert。**
