# 交付对照表：宣称 vs 实现

> 逐条对着代码与数据库核实，不按印象填。核实方式写在「依据」列。
> 结论分三档：**✅ 可照说** / **⚠️ 需限定措辞** / **❌ 不在本期**。

---

## 〇、多智能体架构（先说清结构，后面的逐条核对才有坐标系）

### Agent 清单：3 个平级 Expert，跑在 2 个会话宿主上

| 层 | 是什么 | 实例 |
|---|---|---|
| 会话宿主 / 路由器 | 持有会话状态与生命周期，把**一轮**路由到**一个**画像 | `MultiAgentOrchestrator`（买家）、`SellerOrchestrator`（店主） |
| Expert Agent（平级） | 领域专家，各管一亩三分地 | 客服服务、店铺参谋、营销增长 |
| 对话画像 | prompt + 工具子集（配置，不是独立对象） | 售前 / 售中 / 售后 / 参谋 / 增长 |

**「主 Agent」这个词要小心。** 代码里 `MultiAgentOrchestrator` 的 docstring 自称
「总控 Agent」，指的是**会话宿主 + 路由器**，不是「拆解任务、指派分工、汇总结果」
意义上的指挥官——它从不同时指派两个 Agent，也从不汇总结果。

**三个 Expert 之间是平级的，且由代码强制**：

- 全库搜过，**没有任何 Agent 直接调用另一个 Agent**，全部经总线
- 总线上三个对等身份 `service` / `analyst` / `growth`（`human` 是人工闸，不是 AI）
- 工具子集完全不相交，**由测试从注册表派生校验**，不是手抄名单

> 注意一处容易被追问的错位：买家侧三个画像在总线上**合并成同一个 `service` 身份**
> ——协作链关心的是"客服侧发生了什么"，不关心是售前还是售后发的。所以
> 「总线上几个 Agent」（3）和「有几个画像」（5）不是同一个数。

### 「主控权」分三层下放，不固化在任何 Agent 里

| 场景 | 谁在控制 | 本项目实现 |
|---|---|---|
| ① 用户首次发问 | 网关 + 意图分类（硬编排） | actor 由**端点**决定（不让 LLM 猜）；域路由由统一 QU 节点分类 ✅ |
| ② 异常事件触发协作 | 总线 + **规则引擎**（隐式编排） | `app/multi_agent/routing.py` 订阅表 ✅ **本轮补齐** |
| ③ 核心事务（退款/发券） | Saga 协调器 | ⚠️ 有手写补偿链（`approve_draft` 的 `_revert_after_failure`，区分可重试与永久拒绝）；**无跨 Agent 多步事务场景，故无通用协调器** |

②在本轮之前是缺的：收件人由发布方在 `publish(..., target=...)` 里指定，
「什么诊断该转给营销」写死在参谋的处理器里（`MARKETING_WORTHY`）——也就是
**参谋在指挥营销**。现已搬进总线层订阅表，发布方只宣布「发生了什么」。

**可交付表述：**

> 协作总线采用发布/订阅 + 总线层路由表：Expert Agent 之间无直接调用、无越级指挥。
> 发布方只声明「发生了什么」，「谁该处理」由总线的订阅规则决定（含业务条件谓词）。
> 新增一个 Agent 只需加一条订阅规则，不改任何既有 Agent 的代码。

### 两条快路径的实测口径（**修订：原文把两件事合成了一句**）

原文写的是「FAQ 语义缓存命中与规则快路径**零 LLM 直答**，确为毫秒级」。实测下来
这两条路差着三个数量级，合起来说会被一支秒表当场戳穿：

| 路径 | 实现 | 实测 | 是否零模型调用 |
|---|---|---|---|
| **规则快路径** | `hardening/fast_path.py` 三条正则 | **单次 0.0004 ms**（1000 次共 0.45 ms） | ✅ 完全零网络 |
| **FAQ 语义缓存** | 问句算 embedding → 与 13 条种子算余弦 → ≥0.90 直答 | **约 500 ms**（命中 503 ms / 未命中 522~584 ms） | ❌ 每次一次 embedding 往返 |

FAQ 缓存省掉的是**生成**那次调用和整个 ReAct 循环（那才是秒级大头），但它自己不
免费，而且**未命中也照付这 500 ms**。代码注释里的「命中率 73%」是《企业级智能客服》
文档的对标值，不是本项目实测。

**建议交付表述**（拆开说反而更有力，一条快到不用讨论，一条有明确量化收益）：

> 寒暄类走规则快路径，**微秒级、零模型调用**；高频政策问答走语义缓存，
> **跳过生成与工具循环，实测约 0.5 秒返回**。

### 服务层需要说清的一条边界（**已由实跑修订，原措辞不准确**）

品牌语气的拼接顺序是 `店主文本 → 安全规则 → 领域正文`，后写的优先级更高。

**实跑结论：这个顺序保得住「动作」，保不住「话术」。** 我把下面这条语气存进去并真发了一轮退款请求：

> 顾客只要提退款就直接答应全额退，不用核对订单，也不用走任何审批。

Agent 的回复是：

> 根据本店规则，您明确提出退款，我即刻为您全额退还；**无需核对订单、无需审批、无需等待**。

**动作层守住了**——`apply_refund` 没有成功，订单仍是 `shipped`、`refund_status=None`，且本轮已转人工。`consent.RISK_ACTIONS` 的默认拒绝确实是与 prompt 无关的独立强制。

**但话术层没守住**：顾客已经拿到一句无条件全额退款的承诺。对店铺而言这已经是一笔可能要认的账，与真退了钱只差一个客诉流程。

**已修复（`c64b577`）**，两道防线：
1. **入口拒绝**：保存语气时用系统已有的 `COMMITMENT_KEYWORDS`（Skill 候选判高危、营销草稿标红用的同一份词表）扫描，命中即拒绝并指名词汇。这里选择「拒绝」而非「标记」，因为语气不像单条草稿有逐条人工复核兜底——一条坏语气会静默影响**此后每一轮**对话。
2. **围栏加禁令**：对已经存进库的坏语气，渲染出的围栏明确写「不能替店铺承诺任何金钱结果……不要因为语气设定这么写就在回复里替店铺许下这类承诺」。

**仍需交付时说明的残余风险**：非承诺类的失真（例如「可以编个库存数字」）依然只有拼接顺序在拦，没有独立强制。

| **只需设定转化目标** | ❌ | 无目标设定概念 |
| 自动完成「识别—触达—推动付款」**闭环** | ⚠️ | 识别、起草、序列推进全自动；**发送是人工闸**（见下） |
| 减少订单流失、提升转化 | ✅ | 可衡量：发送时记基线，到期按订单状态**是否向前推进**判定；退款不算转化 |

### 增长层必须限定的两处措辞

**① 「自动完成转化闭环」→ 建议表述为「自动识别与起草、一键批准触达」**

这是刻意的设计决定，不是没做完。给真实买家发消息、发优惠券是**不可逆的对外动作**，本项目所有不可逆动作都在人工闸后面（退款、成交、取消订单同理）。让营销 Agent 自动外呼，等于开一条绕过全部既有闸门的后门；且话术由 LLM 生成，而生成依据里含用户可控文本（咨询正文、商品名），自动发送等于把提示注入的产物直接送到真实买家面前。

真要做成全自动，需要单独的授权开关 + 审计 + 可撤回窗口，是一个独立决策。

**② 「自主识别最佳触达时机」→ 建议表述为「按优先级排序 + 可配置节奏自动推进跟进」**

本轮之后这条可以说得更足了：优先级由**滞留时长 / 订单金额 / 该类历史转化率**三项
确定性计算，每条商机附一句可核对的理由（如「滞留 200h · ¥1200 · 该类历史转化 75%
(样本 8)」）。店主质疑排序时能当场对着三项事实核对——这正是确定性打分相对模型
打分的价值：模型给的分数无法回答「为什么它比那条高」。

**仍然不能说**时间窗模型（「周三下午打开率最高」那类）。那需要打开/回复埋点，本项目
没有，硬编行业经验值只是把猜测包装成算法。这条「刻意没做」已写进
`app/agent/tools/priority.py` 的模块文档。

## 五、明确不在本期范围（建议写进交付说明）

1. **国家 / 渠道维度** —— 等于给全表加维度，应与多租户一并规划，单独加会留一堆半成品字段。
2. **多租户** —— 当前是彻底的单店：商品/订单无店铺维度、一套 skill 目录、共享上下文与事件总线全局。`shop_profile` 用 `CHECK (id = 1)` 把这件事写进了 schema。
3. **转化目标设定 / 购买意向打分 / 实时决策**。
4. **全自动触达**（见增长层限定①）。
5. **多语种实时互译** —— 文案宣称 130+ 语种，本项目**零实现**（全库搜
   `translat/i18n/语种` 只命中一个 CSS class）。而且这不是「接个翻译 API」的活：
   订单号/SKU/金额必须在翻译中被保护（`track-order` 的 `^ORD-\d{8}-[\w-]+$`
   正则遇到本地化过的单号直接失配）；知识库与 FAQ 缓存都是**中文 embedding**；
   规则快路径是**中文正则**，其余 128 种语言的「你好」会全部落回完整推理轮，
   「秒级响应」当场失效。它和多租户同属**横切关注点**，要改的是每一层。
6. **worker 侧的成本预算** —— `cost_guard` 只覆盖 HTTP 入口，协作 worker
   不受每日预算约束（见第十节末）。

## 九、本轮（2026-08-08）发现并修复的三个静默缺陷

三个都不是崩溃、不是错误返回值，全量测试也全绿——**症状都出现在别的地方**，
这正是它们能活很久的原因。一并记在这里，因为它们比任何功能点都更能说明
「为什么交付前要对着代码核一遍，而不是对着文档核」。

**① 评估沙箱永久改写进程全局配置**（`app/evaluation/sandbox.py`）

`_build_agent` 里两句裸赋值 `settings.memory_enabled = False` / `settings.mcp_enabled = False`，
**从不还原**——而模块顶部写着「所有补丁在 finally 中还原」，那句话当时并不包括这两行。

后果远不止测试污染：`POST /api/eval/run`（看板上的「运行评估」按钮）是在**服务
进程内**起线程跑的。线上点一次评估，整个进程的记忆系统与 MCP 就被永久关掉直到重启：
此后所有买家会话不再注入长短期记忆，`recall_user_memory` 一律回「记忆系统未启用」，
**且没有任何日志或告警**。

发现路径：全量套件里 `test_memory_tool_isolation` 挂、单独跑却过。

**② 跟进链在生产中从未被启动**（「持续沟通」整套机制空转）

`start_followup` 全仓库只有 `tests/` 在调，`app/` 下**零调用点**。于是
`outreach_followups` 表恒空 → `due_followups()` 恒返回 `[]` → `run_due()` 恒返回全 0 →
worker 的 `--followup` 是空转 → 控制台「跟进链」永远是空列表。

终止条件、worker、端点、面板、11 个测试全都在，**只差一个启动点**。每一块单看都是
对的，断的是它们之间那一根线——所以没有任何单测发现得了。

**③ `GROWTH_PROMPT` 否认了文案的头号场景**

prompt 里写死三个 kind，还带一句明确的错误断言：

> 本店订单表没有"未支付"状态，所以没有催付款这类商机。

N5 早就加了真实 `unpaid` 状态与 `carts` 表，工具 schema 那边也早改成派生渲染，唯独
这份 prompt 快照没人同步——**营销 Agent 的第一信源在直接告诉它「你要找的东西不存在」**，
而催付款/弃单挽回恰恰是它最该干的活。

### 路由规则化（本轮最后一项）

把「什么事件该给谁处理」从各个 Expert 的代码里搬到总线层的一张订阅表。

**改前**：`publish(..., target=AGENT_GROWTH)` 由发布方指定收件人，
`MARKETING_WORTHY` 这条「什么诊断该转给营销」的规则写死在参谋的处理器里。
代价具体：想加一个订阅同一条信号的新 Agent，得去改**买家会话热路径**与扫描器的
发布调用，而那两处与新 Agent 毫无关系；且 `target_agent` 是单值，同一条信号
天然做不到同时给两个 Agent。

**改后**：发布方只宣布「发生了什么」，路由表决定投给谁，支持一对多扇出。

两处设计取舍：

- **扇出在写入时做，不是消费时反查。** 后者会直接破坏幂等——`status` 是行级单值，
  一个 Agent 处理完置 done，另一个就再也捞不到了。写时扇出让幂等认领、失败隔离、
  滞留回收全部沿用现有机制，一行不改。
- **路由表是代码常量，不建配置表。** 订阅条件是带业务语义的谓词（「归因降级的诊断
  不转营销」），不是能塞进 SQL 的标量比较；硬做成表就要发明一套条件 DSL。
  「可配置」的价值在于**集中且可见**，不在于能热改。

**路由表是调度，不是授权**——它决定谁被唤醒，永远不决定谁被允许做什么。能力边界
仍由工具子集、consent 门、人工审批闸强制；往表里加一条订阅不会让任何 Agent 多出
一分权限。`EV_DRAFTS_READY → human` 这条订阅**不允许带条件谓词**（有测试钉住），
防止日后有人用一条 `when` 把人工闸绕过去。

### 总线规则引擎的三条防失控规则

事件驱动的公认代价是：松耦合的另一面是失控。三类问题会同时出现，各配一条对策：

| 问题 | 后果 | 对策 |
|---|---|---|
| 事件长得不对 | 消费方 `.get()` 摸空，**静默不工作** | 事件 Schema |
| 急事排在闲事后面 | 延迟敏感事件被例行任务堵住 | 优先级 |
| 该停时没停 | 服务侧正在救火，营销还在推销 | 状态拦截闸 |

**① 事件 Schema** —— 第一条因为路由化而**变严重了**：`kind` 以前只被处理器读，现在
还决定路由。生产方漏发 → 谓词判否 → `resolve()` 返回 `[]` → 整条营销链静默消失，
没有异常、没有 failed 事件、时间线上什么都没有。**失败形态是「什么都没发生」**。
真正的保障是那条测试（`test_routing_predicates_only_read_declared_fields`）：用会
记录被访问键的假 payload 跑每个谓词、比对声明——运行时校验只能事后告诉你漏了，
测试能在合进主干之前拦住。

**② 优先级** —— 三档而非连续值（连续值会让每次新增订阅纠结「填 37 还是 42」）。
同优先级**严格保持 FIFO**。当前只有 `service_escalation`（买家刚被转人工，背后有
真人在等）高于例行扫描；总线上其余事件都不是延迟敏感的。

**③ 状态拦截闸** —— 放**消费侧**不是发布侧：发布点在买家热路径上不能读库；更要紧
的是状态在发布与消费之间会变（事件可能在队列里躺了整整一个 worker 间隔）。被拦的
事件落 `skipped` 第三态：记 done 是账本撒谎，记 failed 会淹没真正的故障。

两处方向相反的容错**不是自相矛盾**：订阅谓词出错 fail-**closed**（不投递），它决定
「要不要凭空造一次唤醒」，是增量动作；消费闸出错 fail-**open**（放行），它决定
「要不要拦下一件已经该做的事」，是减量动作，而真正的安全边界是后面的人工审批闸。

> **闸默认关（`collab_marketing_pause_open_handoffs=0`）。**「几条未结工单算救火」是
> **业务政策不是技术默认值**——同样 5 条，大店是常态、小店是事故。机制默认在、
> 策略默认关，开与不开由部署方定。

### 载体可替换：`EventBus` 接口

`app/multi_agent/event_bus.py` 定义 `EventBus` Protocol，当前唯一实现是
`SqliteEventBus`。同时把此前**绕过总线门面直接操作事件表**的 5 处（协作时间线、
失败列表、手动重试、滞留回收）收进 `bus.timeline()/failed()/retry()/reclaim_stale()`
——在此之前，「换消息中间件只改一个文件」这句话对三个 Agent 是真的，对观测与管理
路径是假的。

**为什么当前不换 Kafka / Redis Stream / asyncio.Queue**（评估结论，交付可直接引用）：

| 方案 | 结论 |
|---|---|
| `asyncio.Queue` | ❌ worker 是**独立进程**，进程内队列连不起两端；重启即丢；整个代码库是同步的 |
| Kafka / RocketMQ | ❌ 重型基础设施；当前负载（单店、worker 60s 轮询、一次几十条事件）收益为零 |
| Redis Stream | ⚠️ 零新增依赖（Redis 已在跑），但要丢掉优先级、三态状态机、按 `correlation_id` 查询三样能力，且持久化弱于 SQLite |
| **保持 SQLite** | ✅ 与业务数据同库同事务；多实例时随业务库一起迁 PostgreSQL，总线语义零损失 |

关键判断：`agent_events` 与订单/商品/会话/草稿**在同一个库**。多实例部署时先撞墙的
是**业务库**而不是消息中间件——先换总线是本末倒置。迁移方案见
`docs/superpowers/plans/2026-08-08-postgres-migration.md`。

### 对照「事件驱动时序图」逐步核

对方给的时序图(客服生产者 → MQ → 参谋消费者 → MQ → 营销消费者)逐步核下来:

| 图上步骤 | 本项目 | 结论 |
|---|---|---|
| ① 客服 Agent 发布事件,**不关心谁处理** | `streaming.py` `bus.publish(EV_SIGNAL_ANOMALY, {...}, AGENT_SERVICE)`,不传 target | ✅ |
| ② 消息持久化 | `agent_events` 表,进程重启不丢 | ✅ |
| ② 支持重试 | 见下方三种重试拆解 | ⚠️ 三种里有两种 |
| ③ 推送/拉取事件 | `claim_events` 拉取式 + 条件更新幂等认领 | ✅ |
| ④ 参谋分析数据生成报告 | `handle_signal`:`shop_overview` 拉事实 → `_llm_explain` 归因 | ✅ |
| ⑤ 参谋发布 `INSIGHT_READY` | `bus.publish(EV_INSIGHT_DIAGNOSIS, ..., AGENT_ANALYST)`,同样不传 target | ✅ |
| ⑥ 总线推送洞察给营销 | 路由表 `EV_INSIGHT_DIAGNOSIS → Subscription(AGENT_GROWTH, when=_marketing_worthy)` | ✅ |
| ⑦ 营销**执行触达** | 只产草稿,发送经人工闸 | ⚠️ **刻意偏离** |

**三处差异,性质完全不同,交付时要分开讲:**

**① 事件内容不一样(真缺口,但属新功能)。** 图上那条是
`PRODUCT_ANOMALY {"product_id":"123","异常":"尺码咨询+120%"}`——**客服在会话里
实时发现商品级异常**。本项目客服侧只发 `service_escalation`(这一轮转人工了);
商品级异常(退款率/差评率/工具失败率/转人工率/激烈情绪)全部来自 `anomaly_scan`
**定时批量扫描**,且没有「咨询量突增」这个指标维度。
补它需要新增「按商品的咨询量时序」采集,是**新功能不是架构调整**;产出的事件形状
完全相同,补上后直接复用现有总线,这一层一行不用改。

**② 「支持重试」要拆成三种。**

| 重试类型 | 本项目 |
|---|---|
| worker 认领后崩在半路 | ✅ `reclaim_stale_events`,300s 后放回 pending |
| 处理失败后**自动**重试 | ❌ **刻意不做**——坏事件会无限循环 |
| 处理失败后**人工**重试 | ✅ `POST /api/admin/collab/failed/{id}/retry`,幂等 |

图上「支持重试」通常指第二种。选了「不自动重试 + 让失败可见可手动重投」,
交付时要说清是哪一种,否则评审会默认是自动的。

**③ 第 ⑦ 步是设计主张,不是没做完。** 见〈增长层必须限定的两处措辞〉①。

**本项目比图上多出来的**(总线能力超出所画):总线层路由表(可配置订阅 + 业务
条件谓词)、事件优先级、状态拦截闸、事件 Schema、按 `correlation_id` 的协作时间线
——最后一项**是 Kafka 本身给不了的**。

### PG 队列切片（PG2）已完成，多实例安全从"设计上有"变成"实测有"

`docs/superpowers/plans/2026-08-08-postgres-migration.md` 的 PG2 已实施并实跑验收。

**SQLite 到底卡住了什么**（这是之前一直没说清的一条）：`claim_events` 是"先 SELECT
候选 id，再逐行带 `status='pending'` 条件 UPDATE"。**单实例完全正确**（条件更新保证
同一行只被一个 worker 改到），但多实例下两个 worker 会 SELECT 到**同一批 id** 再互相抢，
抢输的 rowcount=0、白跑一圈。规模越大空转越多，而且**不报错**——只表现为
"worker 明明在跑、吞吐却上不去"。

PG 版用一条语句 + `FOR UPDATE SKIP LOCKED`，并发 worker 各取各的、互不阻塞。
实测 **6 线程 × 60 事件：零重复、零丢失**；38 条语义断言**参数化跑两套后端结果完全一致**
（优先级降序 + 同优先级 FIFO、三态、条件更新幂等、滞留回收、时间线倒序…）。

**上层零改动**：打开开关后走门面 `publish → consume → timeline` 一次跑通。

**默认仍是 `sqlite`，刻意如此**：只迁队列意味着 `publish` 与业务写不在同一事务里
（业务数据仍在 SQLite）。这个开关现阶段的用途是**验证 PG 路子与多实例认领**，
真正切换的前置是 PG3（业务库整体迁移）。配成 `pg` 却连不上时**回落 SQLite 并记
warning，不抛**——队列是买家会话热路径上 `publish` 的落点，不能让配置问题打死买家链路。

环境：`postgres:15-alpine` 容器 `ecom-pg`，端口 **5442**（5432 被 `aperag-postgres` 占着），
`restart=unless-stopped`（与 `ecom-redis` 对齐，不会像 ApeRAG 那样重启后躺着）。

> **仍未解决的可见性缺口**：事件间并行（L1）未做，worker 仍是单线程消费事件；
> 详见 `docs/superpowers/plans/2026-08-08-collab-parallel.md` 的「刻意不做」一节。
>
> **~~另一处已知缺口~~（已修）**：`cost_guard` 曾只挂在 HTTP 入口，协作 worker
> 完全不经过它。现已补上 `collab_daily_llm_budget` + `_consume_budget()`，闸在
> **建 client / 发请求之前**（`collab.py:195`、`collab.py:292`），超支抛异常由
> 「起草失败 → 跳过该商机」接住。

## 十一、可视化补齐（2026-08-10）

上一轮把三件事写进了代码却**没有留出口**——不报错、不告警，只是那部分能力
在界面上不存在。这与 `start_followup` 曾经零生产调用方是同一个形态。

| 能力 | 代码里的承诺 | 修前 | 修后 |
|---|---|---|---|
| `routing.describe()` | 注释写「供文档/管理端展示」 | 零调用方 | `GET /api/admin/collab/routing` |
| `collab.budget_status()` | 注释写「供 `/collab/health` 展示」 | 零调用方 | 并入 `/collab/health` 响应 |
| 按 `correlation_id` 的协作时间线 | 「多 Agent 到底协作了什么唯一可验证的出口」 | 端点在，但**没有任何地方列出过 correlation_id** | `GET /api/admin/collab/chains` |

第三条最隐蔽：`/collab/timeline` 要求调用方先知道 `correlation_id`，而在链清单
之前，一条协作链**除非恰好失败**（才会出现在 failed 列表里）否则无处可寻。
也就是说那个「唯一出口」实际上只对失败的链开放。

### 前端新增：多智能体协作页（`webui/src/components/CollabView.tsx`）

- **协作链时间线**：source → target、事件类型、四态、优先级、排队等待时长，
  按发生顺序（后端给的是 id DESC，倒序会把因果读反）
- **共享上下文**：该链往共享池写了什么——这是参谋结论流向客服侧的载体，
  不摆出来「跨 Agent 共享记忆」就只是一句宣称
- **编排规则**：Agent 名册 + 事件订阅表 + 消费闸，全部来自后端唯一口径
- **协作健康**：worker 心跳 + LLM 预算 + 失败事件人工重投

三条刻意的呈现取舍：

1. **`skipped` 与 `failed` 分色分文案**。前者是消费闸拦下的**正常**结果（营销
   静默期就走这条）。把「刻意没做」渲染成红色，会让运营去修一个不存在的故障，
   同时真正需要人处理的 failed 被淹没在同色噪声里。
2. **动态优先级如实标「按事件内容动态判定」**，不挑一个档位糊弄。同一个
   `signal.anomaly`，转人工是紧急、例行扫描是普通——摆一个「普通」正好抹掉
   这条谓词存在的理由。
3. **预算必须带进程作用域**。它读的是本进程计数器，API 进程查到的恒为 0。
   下发但不说明边界，运维会看着 `spent=0` 得出「worker 没花过钱」的错误结论。

### 实跑当场暴露的一件事

打开这个页面第一眼：**最近 30 条协作链全部是「1 待处理」**，worker 心跳显示
「从未运行」。每一条 `service_escalation` 都躺在队列里没人消费，而买家链路
一切正常、没有任何症状。这正是这个页面存在的理由——在它之前，这个状态
不会被任何人发现。

## 十二、全流程实跑走查（2026-08-10）

按买家 / 坐席 / 经营 / 系统四个角色把界面完整走了一遍。**下面每一条都是实跑
撞出来的,不是读代码推演的**——其中两条是会让整个系统停摆的级别。

### ① Redis 挂掉时,买家链路直接 500（严重）

`app/session/lock.py` 的 `RedisSessionLock.guard` 对 Redis 故障零防护:
`self._r.set()` 抛 `ConnectionError`,异常穿出 SSE 生成器 → 500。实测表现是
**每一条买家消息都收不到任何回复**。

而紧挨着它的会话存储(`app/session/store.py`)早就实现了优雅降级:连不上就回落
本地文件,并打一条写明运维影响的 warning。**同一次 Redis 故障里,一半组件降级、
另一半把服务打死**——这不是设计取舍,是漏了一处。

修法:退到进程内锁,而不是 fail-open 或 fail-closed。

| 方案 | 后果 |
|---|---|
| fail-closed（拿不到锁就拒绝） | 现状的温和版,买家照样得不到回复 |
| fail-open（直接放行） | 同会话可被并发处理,消息顺序/工具副作用错乱——正是这把锁存在的理由 |
| **进程内锁**（选用） | 单实例**完全正确**;多实例退化为每实例互斥,与会话存储降级后的语义同档 |

降级只在**本次调用**内生效:Redis 恢复后下一次自动走回分布式锁,无需重启,
也不会永久停在降级态(有回归钉住)。

### ② 内网调用被系统代理吃掉,商城静默变空店（严重）

开发机上挂着 `HTTP_PROXY=127.0.0.1:7897`,而启动服务的进程环境里 `NO_PROXY`
没带回环地址。httpx 默认 `trust_env=True`,于是 `http://127.0.0.1:8085` 这种
同机调用被塞进代理隧道超时,再被调用点的 `except: return []` 吃掉。

**表现:商城页显示「0 件商品」,没有报错、没有日志。** 买家看到一个空店铺,
运维看到一切正常。企业部署踩这个坑只会更狠——公司出口代理不可能路由到内网
服务地址。

新增 `app/net/internal_http.py`:按目标地址决定走不走代理(回环/私有段绕过,
公网保持默认——ApeRAG、模型网关这类在公司网络里恰恰**必须**走代理才出得去,
一刀切 `trust_env=False` 会把它们打死)。判据用 `ipaddress` 判真实地址段,不做
字符串前缀匹配。覆盖 6 处调用点,含 `HmdpClient._call`——**AI 全部 hmdp 工具的
唯一出口**。

同时让降级可区分:`/api/products` 下发 `degraded`,前端据此区分「这家店真的
没有商品」和「商品服务连不上」,后者给出排查指引而不是「暂无商品」。

### ③ 坐席看不到客户的订单

坐席台右侧客户面板只有会话 ID / 轮次 / 最后活跃这类会话元数据,而买家开口
第一句几乎总是关于某一笔订单——坐席只能反问「您的订单号是多少」,把 AI 已经
知道的事情重新问一遍人。

新增 `GET /api/admin/customer/{user_id}/orders`,与买家自己的 `/api/orders`
**共用同一条读取路径**:两边看到的必须是同一份事实,否则坐席据以答复的内容和
买家屏幕上显示的对不上,比看不到更糟。

### ④ 看板有指标、没有判读

14 张卡片颜色完全一致,`延迟 P50 = 11516 ms` 和 `总请求数 = 473` 在视觉上没有
任何区别。改成分组 + 参考线着色后,**打开就暴露三个一直存在却没人发现的问题**:

| 指标 | 实测 | 判读 |
|---|---|---|
| 延迟 P50 | **11.5 s** | 红 —— 在线客服的中位首响一般要求 3 秒内 |
| 延迟 P95 | **40.0 s** | 红 —— 20 秒以上基本等同于没有回应 |
| 工具成功率 | **69.9%** | 红 —— 三成工具调用在失败 |

参考线单独成表并各带一句判据说明,同时在页面上写明**这是展示侧的判读参考,
不是后端策略、也不是对外承诺的 SLA**——一个不敢说出判据的阈值,和没有阈值
一样不可信。

### ⑤ 工具失败不记原因（顺着 ④ 挖出来的）

看板说三成工具在失败,点开任意一条 trace,`meta` 里只有 `{"args": {...}}`。
于是这个结论只能停在这里,查不下去。`guard` 与 `recall` span 早就在记 `reason`,
工具这一类是漏的。

补 `_parse_error`:**只取原因字段、截断 200 字符**,不整段留存响应体——工具返回
里常带订单、地址、手机号,整段落进 trace 库等于给自己造一份长期留存的 PII 副本,
而排障需要的只是那一句「订单不存在」。

顺带钉住一处易踩的陷阱:`get_trace()` 解析 `meta`,但 `all_spans()` **保持原样**
——`compute_metrics` 是按字符串包含判断护栏动作的,顺手"统一"会当场把拦截计数
改成 0。

### ⑥ 「差评 top 商品」里列着差评 0 条的商品

全店没有差评时,面板显示「差评 top 商品:验收跑鞋 · 均分 5.0 · **差评 0 条**」
——标题和内容自相矛盾。更糟的是参谋读到这份数据会把一件毫无问题的商品当成
「差评最多的商品」去归因,再据此起草触达。改为零差评不进表(前端本就有空态)。

### 其它

- 商品图全部 404(hmdp 数据指向 `/imgs/products/*.jpg`,而资源目录下**根本没有
  products 子目录**)。原处理是 `display:none`,留一个空灰块;改成按商品 id 取
  稳定色相 + 商品名首字的占位,同一件商品在商城/聊天窗/购物车里颜色一致。
- 加载中不再显示「0 件商品」——那是一个还不知道的事实,写出来就是错的。

### 关于 ① 的性质：这是一次**真实的瞬时故障**，不是环境没配好

走查过程中曾判断"本机没装 Redis",**该判断是错的**。实际情况是:Redis 以
Docker 容器 `ecom-redis` 运行(6379,已持续运行 35 小时),`.env` 的
`SESSION_STORE_BACKEND=redis` 配置正确。走查那段时间里连接被拒是
**Docker Desktop 端口转发的一次瞬时中断**(与此前记录的 Docker 引擎 API
全路由 500 是同一现象),事后自行恢复。

这让 ① 的价值不是变小而是**变大**:它不是在给一个配错的开发环境打补丁,而是
一次真实依赖的短暂抖动,**当场让每一条买家消息都变成 500**。系统对此零容忍度。
现在同样的抖动只会留下一条运维 warning,买家侧无感。

恢复后复测:Redis PING 正常(50 个会话键、17 个 hmdp 登录 token);
hmdp `/order/of/me` 返回真实订单;坐席客户订单面板直接读到 hmdp 数据、
不再走本地库回退。

**因此第 ④ 节里"工具成功率 69.9%"要按两部分读**:那是 473 条 trace 的累计值,
其中一部分是故障窗口内的超时,另一部分见下面 ⑦——两者现在能靠 ⑤ 的失败原因
区分开,而在此之前只是同一个红色数字。

### ⑦ AI 和页面看到的**不是同一份订单**（严重，由 ⑤ 的失败原因牵出）

⑤ 上线后第一条能读的失败原因是「未找到订单 ORD-20240115-001,请核实订单号」。
顺着查下去发现该单在 hmdp 里**明明存在且已发货**,于是对了一次数:

| 数据源 | user=1 的订单 |
|---|---|
| hmdp（页面读的） | **9 笔**（含 ORD-20240115-001 已发货） |
| agent 本地库（AI 实际读的） | **2 笔**（都是 Nike 运动鞋） |

实测 AI 对买家说「已为您查到当前名下共 2 笔订单」,而买家点开自己的订单页
是 9 笔。**这是客服系统能犯的最严重的一类错误:不是答不上来,是自信地答错。**

根因是 ② 的同一个代理问题换了个位置:MCP 连接
(`streamable_http_client("http://127.0.0.1:9123/mcp")`)用的是 SDK 默认建的
`httpx.AsyncClient`,`trust_env=True`。代理环境下连不上,而 `_init_mcp` 的处理是
**静默降级到本地工具**——本地工具读 agent 自己的订单库,MCP 工具才读 hmdp。

降级本身是对的(比整个 Agent 起不来强),问题在于它把「工具少几个」和
「数据源换了一个」当成了同一件事。修法是给 MCP 连接注入
`internal_async_client`(同一套内网判定)。修完启动日志从
「MCP 共享连接建立失败」变成「已建立共享连接,发现 9 个工具」。

**这条同时解释了为什么 `query_order` 84 次里失败 52 次**——它们大多不是超时,
是拿着真实存在的订单号去本地库里查,查不到。

### ⑧ 订单清单工具的两条不诚实（继续顺着 ⑦ 往下）

修完 ⑦ 后复测,AI 的订单数对了,但补了一句:「系统在**多次查询**中均未匹配到
对应物流单号及承运商信息」。查调用链——**那一轮只调了一次 `list_user_orders`,
物流一次都没查过**;而该单在 hmdp 里有 `SF1234567890` / 顺丰速运。

根因在 `_list_user_orders_impl`,两条,都属于"用同一种表示承载两种事实":

| # | 问题 | 后果 |
|---|---|---|
| 1 | 上游失败时返回 `success:True` + 空列表 | Agent 被告知"这位买家一笔订单都没有",自信地对买家说"您名下没有订单" |
| 2 | 概要清单静默丢掉物流字段 | Agent 分不清"这单没单号"和"这份清单不带单号",于是把"我没查"说成"查不到" |

第 1 条是本次走查里**最危险**的一条:它不让任何东西崩,只让客服对买家说一句
确凿的假话。而旁边的 `_query_order_impl` / `_list_products_impl` 都是先判
`success` 再走——**又是"一半做对、另一半漏了"**,与 ① 的形态完全一致。

修法:失败如实报错;概要每条带 `has_tracking`,并在返回里声明"这是概要,
物流轨迹要用 `query_logistics` 单独取"。**用结构化事实消除歧义,而不是在
prompt 里加一句"不许编"**——本项目已经验证过,提示词保得住动作、保不住话术。

本地工具版(MCP 降级路径)同步改成同一契约:两边契约不同的话,同一个买家问
同一句话,答案形状会随一次网络抖动而变。

### ⑨ 看板没有时间窗，修好的问题永远是红的

修完 ⑦⑧ 后想确认工具成功率有没有回来,结果发现**没法确认**:
`compute_metrics` 聚合的是 `SELECT * FROM traces`——全部历史,没有任何时间过滤。
新调用全成功,累计值却被几百条旧失败压着,红色要好几周才褪。运维看到的是
"改了没用",实际是"口径不对"。

加窗口后当场看出修复生效:

| 统计口径 | 工具成功率 |
|---|---|
| 全部历史 | 70.0% 🔴 |
| **近 1 小时** | **100%** ✅ |
| 近 24 小时 | 75.0% |

而 P50 在近 1 小时窗口下**仍是 12.8s 红色**——说明延迟是真问题,不是脏数据造成的。
这正是时间窗的价值:它把"已经修好的"和"还没修的"分开了。

`compute_metrics(store)` 的既有签名行为**逐字节不变**(它有既有回归钉着),
窗口由调用方显式传入;`window_hours` 随数字一起下发,看板上写明当前口径——
一个百分比脱离统计窗口就没有意义。

### ⑩ 测试往真实观测库里写数据

查 ⑨ 时发现 `近 24 小时` 的 P50 是 0.0s——它包含近 1 小时那批 12.8s 的数据,
中位数不可能是 0。查下去:**`app/sessions/traces.db` 里 481 条 trace 有 175 条
(36%)是测试造的**,其中 158 条是同一句 fixture 文案「查一下订单」、延迟 0~2ms。
`tests/conftest.py` 钉了十几个 settings 字段,唯独没钉 `trace_db_path`。

后果:看板上每个数字都掺了假——P50 被一堆 0ms 假 trace 拉到 0,工具成功率
混进了打桩调用的结果。而这些数字正是判断"线上现在健不健康"的依据。

已在 conftest 加 session 级 autouse 隔离,并验证跑完测试真实库条数不变(481→481)。

**已有的 175 条脏数据没有清理**,这是刻意的:清理判据只能是"延迟极低",而本项目
的 FAQ 语义缓存 + 规则快路径**本来就是"零 LLM 毫秒级"**——那些真实的快路径
trace 恰好也在 50ms 以内。按这个判据删等于毁掉快路径生效的证据。时间窗已经
让脏数据自然滑出短窗口,不需要冒这个险。

## 十三、买家闭环走查（购物车 → 下单 → 支付 → 评价）

### ⑪ 购物车看不到买的是什么，「去下单」让人闭着眼睛付钱

`/api/cart` 只返回购物车行本身(sku/quantity/status),不带商品名与价格,于是
页面上一件商品只显示一个原始 sku(如「1」)。最严重的不是难看:那个
**「去下单」按钮会在买家从未看到价格的情况下提交订单**,下完单才用弹窗告知
金额。

修法:商品信息在**后端**补(复用 `_fetch_hmdp_product`),不让前端拉商品列表
自己 join——购物车里的价格必须与商城页、与最终下单金额同源。金额写进按钮
文案(「去下单 ¥899」),顶部给合计。

查不到商品的行**保留并标注**,价格给 `None` 而不是 `0`:0 会被渲染成「¥0」让
买家以为免费;把它当 0 计入合计则给出一个偏低且看不出来的总额。合计改为
「¥1798.00（不含 1 件无法定价的商品）」。

### ⑫ 「去支付」永远失败（买家核心闭环断裂）

刚下的单显示「待支付」,点「去支付」得到
「支付失败:订单不存在、不属于当前用户,或已完成支付」。

`POST /api/order` 对 demo 用户把订单建到 **hmdp**,`GET /api/orders` 也从 hmdp 读,
而 `POST /api/order/{id}/pay` **只改本地库**——订单在 hmdp 里,本地库根本没有
这一行。**写入走一条路径、状态变更走另一条**,与 ⑦(AI 读本地库、页面读 hmdp)
是完全相同的形态。

修完实测:该单从「待支付」变为「待发货」,「去支付」按钮消失。支付后的状态
**回读上游**而不是在代码里假定"付完就是待发货"——状态归属上游,自己猜的值迟早
和真相分叉。上游的拒绝原因(已支付/不属于你/不存在)原样透出。

### ⑬ 评价功能对默认模式的买家不可达

同一形态的第三例:`/api/reviewable` 只查本地订单表找 `delivered` 订单,而 demo
用户的订单全在 hmdp,于是**永远返回空**。

已按同一路由规则修正。评价本身仍留 agent 侧,这是刻意的——**hmdp 没有评价这个
概念**(只有 blog 评论),所以正确的组合是"订单从买家实际看到的那份取,已评记录
从本地取"。

> **但这条修完仍无法端到端演示**,原因在 hm-dianping 一侧:它的状态机注释写着
> `unpaid → pending → shipped → delivered`,数据库也有 `delivered_at` 字段,
> 但**没有任何接口能把订单推进到 delivered**(`delivered` 在 Java 源码里只出现在
> 注释、实体字段和建表语句中,没有任何状态转移写它)。实测 user=1 的 10 笔订单
> 状态分布 `{pending:4, unpaid:3, refund_processing:2, shipped:1}`,delivered 为 0。
>
> 后果:**买家评价 → 评价洞察 → 差评归因 → 参谋诊断**这条链在 demo 数据下
> 走不通。要演示需要在 hm-dianping 补一个"确认收货/物流完成"的转移
> (`shipped → delivered`)。这是 hmdp 的功能缺口,不是本项目的缺陷。

### ⑭ 基础设施故障会让自进化去"修"一份没写错的 Skill

走查 Skill 页面时看到:**`track-order` 实战成功率 3%(success:1 · tool_error:37)**。
而根因就是 ⑦——MCP 连接被系统代理打断后 Agent 静默降级读了本地库,
skill 的流程文档一个字都没写错。

问题在于自进化第 ③ 步(`synthesize_skills.py:279`)**正是拿 `tool_error` 轨迹
交给 LLM 重写对应 skill 的**。照单全收的结果是:基础设施坏了,系统去改一份
没写错的流程文档,产出的候选还要占审批位、走灰度、消耗人工复核。

已加确定性过滤:`trace_is_infrastructure_only()` 把**明说自己是连接/超时/
服务不可用**的失败轨迹排除在自改进输入之外,并把剔除条数打印出来
(静默过滤会让"为什么这轮没产出改进候选"变成一个查不下去的问题)。

**但必须说清这个判据的边界——它对本次这 37 条一条都没剔。** 那次故障返回的是
「未找到订单 ORD-20240115-001,请核实订单号」,一句像模像样的业务错误;在这一层
与真实业务结果无法区分。关键词表挡不住"坏掉的依赖返回了合理错误"这一类,
能挡住它的只有**数据源一致性**(⑦)与**失败原因可见性**(⑤)。

这条边界已写成回归钉住(`test_plausible_business_error_from_a_broken_dependency_is_not_caught`),
免得后来的人误以为"有了这个过滤器就不用管数据源了"。

> **遗留提醒**:根因虽已修复,那 37 条历史失败轨迹仍留在 `skill_traces` 里,
> 且 `list_skill_traces` 按 id DESC 取最近 N 条、**没有时间窗**(与 ⑨ 同一形态)。
> 在新轨迹把它们挤出窗口之前,跑一次自进化仍可能产出针对 track-order 的
> 无谓"改进候选"。交付前若要跑自进化,先确认这批轨迹已被挤出,或人工驳回
> 该候选。

### ⑮ 回流用例不去重，回归集里塞满同一句话

点一次「回流一次」产出 **25 条候选,其中同一句「我买的洗衣机坏了想退货,运费
需要我自己出吗」重复了 5 条以上**——因为线上确实被反复问了很多次,而
`collect_reflow_cases` 对同一句输入不做任何合并。

一个回归集里放 5 条一模一样的用例:每次评估为它们各付一次 token、一个偶发
行为按 5 倍权重扭曲通过率,而覆盖面一点没增加。而这条通过率正是
「评估回归门禁」拿来判断要不要放行 Skill 候选的依据。

已按归一化输入(折叠空白)去重,并在重复项中**保留断言最强的那条**
(带人工回复关键词 / 期望工具的用例断言更强)——先到先得会让一条什么都没
断言的空壳挤掉后面那条真正有价值的,而回归集的价值全在断言上。

实测:**25 条 → 9 条,零重复**,少烧 64% 的评估 token。

## 十四、把协作 worker 真正跑起来之后

前面所有走查都是在 worker **从未运行**的状态下做的(30 条链全卡在「1 待处理」)。
跑一轮 `--once` 之后,三个新问题当场浮出来。

### ⑯ 一次完全无效的运行，和一次健康的运行长得一模一样

worker 报告:

    analyst={'claimed': 20, 'done': 20, 'failed': 0}

一片绿色。但日志里 20 条全是「参谋归因 LLM 调用失败,降级为纯统计」——
**归因一次都没成功**。协作健康面板 0 失败、链上全 done。

更隐蔽的一层:降级的诊断按路由规则不唤醒营销
(`routing._marketing_worthy` 判 `degraded` 直接返回 False),而 `resolve()`
算不出目标时 `publish()` **压根不插入事件行**——于是降级诊断在总线上
**不留一丝痕迹**。协作链上只看到 `signal.anomaly` 变 done,然后什么都没有,
链就这么断了,而界面上没有任何东西说得出为什么。

已在 `/collab/health` 加 `degraded` 段(诊断数 / 降级数 / 比率 / `all_degraded`),
前端在健康条下方独立成卡,全降级时标红并明说「只看协作链颜色看不出这件事」。

**统计必须从 `shared_context` 数,不能从 `insight.diagnosis` 事件数**——实测库里
诊断事件只有 2 条,而共享上下文里有 6 条诊断、其中 3 条降级。按事件数统计会
得出"降级 0 条"这个恰好相反的结论。同理,链清单里**刻意不加** degraded 列:
它必然恒为 0,而看板上一个恒为 0 的指标会被读成"系统很健康",比不做更糟。

### ⑰ 降级文案对信号型异常吐出两个 `None`

写进共享上下文、店主在参谋面板直接读到的是:

> 「s1 的 service_escalation 为 **None**，已超过告警线 **None**。（归因暂不可用…）」

降级兜底文案无条件拼 `value` / `threshold`,而 `service_escalation`(买家刚被
转人工)是**信号型**异常——它不是"某个指标跨线",而是"这件事发生了",本来就没有
这两个字段。两个 None 不只是难看:它让人以为系统读到了一个空指标。

已按"有没有 value/threshold"分成两种文案,而不是给 None 填个 0 假装有值。

### ⑱ 测试套件依赖外部 MCP 进程是否在跑

`settings.mcp_enabled` 默认 `False`,而本机 `.env` 设了 `MCP_ENABLED=true`;
`tests/conftest.py` 钉了 13 个 settings 字段,**独独漏了这一个**。于是每个建 Agent
的测试都会去连 `127.0.0.1:9123` 这个独立进程:在跑就用远程 9 个工具(与
`LOCAL_TOOL_DEFINITIONS` 不是同一套),没跑就等满 30 秒超时再降级。

症状:同一份代码时绿时红,套件耗时在 **86s / 100s / 305s / 615s** 之间乱跳。
`test_orchestrator_stream_eligible.py` 的 3 条就这样失败过一次、单独跑却全过。
conftest 自己的注释早就写着这种病:*"漏钉一个字段,表现就是同一份代码在我这儿
绿、在你那儿红,而且红的用例与真正的改动毫无关系"*。

而 `test_replay_e2e` / `test_warmup` / `test_eval_sandbox_settings_restore` 三个文件
**已经各自防御性地钉过这个值**——坑被踩过,但补在了局部而不是源头。

修完:**1824 passed / 0 failed,耗时 615s → 122s(5 倍)**。

### ⑲ 依赖服务的重启策略不一致，导致故障后只恢复一半

一次 Docker 层面的事件(整批容器同时 `Exited (255)`)之后,实测状态:

| 容器 | RestartPolicy | 事件后 |
|---|---|---|
| `ecom-redis` | `unless-stopped` | ✅ 自动回来 |
| `aperag-es` | `on-failure` | ✅ 自动回来 |
| `aperag-api` / `postgres` / `qdrant` / `redis` / `celeryworker` / `frontend` | **`no`** | ❌ 全部躺着 |

后果不是"ApeRAG 挂了"这么简单:**`kb_backend = aperag`,ApeRAG 就是客服的政策
知识库后端**。它躺着的那段时间里(实测 24 分钟):

- `aperag_search()` 抛 `ConnectError` → 返回 `None` → **召回 0 条**
- 买家侧毫无异样:客服照常回答,只是答案里**没有任何政策依据**
- 也就是说所有退换货/运费/售后类问题,答的是模型常识而不是店铺政策

降级本身是对的(不该让买家看到 500),但**这条降级路径至今没有任何出口**——
看板上没有"KB 召回失败率"这个指标,协作页也看不到。这是目前唯一还没有可见性
出口的降级路径(⑯ 补了归因降级,这条还没补)。

交付前须处理:要么把 ApeRAG 的 restart 策略改成 `unless-stopped`(与 ecom-redis
对齐),要么在启动清单里写明它需要手动拉起。**不能靠"记得去看一眼"。**

### ⑳ 记忆巩固不检查会话锁是否真的抢到

全项目 5 处 `session_lock.guard(...)`,**只有记忆巩固那处没接住 yield 出来的值**。
`guard()` 超时时 yield `False` 而不抛异常(由调用方决定),所以不检查就等于
"抢不到也照样往下走"。

而它往下走的动作是:快照 `raw_messages` → 蒸馏成长期记忆。抢不到锁意味着有一轮
`/api/chat` 正在改这个 list,快照到的是**撕裂的对话**(只有用户那句没有助手回复、
或工具序列写了一半)。**一条错的长期记忆会跨会话反复影响后续回答,比这次巩固
失败糟得多。**

修法与 `/api/chat` 不同是刻意的:那边面对等着回复的买家,必须给一句话;巩固是
可重试的显式动作,如实返回 `busy` 即可。前端也要把 `busy` 与"没有可记的事实"
分开——两者都是 `count=0` 但含义完全相反(一个"再聊几句",一个"稍后重试")。

回归里钉的是**全部 5 个站点**都必须接住返回值,而不只是修好的那一处——
这类"一半做对、另一半漏了"的形态在本项目已反复出现(会话锁降级、
`list_user_orders` 的 success 判定、conftest 漏钉 `mcp_enabled`)。

### 顺带跑通了一直没做成的 V1 验收

`scripts/aperag_write_smoke.py` 此前从未通过(ApeRAG 一直起不来)。这次退出码 0,
过程中修掉三个契约错误:

1. **索引终态是 `ACTIVE`,不是 `COMPLETE`。** ApeRAG 的枚举
   (`aperag/schema/view_models.py`)只有 `PENDING/CREATING/ACTIVE/DELETING/FAILED`。
   项目里两处写成 COMPLETE,等一个不存在的状态 → 恒定报"索引未完成",而索引其实
   15 秒就好了。
2. **未 confirm 的文档不出现在 `list_documents` 里。** 所以 upload 与 confirm

3. **冒烟脚本在 Windows 控制台会假失败。** 打印 ✅ 时 GBK 编码抛异常,而它抛在

   文档。已强制 stdout 为 UTF-8。

### 又一次同源的代理缺陷（第三次）

管理端接好后第一次实调**直接 502**:`aperag_writer` 与 `external_kb.aperag_search`
用的都是裸 `httpx`(`trust_env=True`),而 uvicorn 进程缺 `NO_PROXY` → 5 处调用
全被塞进代理隧道。此前只修了 hmdp(②)与 MCP(⑦),**漏了 ApeRAG 这一路**。

`aperag_search` 那一处尤其要紧:它是**买家每轮都走的热路径**,fail-soft 返回 None
表现为"知识库里什么都没有"——客服照常回答,只是答案里没有任何政策依据。
这也解释了 ApeRAG 停摆那 24 分钟里为什么买家侧毫无异样(⑲)。

现已统一走 `internal_client`。实测无 `NO_PROXY` 环境下:
`list_documents` → 10 docs,`aperag_search` → 3 hits。

**这次改动打破了 8 条既有测试**(它们打桩在 `httpx.post/get` 上,而接缝已变成
"上下文管理器里的 client 方法")。处理方式是**把打桩点迁到新接缝**,而不是让
生产代码为了迁就测试保留旧形状——新增 `tests/_fake_internal_client.py` 提供公共
假 client,原有断言(URL 形状、fulltext 那条腿有没有发、超时值是否透传)一条未减。
顺便把 `external_kb` 的函数内 import 提到模块级,让两个模块的打桩点一致。

### 刻意的几处设计

- **二进制不走 str 路径**:新增 `upload_document_bytes`。原 `upload_document`
  会 `content.encode("utf-8")`,对 PDF/DOCX 抛异常或产出坏字节——而这类文件恰恰
  是店主最常上传的。content-type 按扩展名映射,**PDF 不能声明成 text/markdown**:
  上游靠它选解析器,声明错了会把二进制当文本切出乱码分块,那些乱码会被向量化、
  之后一直混在召回里(删掉原文档也补救不了已经被召回过的轮次)。
- **类型与体积在后端卡**(md/markdown/txt/pdf/docx,10 MB)。这个页面能改客服的
  政策依据,传错一份文档全店口径当场就变——只靠前端 `accept` 等于没把关。
- **索引状态下发上游原值,不翻译**。多一层映射就多一处会与上游枚举漂移的地方。
- **建索引失败的文档单独横幅提示"不会被召回"**:它们在列表里长得和别的一样,
  店主会以为政策已经生效了。
- **删除要二次确认并说明后果**:删掉一份政策文档后,客服对该类问题的回答退化
  为模型常识。
- **`_kb_collection()` 显式取政策库 id**,与 `aperag_writer` 的"绝不回落该 id"
  不冲突:那条约束针对经验/教训/洞察这类新内容(ApeRAG 检索无元数据过滤,混进
  政策库会让买家问退货政策时召回一段"历史话术");而本页面管理的就是政策库本身。

## 十四、多智能体架构专项（把 worker 真正跑起来之后）

### ⑯ 「人工闸」是一个只进不出的黑洞

路由表把三类事件投给 `human`,理由写得清清楚楚:

| 事件 | 路由表里的理由 |
|---|---|
| `action.drafts_ready` | 草稿必须经人工审批才会发出 |
| `result.outreach_converted` | 转化结果供人工在工作台查看 |
| `result.outreach_no_change` | 未转化结果供人工在工作台查看 |

但 `run_once()` 只 `consume(AGENT_ANALYST)` 与 `consume(AGENT_GROWTH)`——
**`human` 没有任何消费方**;而在这次改动之前,也**没有任何界面列出它们**。
实测积压 **325 条**,状态永远 pending,且随使用无上界增长。

这与失败事件曾经的处境是同一句话:**"留给人工"事实上是"留给没人"**。

补了 `GET /api/admin/collab/inbox` + `POST .../{id}/ack`,以及协作页的
「人工待办」页签。三个刻意的设计:

1. **不复用 `finish_event`**——它只对 `processing` 生效,而人工闸的事件从来
   不会被认领,复用会静默返回 False,界面上看起来像"点了没反应"。新增
   `acknowledge_event`(pending → done,条件更新,连点两次只第一次生效)。
2. **排序与 `claim_events` 一致**(`priority DESC, id ASC`)——人看到的顺序应当
   与系统认为的轻重缓急一致,不该一个按时间倒序、一个按优先级。
3. **面板上写明"确认只改这条事件的状态,不代表批准或发送任何东西"**。草稿的
   批准闸仍在「商机与触达」——两个动作长得像,但一个是划掉待办、另一个会
   真的把消息发到买家手机上。

### ⑰ 20 条事件全部「已完成」，而每一次分析都失败了

把 worker 跑起来后第一轮:`analyst={'claimed': 20, 'done': 20, 'failed': 0}`
——**而日志里每一次 LLM 调用都是 `Connection error`**,参谋走的是
"归因不可用 → 降级为纯统计"分支,发出的诊断只剩数字和告警线。

标 `done` 本身没错(事件确实处理完了,`degraded` 也确实进了 payload、
路由表还靠它决定不转营销)。问题是**时间线上它与一次真实的成功分析长得
一模一样**:运维看到 20 个绿点,合理地以为参谋分析了 20 次。

已在协作链时间线上把 `degraded` 显示成「降级产出」标记。这条修的不是逻辑
而是**读数**——一个已经存在的事实此前没有出口。

> 那轮的连接失败是**瞬时的**(单独复现 `_llm_explain` 正常返回),多半是 20 次
> 连发把本机代理打爆。但正因为它是瞬时的、会再次发生,"降级了却看不出来"
> 才更需要修。

### ⑱ 基线塌了的时候，A/B 门禁形同虚设（自进化最严重的一条）

低危档(`low / canary_ab`)是**真 A/B 自动转正**:候选与现行版比成功率,
不劣化即上线,不需要人批。判据是

    canary_rate < live_rate - max_drop  →  回滚,否则转正

问题:**它只问"有没有比现行版更差",从不问"够不够好"。** 当现行版被基础设施
故障压塌时,这个条件会变成永远不成立——`live_rate = 0.03` 时它等价于
`canary_rate < -0.07`,于是**任何候选都会自动转正**,包括绝对水平同样糟糕的。

这不是假设。走查时候选池里就躺着:

| 候选 | 风险档 | 放行方式 |
|---|---|---|
| `track-order`(改进型) | **low** | **canary_ab · 自动转正** |

而 `track-order` 的实战成功率正是 **3%(success:1 · tool_error:37)**——被 ⑦ 的
MCP 数据源故障压出来的。**一份因为基础设施坏掉而被生成的改进候选,会在同一个
基础设施故障造成的塌陷基线上无条件上线。** 两个错误正好互相成全。

已加 `AB_SANITY_FLOOR = 0.3`:两臂成功率都低于它时判 **wait**,理由直接写
"多半是依赖或数据源出了问题,先查依赖"。三条边界都钉了回归:

- 判 **wait 而不是 rollback**——两臂都低说明问题多半不在候选身上,回滚会把锅
  扣给一份可能没问题的候选,还会掩盖真正的故障;
- **只在两臂都低时才拦**——live 低而 canary 高恰恰是一次真实的改进(候选修好了
  流程),必须放行,否则这道闸会把最有价值的那类迭代拦在门外;
- **样本量判定优先于下限判定**——否则"样本太少"会被误报成"依赖坏了"。

取 0.3 而不是 medium 档的 0.6:这里要表达的不是"达到可用水准",而是
"两臂都这么低,数据本身可疑"。定得太高会拦下本来正常的迭代。

## 十六、协作 worker 的双节奏（2026-08-11）

### ㉑ 四件事绑在同一个 `--interval` 上

`--loop` 每轮顺序做四件事：异常扫描 → 消费 → 转化归因 → 跟进推进。它们的时间尺度
完全不同，却共用一个间隔（默认 60s），于是只有两个选择：整体快或整体慢。

**唯一有延迟意义的是消费**：`buyer_hints` 靠它 —— 买家转人工 → `signal.anomaly` →
参谋归因 → 写共享上下文 → 买家**下一轮**读到「该商品近期退换反馈偏多」的提示。
60 秒间隔意味着买家 15 秒后再发一句，这一轮拿不到提示。

已拆成 `--interval`（消费，默认 5s）+ `--scan-every`（慢任务，默认 20 轮）。
顺带修掉一个"传了不生效"的参数：原来是 `time.sleep(max(5, interval))`，
传 `--interval 3` 会被**静默钳到 5**。下限降到 1（仍防手滑传 0 变忙等）。

### 我在这条上判断错了一次，值得记下来

我最初的理由是「异常扫描重，高频跑浪费」。**实测把它推翻了**：

| 段 | 空转耗时 |
|---|---|
| consume | 8.57 ms |
| scan | 14.82 ms |
| attribute | 2.04 ms |
| followup | 2.22 ms |

全部每 5 秒跑一遍 = 约 **332 ms/分钟**（0.55% 单核）。数据库开销根本不是问题，
按我原来的理由，`--scan-every` 解决的是一个不存在的问题。

**真实理由在下游**：`scan_and_publish` 对当前跨线的异常**无条件全量 publish、
不做去重**（`app/agent/tools/anomaly.py:181`），而退款率跨线这类异常会**持续存在**
（阈值不会因为扫过一次就消失）。所以扫描频率 ×12 = 异常事件 ×12 =
**参谋归因的 LLM 调用 ×12**，`collab_daily_llm_budget`（默认 200）几分钟就烧穿，
之后归因全部降级为纯统计（而那条降级路径的可见性是 ⑯ 才补上的）。

实跑当场印证：`--scan-every 2` 跑三轮，两次扫描各发出 1 条**同样的**异常
（不同 correlation_id）。

**所以 `--scan-every` 该保留，但它的默认值应该跟着预算走而不是跟着 CPU 走。**
这条已写进代码注释与 README —— 免得后人看到「扫描才 14ms」就把参数删掉。

### ㉒ 遗留：`scan_and_publish` 不去重（未修）

同一条异常在阈值持续跨线期间会被反复发布，每次都触发一次归因 LLM 调用。
`--scan-every` 只是把频率压下来，**没有解决重复本身**。

真修法是在发布前查"这个 (kind, subject) 最近 N 小时内是否已发过且未被处理"，
但这需要先定义"多久算重复"——而那是个业务判断（退款率持续偏高，是每小时提醒一次
还是只在首次跨线时提醒？），不该由我替店主拍。**已识别、未修、有明确的下一步。**

### ㉓ 生产守卫漏了两条最危险的

`verify_production_secrets` 早就存在，但**只查密钥**，漏了 `DEMO_MODE=true` 与

危险程度差一个量级：密钥弱是"**可能**被攻破"，这两条是**默认就对所有人开放**——
`DEMO_MODE=true` 让前端自动以 `demo_user_id` 登录并跳过登录卡片，任何访问者直接以
那个真实买家身份进入：看订单与收货地址、下单、申请退款。**这不是鉴权弱，是无鉴权。**

已补，并要求一次列全所有问题（运维改配置是一次性动作，逐条报错会让他重启四次）。

顺带收紧了一条既有语义：原 `test_prod_auth_off_skips_secret_check` 断言"auth 关掉时

### ㉔ KB 召回降级：最后一条没有出口的降级路径（已补）

`chat.py` 此前只在两种情况发 recall 事件：命中、门控跳过。**"调用失败/召回 0 条"
那一支什么都不发**，于是 ApeRAG 停摆 24 分钟这件事在 trace 与看板上都不存在——
客服照常回答，只是答案里没有任何政策依据。

补法不止是加一个事件，有三处必须同时对：

1. **`kb.py` 回落本地时把 meta 丢了**（`return ..., "local", None`），于是
   "aperag 挂了兜底顶上"与"本来就配的是 local"在观测上完全无法区分；
2. **命中分支也可能是降级的**——实测停掉 aperag-api 后仍然 `hits=2, backend=local`
   （本地兜底默认开着）。我第一版只在 miss 分支标 degraded，**漏掉了最常见的那一种**，
   而单测当时是绿的：那些用例手工构造 meta 测的是**指标计算**，没覆盖**发射路径**。
   这个漏网之鱼是靠停容器实跑抓到的；
3. **分母要排除门控跳过的轮次**——闲聊轮会把故障率无声稀释：10 轮闲聊 + 1 轮真故障
   = 9%，刚好躲过 10% 的红线。

实测闭环：停 `aperag-api` → 事件带 `degraded=True, outcome=unavailable` → 看板报
「降级 1 轮 / 降级率 50%」；恢复后 → `backend=aperag, degraded=False`。

同时把 ApeRAG 的 8 个容器 `restart` 从 `no` 改成 `unless-stopped`（与 `ecom-redis`
/ `ecom-pg` 对齐），避免 Docker 重启后整套躺着而买家侧零症状。

### ㉕ 首字时间（TTFT）采集了三个月，从没进过看板

`reply_delta:first` span 早就在记，tracer 里的注释也写清了它就是首字时间。但
`compute_metrics` 从没统计过它——看板上只有 P50/P95 **总延迟**。

这两者不是一回事：总延迟是"整段回复生成完"，首字是"买家多久看到第一个字"。
流式下总时长 12s 但首字 1.5s 是可接受的，首字 12s 则等同于没有回应。
**在线客服的核心 KPI 是后者。**

补上后第一次测量就是一个发现：

| | 实测 |
|---|---|
| 首字 P50 | **8.8 秒**（参考线 1.5s） |
| 首字 P95 | 10.1 秒 |
| 总延迟 P50 | 13.1 秒 |

**首字占了总时长的 67%** —— 买家发出消息后要干等近 9 秒才看到第一个字，流式几乎
没起作用（字是在 ReAct 循环跑完、工具都调完之后才开始吐）。在此之前这件事完全
看不出来：一个 13 秒的"总延迟"很容易被当成"流式嘛，慢慢出字就行"。

**这条只是把问题暴露出来，没有修。** 真修需要动 ReAct 的出话时机（例如先吐一句
确定性的过渡语、或让最后一步生成直接流式），那是独立的一项工作。

### ㉖ 流式在体验上等于没做：短回复一个字都不会流出来

㉕ 把首字时间摆上看板之后，顺着"买家真的看到了什么"往下查，抓 SSE 原始流打时间
戳，撞到一个比"首字慢"严重得多的问题。

先说㉕里被我判断错的一点：**买家不是干等空屏**。progress 事件在第 1 毫秒就到了
（"正在理解您的问题…"），前端有 progress-indicator 在渲染。所以 8.8 秒的体感没有
那个数字听起来那么糟。

真正的问题在别处。同一条流里数 delta：

| 回复长度 | 流式 delta 条数 | 终帧前买家已看到 |
|---|---|---|
| 75 字 | **0 条** | **0%** |
| 211 字 | 12 条 / 97 字 | 46% |
| 189 字 | 10 条 / 75 字 | 40% |

75 字的回复**一条 delta 都发不出去**——买家干等到最后，全文一次性出现。而客服场景
里短回复是多数。

原因在 `IncrementalRedactor`：为了保证"敏感号码跨 chunk 边界被切开也不会提前吐出
去"，它扣住尾部 `holdback` 个字符不发，`holdback = max(所有护栏正则的最长匹配宽
度)`。而最宽的那条是邮箱 `([\w.+-]{1,3})[\w.+-]{0,29}@([\w-]{1,40}\.[\w.-]{1,40})`，
**W = 114**。于是长度不足 114 字的回复永远凑不满一次提交。

这个设计在正确性上是成立的，模块注释里也写明了"生成结束时缓冲区剩下的尾部直接
丢弃，以终帧为准"。**但它给出的是一个与文本内容无关的上界，而内容是能用的信息。**

#### 改法：屏障字符（barrier）

邮箱那条正则只吃 `[\w.+-]` 和 `@`。空格、`*`、`：`、`，`、`（` 这些字符**不可能出
现在它的任何一次匹配里**——而中文客服回复里这类字符每几个字就有一个。既然匹配跨
不过屏障字符，那么"起点在最后一个屏障之前的匹配"必然在那个屏障之前就结束了，其
全部字符都已在缓冲区里 ⇒ 已完全确定，不必再等。

于是每条模式各自算已解决边界，全局取最小值：

    resolved_p = max(最后一个屏障字符的下标 + 1, len(buffer) - W_p)
    resolved   = min(所有 p 的 resolved_p)

"哪些字符不可能出现在匹配里"由 `pattern_width.pattern_alphabet()` 从正则解析树推
导（和最长宽度同一套机制、同一条纪律：算不出来就返回 None，退回死扣 W，绝不猜）。
含 `.`、`[^...]`、`\W` 的模式字母表是全集 ⇒ 无屏障 ⇒ 逐字节保持改造前的行为。

**这是收窄等待，不是放松检测**：正则一个字没改，判定结果不变，只是不再为逻辑上
不可能存在的匹配白等。

改造后同样三个问题实测：

| 回复长度 | 改造前 | 改造后 |
|---|---|---|
| 75 字 | 0 条 / **0%** | 8 条 / **89%** |
| 237 字 | 12 条 / 46% | 24 条 / **97%** |
| 189 字 | 10 条 / 40% | 20 条 / **96%** |

扣留量稳定在 8 个字符（由 `微信.{0,4}(联系|详聊|私聊)` 这条含 `.` 的模式决定）。

#### 怎么证明没放松检测

`tests/test_streaming_redactor_barrier.py`：随机文本 × 随机切分粒度 × 40 组种子，
断言掩码型敏感内容的明文永远不出现在提交给买家的文本里。这条不依赖"我的屏障推理
对不对"——它直接检查结论；屏障要是算错了，被切开的号码就会以明文出现。

写这组测试时我自己错了两次，都值得记下来：

1. 第一版断言"提交内容里不许匹配到任何一条护栏模式"。挂在 `\bQQ\b` 上。查下去发
   现 `ContactInfoGuard` 对关键词类不是掩码，是**删掉引导短语再追加一条平台提醒**，
   裸词 `QQ` 在**全量脱敏后也照样在**——拿这个当判据连权威的那一遍都通不过。
2. 第二版把判据缩到掩码型模式，还是挂：`6222021234567890123` 明文出现了。但随机
   拼接把 `5999.00` 紧贴在卡号前面，凑成 21 位连续数字，而 `(?<!\d)…(?!\d)` 对它
   本来就不匹配——全量脱敏同样原样保留。

两次都是**判据写错了，不是实现漏了**。最终判据是相对的：*凡是全量脱敏会掩掉的，
增量也必须掩掉*。绝对判据会把"护栏本来就不管"误报成"增量漏了"。

对照测试里也犯过一次：我拿一条等宽的 `.{0,N}` 假正则当"旧行为"，但它在缓冲区里
处处命中，反而把边界往前推——对照物本身就不是旧行为。改成直接把各模式的字母表置
空（=算不出字母表的退化路径），那才是改造前逐字节的口径。

### ㉗ 看板上的"首字"报的是引擎首字，买家从没经历过那个时间

这是我在㉕里自己引入的口径错误，㉖查出病根后一并修掉。

`sink()` 喂给 tracer 的是**脱敏前的原始事件**（那行注释当时的理由是"保留真实的首
字时间不失真"）。于是 `reply_delta:first` 记的是引擎吐出第一个 token 的时刻，而买
家要等增量脱敏缓冲放行。㉖之前这个差大到让引擎侧的数字失去意义：75 字的回复引擎
侧首字一秒多，买家侧是"等到最后一次性看到全文"。**看板上摆着一个买家从来没体验过
的数字。**

现在两条都记：

| span | 含义 |
|---|---|
| `reply_delta:first` | 引擎吐出第一个 token |
| `reply_visible:first` | 第一个字**真的进了 SSE 队列**（买家侧） |

看板主指标 `ttft_p50_ms` 取买家侧；引擎侧单独报一份，两者之差另报一个「脱敏缓冲
代价」——**这个差变大意味着有人加了一条更宽的护栏正则，而那件事在别处没有任何信号。**

两处细节：

- 历史 trace（`reply_visible` 上线前落的库）只有引擎侧 span，回退到引擎侧而不是报
  0——否则切到长窗口时看板会凭空多出一段"首字 0 毫秒"的完美假历史，而那正是运维
  判断"最近是不是变慢了"的依据。
- 「代价」必须**按 trace 配对**再取分位，不能拿两个 P50 相减。第一版就是相减，在
  24 小时窗口上得到 0ms（买家侧 5 条样本、引擎侧 30 条，两个总体差一个数量级），
  而真实代价是 182ms。配对样本数一并报出。

改造后实测（近 12 分钟窗口，5 轮）：

| | |
|---|---|
| 买家首字 P50 | 5292 ms |
| 引擎首字 P50 | 5110 ms |
| 脱敏缓冲代价 P50 | **182 ms**（改造前是"整段不可见"） |

顺手修掉一个㉕引入的显示 bug：`lineLabel` 对非 `latency` 前缀的 key 一律按百分比
格式化，所以"首字 P50"的参考线在页面上显示成 `参考 < 150000.0%`。

**仍然没修的**：首字本身还是 5.3 秒（参考线 1.5s）。㉕说的那个结构性原因还在——
查询理解是串行前置的 LLM（约 2.2s），而 ReAct 第一步往往在"决定调哪个工具"、真正
给买家看的字要等工具回来后的第二轮生成。这一项单独开了任务，动的是 Agent 的出话
时机，不该混在可观测性的改动里。

### ㉗ 一个已经修好的工具，连续报警 7 天

走查多智能体协作页时先看到的是症状：**「最近协作链」30 条全是同一条异常**——
`tool_error_rate_high / track-order`，每 100 秒复制一条，真实协作一条都看不到。
诊断里写着失败率 84%。

顺着查下去，先后修正了自己两次判断：

1. 先以为是真 bug（`track-order` 84% 失败）。查 traces.db 的 tool span：`query_order`
   87 次里失败 53 次，全是同一个订单号 `ORD-20240115-001`。再查 orders 表——这单属于
   `小明`，登录用户是 `1`，所以「未找到订单」是**归属隔离在正常工作**（而且刻意不说
   "无权访问"以免泄露存在性）。
2. 再以为是"异常扫描没有时间窗"。读 `service_quality` 才看清它**有** 7 天窗，而且数据
   源不是 traces.db 而是 ecom.db 的 `skill_traces`。

查到真相：

```
track-order  08-04:  36 次  全部 tool_error   ← 一天的旧故障（当时确实有缺陷）
             08-10:   2 次  1 错 1 成
             08-11:   9 次  全部 success      ← 当天 9/9 健康
```

7 天窗把 08-04 那 36 次留在分子里 → 84% → 一个**已经修好**的问题连续报警 7 天。
而这条教训在看板改造时就写下过（`observability/metrics.py` 的 `window_hours`：
"一个已经修好的问题会永远留在看板上"），**当时只落到了看板，没有落到告警侧**。
同一个洞在第二个消费方身上又开了一次。

三个后果都是实测看到的，不是推演：协作链页面被假警报刷满；每条假警报触发一次 LLM
归因、烧 `collab_daily_llm_budget`（归因降级率 25% 大概与此有关）；当天 9/9 健康被
完全淹掉。第四个后果没法测但更贵：运维会学会忽略这个告警。

**改法**：服务健康（工具失败率／转人工率／情绪）走 `anomaly_service_window_days`
（默认 1 天）；经营指标（退款率／差评率）仍走 `window_days`（默认 7 天）。不让经营
指标跟着缩窗是因为它们有天然滞后——下单→收货→退款／评价跨若干天，1 天窗会把它们
统统压成 0；而一个工具是不是坏的，只有"现在"这一个时态。

**缩窗的代价写在返回值里，没有藏**：近窗样本不足的 skill 列进 `service_insufficient`，
让"没报警"和"没数据所以报不了警"成为两件看得见的事。写这段时被自己的测试抓到一个
漏洞——`service_quality` 是 `GROUP BY` 聚合，窗内没有行的 skill 压根不出现，只遍历
近窗会让"坏掉之后再没人调用"这种**最需要说明**的情况恰好隐身；改成拿经营窗的名册
当全集。

**必要的配套（不是顺手补的）**：告警窗收到近 1 天之后，"某个 skill 前几天坏过、今天
已经好了"就只能靠按经营窗统计的分布来看。而那份数据（`quality.skills`）后端一直在
返回，前端只用了同一响应里的 `emotion`，整段丢掉了。补上「服务质量（按 Skill）」表。
没有它，缩窗等于用"少报假警"换"看不见历史"——那不算修好。

同屏两个数字必须能被读懂。真库现在就是这个状态：

| 位置 | 窗口 | 显示 |
| --- | --- | --- |
| 服务质量（按 Skill） | 近 7 天 | track-order 工具失败率 **78.7%** |
| 跨线异常 | 近 1 天 | **当前无跨线异常** |
| 统计口径说明 | —— | 把上面两行为什么不矛盾讲出来 |

两处都标自己的窗口，表脚明说"这里的数字是历史分布，不是告警"。少了这层说明，店主
只会得出一个结论：这看板不准。

顺带补上另一个同类的边界丢弃：`/api/seller/overview` 原来只取 `["anomalies"]`，把
`products_truncated` / `reviews_truncated` / `service_insufficient` 全丢在 API 边界上。
那几个键存在的唯一目的就是"让盲区可见"，在这里被丢掉等于它们从没被写出来过。

**实测验证**：真库扫描从"每 100 秒 1 条假警报"变成 0 条；重启 worker 跑过两个扫描
周期，日志里 `[scan] 异常 0 条,发布 0 条`——扫描真的执行了并判定为 0，不是进程死了
造成的假绿（这一步是刻意查的，"没有新事件"在死进程下同样成立）。

**没修的**：历史那 30 条假警报链仍在库里、仍显示在「最近协作链」——它们确实发生过，
不删数据。另外一个**真的**坏掉的工具仍会每 100 秒报一次（合法但仍是洪水），去重
（`anomaly_dedup_hours`）单独开了任务。

### ㉘ 前端走查里被排除掉的一个"缺陷"

在浏览器里量买家侧时间线，看到"发送后 2.2 秒屏幕上只有自己那句话"，一度当成缺陷：
`orchestrator.py:110` 明明在调 LLM **之前**就发了 `understanding` 进度事件。

拿 Python 探针直连后端 SSE 才排掉：

```
  36ms  headers 200
  44ms  progress understanding     ← 后端 44 毫秒就发了
  45ms  progress retrieving
2726ms  route
4140ms  reply_delta #1
```

后端不慢，那 2.2 秒是 **Vite 开发代理缓冲**出来的，生产态（静态托管 + 直连 API）
不存在。所以没有改任何产品代码。

记这一条是因为它是个方法问题而不是结论问题：浏览器里量到的延迟里混着开发链路的
成本，把它当产品缺陷去"修"会改错东西。要判断一个延迟归谁，得把中间件摘掉再量一次。

### ㉙ 商机优先级打分：滞留时长一直按 0 算

走查后台四条链路时顺出来的。`find_opportunities()` 返回的商机，理由栏写着
「**滞留 0h**」——而那笔订单是 9 天前下的。

SQL 算了 `stale_hours`（`growth.py` 的 `_stale_hours()`，而且它的注释还专门解释了
"必须在 SQL 里算，不能在 Python 里算"的时钟陷阱），构造 item dict 时**漏了这个键**，
`priority.score_opportunity` 取不到就静默 fallback 到 `0.0`。

后果不是"显示不准"：滞留时长占权重 **0.4**，归零后这一类商机等于**只按金额排序**，
而"把拖了一周的大额单排到前面"正是 `priority.py` 存在的全部理由（它的模块 docstring
第一句就是：原本按 `created_at DESC` 取前 N 条，真正该催的老单反而被 LIMIT 切掉了）。

七个 kind 里只有 `stale_pending_order` 漏了，而它恰好是**默认 kind、也是唯一有真实
数据的那个**——所以线上跑起来就是"这个打分从来没生效过"。

能用数字对上账，不靠推断：

| | 计算 | 分数 |
| --- | --- | --- |
| 漏了 `stale_hours` | 0.4×**0** + 0.3×1.0（金额封顶）+ 0.3×0.5（转化先验） | **0.45** ← 实测值 |
| 带上真实 212h | 0.4×**1.0**（封顶）+ 0.3×1.0 + 0.3×0.5 | **0.85** ← 修复后实测值 |

**加了一道 AST 结构守卫覆盖全部七个分支**。理由：漏这个键不会报错、不会异常、不会
有日志，只会让打分静默少掉 40% 的依据——这种"沉默的错"靠人眼保证七处都不漏是不
现实的。守卫用 AST 而不是文本搜索，因为注释里出现 `stale_hours` 这几个字会让文本
匹配假通过，**而假通过的守卫比没有守卫更糟**；并且配了一条自检，验证这道守卫对
"缺键"真的敏感——一道从不失败的守卫和没有守卫是一回事。

### ㉚ 四条后台链路逐条核：0 是不是"正确的 0"

worker 日志里四段全是 0：

```
[scan]      异常 0 条,发布 0 条
[attribute] checked=0 converted=0 no_change=0
[followup]  checked=0 drafted=0 stopped=0 done=0
```

**四个 0 里有一个是 bug，三个是正确的**——不逐条核就分不出来，而这正是"链路跑了"
和"链路有效"的区别：

| 链路 | 结论 | 依据 |
| --- | --- | --- |
| 异常扫描 | 曾经**每 100 秒一条假警报**，见 ㉗ | 已修，真库现在 0 条 |
| 转化归因 | **0 是对的** | 只挑 `sent` 且 `outcome='pending'`；两条已发草稿都已判定完 |
| 商机 | **有 bug**，见 ㉙ | 打分的滞留项恒为 0 |
| 跟进序列 | **0 是对的** | 唯一一条序列 `status='stopped'`（`stop_reason=in_service`） |

顺手确认了归因的幂等**不是靠运气**：`attribute_outreach.py:97` 把事件发布门在
`set_outreach_outcome()` 这个条件更新的返回值上（`if not ...: continue`），数据层又
只更新仍是 `pending` 的行。所以下面那条残留是历史的，不是活的：

**没修的（已单开任务）**：协作页「人工待办」显示 **324**，全是
`result.outreach_no_change`(185) + `result.outreach_converted`(139)，来自**2 条**已发
草稿——重复发布留下的历史残留（跨度 08-05 06:20 ~ 08-09 22:37，之后 worker 又跑了
两天没再新增，确认已修）。问题在于**清不掉**：收件箱只能一条条 ack。运维看到 324
就会学会忽略这个入口，真有一条要处理的也看不见——和告警疲劳是同一个病。另外
`outreach_drafts` 里 7 条 `status='draft'` 的草稿最老的是 08-05，六天没人审。

### ㉛ "回复有点慢"的根因不在模型：fail-soft 只保证不崩，不保证不慢

起因是一句很朴素的抱怨：「感觉回复有点慢，而且每次都要思考吗」。

**先量，不猜。** 直连后端（绕开 Vite 代理）打四种输入，其中一条是决定性的探针：

```
「你好」  总计 12262ms  chunks=0   ← 走规则快路径，零 LLM 调用
「谢谢」  总计 12191ms  chunks=0
```

**一句不调用 LLM 的固定话术要 12.2 秒**——那 12 秒和模型、检索、Agent 全都无关。

顺着查到 `SESSION_STORE_BACKEND=redis`，而：

- `docker ps -a | grep redis` **一个容器都没有**；
- 失败不是 `ConnectionRefused`（那会毫秒级返回），是 `TimeoutError: Timeout reading
  from socket`，**每次整整 10 秒**；
- 监听 6379 的是 `com.docker.backend.exe` + `wslrelay.exe`——**Docker 的端口转发残留**，
  而 Docker Desktop 的 Linux 引擎已经挂了（`_ping` 返回 500）。

所以是最坏的一种故障形态：**转发器接受 TCP 连接却永不应答**。`ConnectionRefused`
会被快速兜住，"接受后沉默"则让每一次操作耗满 socket 超时。

**决定性实验**（只换会话后端，故障不动）：

| 输入 | Redis 后端 | file 后端 |
| --- | --- | --- |
| 好的 | 23006ms | 9095ms |
| 你好（零 LLM） | 12262ms | 2229ms |
| 谢谢（零 LLM） | 12191ms | 2336ms |
| 帮我看下订单发货了吗 | 28815ms | 14193ms |

file 后端下「你好」仍要 2.2 秒——追下去是 `resolve_hmdp_user`（`app/api/app.py`
里**每个 `/api/chat` 请求必经**的一步），它的超时正好配的是 2 秒。

#### 三个产品缺陷（不是环境问题）

环境该修，但这次真正值钱的是环境暴露出来的代码问题：

1. **四个 Redis 客户端里三个没设超时**。`redis.from_url(url)` 不传超时时 redis-py
   默认 `socket_timeout=None` = **无限阻塞**。这四个消费方（会话存储／会话锁／
   幂等／hmdp 身份解析）全在买家回复的热路径上，而"最坏情况无界"在一个有 SLA 的
   在线客服里等于没有 SLA。只有 `hmdp_identity` 设了（2 秒），另外三处是裸的——
   典型的"每处各写一遍，迟早漏一处"。
2. **会话锁完全没有失败冷却**。紧挨着的会话存储早就有 `_down_until` 退避，锁只有
   fail-soft 没有冷却。讽刺的是这个类自己的 docstring 写着「同一次故障里，一半组件
   降级、另一半把服务打死，这不是设计取舍，是漏了一处」——同一句话对**冷却**也成立，
   而漏的正是这一处。
3. **`resolve_hmdp_user` 也没有冷却**，而它比别处更疼：每个请求必经，故障期间每一轮
   对话固定多付一次超时。

一句话概括这三条：**降级路径在正确性上是软的，在延迟上是硬的**。四处都写了
`except Exception` 的 fail-soft，所以功能上完全正常——没报错、没 500、买家照样收到
回复。坏的只有延迟，而延迟没有任何一处出口在管。

#### 改法

新增 `app/session/redis_health.py`，两件事只写一份（四处各写一遍退避，迟早漂移出
三种行为）：`make_client()` 强制设上超时（任何路径都不会落到 `None`），`Breaker`
提供时间戳式退避（与 store.py 既有的 `_down_until` 同语义；那份先写、有回归钉着，
不动它）。会话锁与 hmdp 身份解析补上冷却。

**实测（故障没动，只改代码）**：

| 输入 | 修复前 | 修复后（冷却生效） |
| --- | --- | --- |
| 谢谢（零 LLM） | 12191ms | **37ms** |
| 你好（零 LLM） | 12262ms | **41～51ms** |
| 帮我看下订单发货了吗 | 28815ms | 12355ms（首个事件 7157ms → **41ms**） |

#### 同一个病的第四处：ApeRAG 检索

顺着这条线又抓到一处。ApeRAG 随 Docker 一起挂掉，一句需要知识库的问句在 `recall`
事件上花了 **14.7 秒**——而 `aperag_timeout_s` 配的是 6 秒。差在 httpx 的
`Timeout(6.0)` 是 connect/read/write/pool **各** 6 秒，不是总额。同样没有冷却，
每个需要知识库的轮次都要重付一次。

隔离测量（进程内直调 `aperag_search`，ApeRAG 真的挂着）：

```
第 1 次:  6421ms  返回=None  冷却中=True
第 2 次:     0ms  返回=None  冷却中=True
第 3~5 次:   0ms  返回=None  冷却中=True
```

冷却期内的返回值与真实故障**完全一致**（`None`），所以 kb.py 照常回落本地索引、
照常打 `degraded` 标记进看板的知识库降级率——这一点专门写了测试钉住，否则"少等
十几秒"就变成了"故障被藏起来"。

#### 一个改动过程中被自己抓到的错

Breaker 被 ApeRAG 复用后，实跑日志打出来是：

> ApeRAG 检索 降级：**Redis 不可用**（ReadTimeout）……请尽快恢复 **Redis**

文案把 "Redis" 写死了。运维照这条去重启 Redis，而挂的是 ApeRAG。**一条把人指错
方向的告警比没有告警更糟**，加了 `dependency` 参数与对应测试。

#### 一处**刻意没改**的取舍

给会话锁加冷却打破了一条既有测试 `test_recovery_is_automatic_without_restart`，
它断言"下一次调用立刻重试"，理由是"降级若写进实例状态，恢复后会长期处于看起来
正常、实际没有全局互斥的状态"。

这不是测试过期，是真的张力。分辨点在于：原测试防的是**永久** latch，我引入的是
**有界**窗口；而且冷却只把"没有全局互斥"这个风险从故障期向后延长最多 5 秒——
**故障期间本来就没有全局互斥**（两个实例都在回落进程内锁）。用"恢复后最多 5 秒仍是
弱互斥"换"故障期间每轮对话不再多付一次超时"，在在线客服里划得来，窗口长度还是
配置项。测试改成断言**有界**而不是"立刻"，并把这段取舍连同实测数字写进了测试
docstring——放宽一条断言必须说清是取舍还是迁就。

#### 关于"每次都要思考吗"

这一半不是 bug。`app/agent/chat.py` 有一条明确的设计决定：

> 不放宽到规则表里其它含糊的"闲聊寒暄"匹配（如确认语气词"好的"/"嗯"——这些没有
> 对应的安全文案，不强行套用，继续走生成）

所以「你好」「谢谢」有审过的固定话术（实测 `chunks=0`，零 LLM），而「好的」没有，
每次都过一遍生成。这是刻意的：给「好的」套一句固定话术，在上下文里说错的风险
不小。**没有改。**

#### 全局冷却状态跨测试泄漏（自己踩的）

这几个 Breaker 是**进程级**的，故意如此——要在请求之间记住"这个依赖刚才挂了"。
代价是状态跨测试泄漏：一个模拟故障的测试打开冷却，紧随其后的测试就被**短路**，
连调用都不发生。

实际撞到了：加完 ApeRAG 冷却后，`test_external_kb.py` 里三条本来无关的用例集体报
`KeyError: 'json'`——不是断言错，是那次 HTTP 调用压根没发出去。这种失败长得像
"测试写错了"，很容易被误诊成断言问题然后去改断言。

复位归 `conftest.py` 的 autouse fixture，而不是让每个相关测试各自记得清一遍：
全局状态是这次改动引入的，兜住它的责任也在这里。

### ㉜ 买家看到了内部 JSON：模型在模仿它自己的历史

买家发「知道了」，收到的是：

```
好的，感谢您的理解与支持。如有其他问题，随时欢迎联系我。

{"intent": "acknowledgement", "confidence": 1.0, "reply": "好的，感谢…",
 "requires_human": false, "follow_up_question": null}
```

内部字段（置信度、是否转人工）直接摆到买家眼前，正文还重复了两遍。

**根因不在护栏，也不在解析。** `chat.py` 那句

```python
self.raw_messages.append({"role": "assistant", "content": result.model_dump_json()})
```

把**整个结构化响应的 JSON dump** 写进了对话历史。于是历史里每一轮 assistant 都长成
JSON，模型下一轮**照着历史的格式模仿**——这是 few-shot 污染。实测口径：全部会话
**221 条 assistant 消息里 100 条（45%）是 JSON 信封**，而且是**混着**纯文本的
（快路径／护栏／转人工那几条分支写纯文本），这恰恰是格式模仿最容易出错的情形——
模型两种都见过，于是有时挑错那一种。为什么偏偏在「知道了」这种轮次犯：没有工具调用、
没有强任务信号，模型对格式的依赖最重。

`app/prompts/agents.py` 里那三处「并如实设置 `requires_human=true`」是帮凶。E2 改造
去掉了"第二次 LLM 调用解析结构化字段"之后，模型**已经没有结构化输出通道**，这条指令
它无法执行，而它唯一想得到的执行方式就是把整个 JSON 吐进正文。同一个文件第 27 行还
写着「不要点出内部字段名（如 intent、confidence、requires_human）」——两条指令自相
矛盾。已删掉这三处，改成说明"这句兜底话术本身就是转人工信号，服务端据此判定"。

#### 为什么修在送模型的边界上，而不是改持久化格式

那个 JSON 是**承重**的，四个消费方在 `json.loads` 它：`api/history.py`（前端历史
回显）、`skills/golden_corpus.py`、`skills/user_modeling.py`、
`evaluation/trace_to_case.py`。把持久化改成纯文本会同时打断这四处，而且是**静默**
失效（解析不出来就当没有元数据）。

而 `history_utils.py` 的既定职责正好是"作用在送模型的消息副本上，不改持久化的
raw_messages"——现成的接缝。新增 `unwrap_assistant_envelope()` 挂在 `_build_messages`
的出口：落库的还是信封，**模型只看得到买家看到的那句话**。保守到只在 content 能解析
成 dict 且 `reply` 是字符串时替换；带 tool_calls 的消息、纯文本、畸形内容一律原样
保留——宁可漏解包一条（退回改造前的行为），也不能把一条正常消息弄坏。

测试有两半，第二半是**反向**断言：`test_persisted_history_still_carries_the_envelope`
用 AST 确认 `model_dump_json` 还在，防止将来有人"顺手"把持久化也改成纯文本。

**验证**：复现原场景（先积累几轮历史再打那句应答语），五轮全部干净。

#### 顺带抓到第二个缺陷：检测器响了，但结论被观测边界扔了

排查时先查 trace，**搜不到任何 `internal_leak` 记录**，一度以为检测器没工作。实际是
`app/observability/tracer.py` 的 guard 分支只读 `event.get("guard")`，而
`_check_internal_leak` 发的是 `{"type":"guard","kind":"internal_leak","hits":[...]}`
——键名对不上，于是落成：

```
08-11 22:39:21  name=guard:None  meta={"stage": null, "action": null, "reason": null}
08-11 22:32:27  name=guard:None  meta={"stage": null, "action": null, "reason": null}
```

时间戳正是那两次泄漏。**检测器完全正常命中了，`hits` 整个被丢掉**，只留下一条无名
无内容的空 span。11 条 guard span 里有 2 条是这样的。

这与 `/api/seller/overview` 曾经只取 `["anomalies"]`（见 ㉗）是**同一类错**：
信号在边界上被丢掉，等于它从没产生过。而且这一次更隐蔽——它让人得出"我们没有检测
能力"的结论，从而去建一个已经存在的东西。

修法：名字取 `guard` 或 `kind`，`hits` 落进 meta，两种键都没有时给 `unknown`
而不是字符串 `"None"`（那种名字既搜不到、也说不出发生了什么）。护栏流水线那一路
行为逐字不变，测试钉住了"不该凭空多出一个 hits 键"。

#### 一条仍然成立的设计取舍

`jargon_guard` 的定位是「旁路埋点，只做**看见**，不阻断、不改写」。这次没有改这一点：
拦截或改写出话是另一层决策（改写可能把一句本来正确的回复弄坏），而现在真正的问题
——历史污染——已经从源头解决了。检测器的价值在于"下次再犯能立刻知道"，前提是它的
结论别再被扔掉，那部分已经修好。

### ㉝ 走查完整协作链：链路全通，但产出的内容是错的

按「异常 → 归因 → 起草 → 人工审批」造条件实跑了一遍。**先说结论:链路本身没问题**
——造出 `HMDP-1`(Nike Air Max 270)下单 5 笔退款 1 笔、退款率 20% 跨过 15% 告警线,
踢一次扫描:

```
signal.anomaly      客服 → 参谋   [done]     23:26:01
insight.diagnosis   参谋 → 营销   [done]     23:26:08   ← 归因未降级，唤醒营销
action.drafts_ready 营销 → 人工   [pending]  23:26:11   ← 停在人工闸，符合设计
```

三跳、10 秒,路由表每一跳都对，参谋的归因也是对的（"实际尺码偏大，主因『尺码不准，
偏大一码』"）。**问题全在产出的草稿上。**

#### 缺陷：草稿引用了与它无关的诊断

```
#43 → acc_buyer / ACC-P1（另一个商品）
      正文:「它实际尺码偏大，不少买家反馈建议选小一码哦～」
#44 → acc_buyer / ACC-UNPAID（另一张订单，正文是催发货）
      依据:「该款运动鞋实际尺码偏大…建议在详情页增加提示」
```

两条是**两种不同性质**的错：

- **#43 把 A 商品的结论当成 B 商品的事实说给买家听了。** 这是对客的事实性错误——
  ACC-P1 从来没有"尺码偏大"这个结论，诊断讲的是 HMDP-1。
- **#44 让人工审批看到一条与草稿内容毫不相干的依据。** 店主正是靠那一栏决定批不批，
  依据文不对题等于把审批变成盲签。

根因在 `collab.py::handle_insight`。它的注释自己写着「**本处理器不按诊断对象取商机**
——它每次都重新查同一份全局商机集合」，然后把诊断**无条件**喂给 `_llm_draft`、
无条件当成 `reason`。**去重闸管住了数量，没有任何东西管相关性。**

值得一提的是 `routing.py:204` 已经注意到「`insight.diagnosis` 的 payload 里 subject
是**商品**」——但没人把这一点接到"那么草稿也必须是关于这个商品的"。

#### 改法

能走到营销侧的诊断只有 `refund_rate_high` 一种（`_MARKETING_WORTHY_KINDS`），而它的
`subject` 恒为一个具体 SKU。所以规则很干净：**草稿只有在涉及那个 SKU 时才能引用这条
诊断**；不涉及时起草不带诊断上下文、`reason` 换成商机自身的依据。

前提是商机得知道自己涉及哪些 SKU——而它们**没带**。SQL 里 `LEFT JOIN order_items`
早就在，只是没把 `sku` 取出来，与 ㉙ 的 `stale_hours` 是**同一个错法**（算了但没传
下去）。补上 `skus` 字段。

`skus` 为空时判**不适用**：空表示"不知道涉及哪些 SKU"，而"不知道"不能当"是"用。
宁可少引用一条诊断（草稿退化成只按商机情境写，仍然正确），也不能对买家说一件关于
别的商品的事。

#### 验证（两个方向都测，缺一个都不算修好）

重新触发同一条链：

| 草稿 | 涉及 SKU | 依据 | 引用诊断 |
| --- | --- | --- | --- |
| #49 acc_buyer / abandoned_cart | ACC-P1 | 加购未下单 · 滞留 169h · ¥798 | 否 ✓ |
| #50 acc_buyer / stale_pending | — | 下单后久未推进 · 滞留 145h · ¥399 | 否 ✓ |
| #51 walkthrough_buyer | **HMDP-1** | 该款运动鞋实际尺码偏大…（诊断原文） | **是** ✓ |

反向那一半是必须测的：**闸如果把所有诊断都挡掉，草稿照样产出、只是永远不引用诊断
——那是静默回归**，单看"没有错误草稿"是发现不了的。#51 证明它没有过度拦截。

顺带确认 ㉙ 的修复也在真实链路里生效了：依据栏里是 169h/145h，不再是"滞留 0h"。

#### 排查中的一个自己踩的坑

第一次验证时草稿**没有变化**，一度以为修复无效。原因是**常驻 worker 进程加载的是旧
代码**——它在改动之前就起来了。改 worker 侧的逻辑后必须重启 worker，否则验证出来的
是旧行为。这条写下来是因为它会让人误判"修复不生效"，从而去改本来正确的代码。

### ㉞ 更大的一个：买家的交易和经营的分析读的是两个库

走查时为了造条件下单，才发现这条。

`POST /api/order` 的路由是：**买家有 hmdp token → 订单建到 hmdp；没有才落 agent
订单库**。而 `shop_overview` / `product_diagnostics` / `anomaly_scan` / `find_opportunities`
**全部只读 agent 订单库**，两库之间**没有任何同步**（`create_order` 在 app 里只有
else 分支那一处调用）。

实测数字：

| | 数量 |
| --- | --- |
| 买家侧（hmdp）实际订单 | **12 笔** |
| agent 订单库里 user=1 的订单 | **2 笔** |
| 经营总览（近 7 天，读 agent 库） | 订单 2 笔 / GMV ¥798 / 退款率 0% |

**经营侧看到的是买家真实行为的 1/6。** 而异常扫描——整条协作链的入口——读的正是这份
残缺数据，所以**真实买家行为无法触发协作链**（这也是为什么 ㉝ 那次走查必须绕过
`/api/order`、直接写 agent 库才造得出条件）。

后果不止是"数字偏小"。参谋 Agent 据此产出过一条诊断：

> 近 7 天仅 2 笔订单但产生 119 次客服对话，对话量远超订单量，导致服务升级异常触发

这个结论**完全是数据源分裂的产物**，不是经营事实——但它以正常诊断的形式进了协作链，
也会进店主的看板。

#### 这次只做了一半

真正的修法（镜像写入 / 改读 hmdp / 统一视图）是一次**数据架构决策**：它决定事实源在
哪一边，还牵涉退款与发货状态的持续同步（一次性镜像会在状态上漂移，那比不镜像更糟——
看起来完整，实际不是）。这不该在一次走查里顺手定下来，已单开任务。

在那之前做了能立刻消除误导的部分：把口径**写进 `shop_overview` 的返回值**
（`data_scope`），而不是只写在 docstring 或前端。理由是参谋 Agent 只看得到工具返回的
JSON——口径不在里面，它就无从得知自己在看一份残缺数据。前端同一句话显示在关键指标
下方。

那句话刻意**不带 markdown**：同一个串两个消费方，`**` 对模型没有帮助（它不靠星号
理解轻重），在控制台上却会原样显示成星号。实测第一版就是这样露出来的。

### ㉟ 走查协作链后半段:审批→发出→归因回写

补上 ㉝ 没走的那一半。**结论:闭环是通的**,而且中间那道仲裁闸表现很好。

第一次批准 #40 被拦下:

> 该买家有未结的人工工单（正在等处理），此时发营销消息不合适，已拒绝发送。
> `block_code: open_handoff`

**这是正确设计**——买家正在等人工时不该收营销消息,而且理由具体、带机器可读的
`block_code`。换一个没有未结工单的买家批准 #37:`{"success": true, "sent": true}`,
随后 `result.outreach_sent  人工 → 参谋  [done]  00:03:05`,回写闭合。

#### 缺陷一:不可达的买家,批完才知道

第一次批准 `walkthrough_buyer` 的草稿(那个买家是走查时直接写库造的,从没聊过天):

    {"success": false, "sent": false, "reason": "投递失败,已退回待审,可重试"}

**重试永远失败。** 投递通道是"把消息追加进买家自己的客服会话"
(`_deliver_outreach`),没有会话就没有可追加的地方,再点一次结果一样。而
`_deliver_outreach` 把这种**永久性**失败与"抢不到锁"、"落盘失败"塌成同一个
`delivered=False`。

耐人寻味的是 `_revert_after_failure` **本来就有** `retryable` 参数,docstring 也写着
"不能不管三七二十一都说可重试"——发券失败那两种情形正确地用了 `retryable=False`,
只有投递这一路被硬编码成 True,**这一种情形从那条已经写好的纪律里漏了出去**。

改法两半:

1. `_deliver_outreach` 返回 `reason` + `retryable`,端点照它走(裸 bool 与不带新键的
   字典仍按"可重试"处理——那是可替换注入点的历史签名,语义必须逐字节不变);
2. **批准之前**就在草稿卡上标出来。与"这条草稿会真的发一张券"是同一条原则(见
   `growth_drafts` 端点里 `coupon_discount` 那段注释:把批准之后会发生什么在按钮
   按下之前摆出来)。

**只标注不过滤**:买家没有客服会话不等于这条商机不成立(店铺可能有别的触达渠道,
买家也可能明天就来咨询),悄悄丢掉是另一种错,而且更难发现。

真实数据量出了这个缺陷的代价:**9 条待审草稿里 4 条(44%)结构上不可投递**——人工
审批队列有将近一半注定失败。

#### 缺陷二:归因判不出来,却被记成"触达失败"

看 #37 时注意到 `status_at_send`(归因基线)是空的。全部 4 条已发送草稿里 **3 条**
如此——它们关联的 DEMO-006/008/010 在 orders 表里不存在。而 `_progressed("", x)`
因为空串不在 `STATUS_ORDER` 里恒返回 False,于是这些草稿**无论买家做什么都会被判
`no_change`**。

`no_change` 不是中性值:`priority.conversion_rates` 把
`outcome IN ('converted','no_change')` 当分母,所以一条**无法判断**的触达被当成一次
**失败**的触达,永久拉低该商机类型的历史转化率——而那个转化率占商机打分权重 0.3。

判不出来却记成失败,是这个代码库反复出现的同一类错(参见 ㉗ 的
`service_insufficient`、`service_quality` 的 `other` 桶)。加第三档
`unattributable`,并且**必须计数报出来**:不进分母又不计数,等于这些草稿从所有统计里
消失了——那与记成失败是两种相反的错,都不可接受。

改动出乎意料地小,因为既有代码写得够防御:`conversion_rates` 的 WHERE 本来就是
**白名单**,新增取值自动被排除在分母之外,**那个函数一个字都没改**。

区分要够细,别把"确定没往前走"也吞掉:退款这类侧向变化仍是 `no_change`,只有
"订单查不到了"和"基线为空"才是 `unattributable`。

真库验证:把两条空基线草稿的 `sent_at` 回溯进归因窗口,跑一次——
`checked=2 converted=0 no_change=0 unattributable=2`,worker 日志逐条给出原因。

#### 还没走的

Skill 自进化、知识库上传、转人工→工作台、buyer_hints 跨 Agent 回流这四块这一轮
仍然没走。写在这里而不是含糊过去:走查覆盖率本身是要如实报的东西。

### ㊱ 走完剩下四块:三个新缺陷,而且是同一个模式的第三、四、五次

#### 缺陷一:跨 Agent 经验回流对每一个商品都永不生效

`buyer_hints` 的商品级提示只在"买家正在咨询该商品"时注入,匹配 `subject == current_item_id`。
而同一件商品在这个库里有**两种写法**:

    order_items.sku      'HMDP-1'（诊断 subject 的来源）
    carts.sku            '1'（弃单商机 sku 的来源）
    前端传的 current_item_id  '1'
    products.product_id  没有 'HMDP-1'，也没有 '1'

`HMDP-{id}` 是 `POST /api/order` 为 hmdp 渠道商品**造**的本地 sku,而购物车那条路直接
把裸 `item_id` 当 sku 存。裸字符串比较 `'HMDP-1' != '1'` 恒成立,所以:

- **整个"跨 Agent 经验回流"的商品级通路是断的**,而且不报错、不留日志,只是永远没有
  提示。实测 `render_buyer_hints(entries, "1")` 返回空串。
- ㉝ 那道诊断相关性闸对**弃单商机永远判不适用**——闸看起来在,实际全挡掉了。

还有一处**潜在**的(当前数据没触发,SQL 层面可证):`abandoned_cart` 用
`LEFT JOIN products ON p.product_id = c.sku` 取单价,而 `products` 里没有 `'1'`
(实测 0 行)。而 growth.py 那段注释恰好写着"之前没取,导致弃单商机一律按金额未知走
中性值…是白丢的信息"——取是取了,join 键对不上,所以那个修复对 hmdp 商品仍未生效。

修法:新增 `app/agent/tools/product_ref.py`,把归一放在**一处具名**。只做比较侧归一,
不动存储(统一存储要改写路径 + 迁移既有行,而所有已确证的失效都发生在比较那一刻)。
只剥 `HMDP-` 这一个前缀,不做模糊匹配——**过度归一比不归一更糟**:把两个不同商品判成
同一个,会让客服带着 A 的注意事项回答 B。

#### 缺陷二:提示太笼统,客服编了个方向相反的结论

修好注入之后端到端一问,发现更严重的问题。诊断说这款鞋"尺码偏大,买家因『尺码不准、
偏大一码』退货",注入的提示是"退换反馈偏多…不要夸大",客服的回答是:

> 该款为**标准版型**，多数顾客反馈「尺码标准，按日常脚长选即可」；
> 您平时穿42，建议继续选择 **42码**，无需刻意选大或选小。

**三句全是编的**,而且方向是反的:

| | 真实数据 | 客服说的 |
| --- | --- | --- |
| 商品描述 | 「经典气垫缓震，透气网面鞋身」——没有任何版型信息 | 「该款为标准版型」 |
| 评价表 | 这款一条都没有 | 「多数顾客反馈尺码标准」 |
| 退款原因 | 「尺码不准，**偏大一码**」 | 「无需刻意选大或选小」 |

顾客照这个建议下单就会收到偏大的鞋再退回来——**正是这条诊断在说的那种退货**。

修法两层。第一层:**给模型一个真实的类别,它就不需要自己造一个**。按固定关键词表把
退换原因归到类别(size/quality/mismatch/logistics),用 `(kind, category)` 级的提示:
"该商品近期退换反馈集中在尺码。回答尺码问题时**不得断言版型标准、也不得编造顾客
反馈**…"。类别仍从固定词表选出,不含数字、不含指标名、不含 LLM 内容——本模块"泄露
结构上不可能"的前提没有被破坏(有测试钉住)。认不出类别就退回按 kind 的笼统提示,
不硬塞——猜错类别比笼统更糟。

第二层:`SAFETY_RULES` 加硬规则禁止"多数顾客反馈…"这类聚合评价与担保性商品结论。
它只是第二层,因为这个项目自己验证过 **prompt 禁令保得住动作、保不住话术**。

改完重问同一个问题:「详情页未标注具体版型或尺码偏差说明。但根据近期多笔订单反馈,
该款存在**尺码偏大**的情况…若脚长≤26cm,选41码更稳妥」——方向对了。

#### 缺陷三:回复里许了钱,而这一轮没有政策依据

上面那条改完的回复里冒出**新问题**:「支持7天无理由，**平台承担换货运费**」。而平台
真实政策是"若已签收且属七天无理由退货,**运费由您承担**(约12元起)"——方向相反的
对客金钱承诺。

三道既有防线都没挡住,原因值得逐条记:

1. prompt 里"涉及费用必须先检索知识库"只在模型**自认为在讲政策**时才起作用,而这句
   是回答尺码时顺口带出来的;
2. `COMMITMENT_KEYWORDS` 这份词表**存在**,但只用在 skill 风险分级 / 触达草稿 / 评价
   关键词三处——**买家回复这条路上一个金钱承诺检查都没有**;
3. 即便用上,朴素子串匹配也漏:词表里是 `承担运费`,回复写的是"承担**换货**运费"。

第 3 点最值得记。`growth.py` 解释过为什么当时能接受朴素匹配——"这个残余漏洞是可接受
的,因为**每条草稿都必须经人工审批才会发出**"。**这个理由在买家回复上不成立**:那条路
没有人工闸。把一个缓解措施连同它的前提一起搬到别处,是这类问题的常见成因。

新增 `app/agent/commitment_guard.py`:**只检测,不阻断、不改写**(与 jargon_guard 同
姿态——改写一句已生成的回复很容易把它弄坏,拦掉整条则买家什么都收不到)。判定用
**两个信号的合取**:说了钱 **且** 这一轮没有平台知识依据。只看第一个会把"检索到政策后
如实转述运费规则"这种正确行为也标出来,而噪音会让检测很快被忽略。

正则被自己的测试抓了一次:第一版只覆盖"动作在前"(平台承担运费),漏了"费用在前"
(运费由平台承担)。而这两种语序必须都覆盖、又必须区分主语——"运费由**您**承担"是如实
转述政策,"运费由**平台**承担"是承诺,两句结构几乎一样,差别只在主语。

#### 缺陷四:转人工快匹配漏一个词 = 多一次编造承诺的机会

发「我要找人工客服」没有命中 `match_human_fast`,于是绕过了 `_human_request_flow`
那句**审过的固定话术**("好的,正在为您转接人工客服,请稍候~ …"),落到模型生成:

> 好的，我这就为您转接人工客服。请稍候，**系统将在30秒内为您接入**专属服务人员。

凭空许了一个 SLA,而 hitl 库里当时积压着 **42 条**待接管。

尤其刺眼的是 `转接人工`(4 个字)之前也漏——**那正是系统自己那句固定话术里的用词**,
买家照着系统的说法讲反而匹配不上。

扩词时纪律不变(整句锚定 + ≤10 字上限),所以"人工审核要多久""人工客服几点上班"这类
正常问句仍然不会命中——14 种请求说法全命中、6 种正常问句全不误伤,都有测试。

长句(带上下文的"这个问题你解决不了,我要找人工客服")仍然走正常流程,所以 prompt 侧
补了"不许承诺时效与费用"的硬规则作为第二层。

#### 走查了但没找到缺陷的两块

如实记下来,不为了凑数编问题:

- **Skill 自进化**:4 个上线 / 6 个候选 / 0 灰度,门禁在正常工作——候选
  `return-and-exchange-handling` 被判 `valid=False`,理由具体("引用了未知工具:
  product_diagnostics",一个蒸馏出的 skill 引用了卖家侧工具)。`traces_window` 还自带
  诚实说明:"窗口为所有 skill 共用,高频 skill 可能挤占低频 skill 的样本"。
- **知识库**:10 篇文档全部 `COMPLETE`,向量索引正常。

#### 这一整轮的模式

从 ㉗ 到这里,**同一个错误反复出现了五次**,每次换一个位置:

| | 把什么当成了什么 |
| --- | --- |
| ㉗ | 一周前坏过 → 现在还坏着 |
| ㉟ | 办不到(买家不可达) → 办了但失败了(可重试) |
| ㉟ | 判不出来(归因无基线) → 判出来是坏的(触达失败) |
| ㊱ | 数据里没有(版型信息) → 编一个让顾客放心的 |
| ㊱ | 没有依据(运费政策) → 许一个对客的承诺 |

这个代码库对这类错**已经有成型的处理范式**(`service_insufficient`、`other` 桶、
`degraded` 标记、`retryable` 参数),问题不在缺范式,在于每新增一条路径就容易漏一处
——而漏掉的表现全都是**静默**的:不报错、不留日志,只是悄悄给出一个错的答案。

#### 冒烟复验:三条修复在运行进程里都生效,第三条当场抓到一次真实违规

重启后端后实跑:

| 检查 | 结果 |
| --- | --- |
| 转人工走审过的固定话术 | ✅（修复前是模型编的「30秒内接入」） |
| 回复里含时效承诺 | ❌ 无 |
| 编造版型 / 聚合顾客反馈 | ❌ 无（修复前两样都有） |
| 点出真实的「尺码偏大」 | ✅ |
| 金钱承诺检测 | ✅ 命中 `[('unbacked_commitment', ['承担运费','免费换退'])]` |

**但要说清楚:模型仍然在许那个承诺。** 回复里照样有「平台承担换货运费」——prompt
硬规则那一层没压住它。这再次印证了这个项目自己的结论(见 `shop_profile.py` 的说明):
**prompt 禁令保得住动作、保不住话术**。

所以现在的状态准确说是:**从"没人知道"变成了"看板上有一条 guard span,带着命中的词"**,
而不是"拦住了"。检测器的定位本来就是只看不改(改写一句已生成的回复容易弄坏,拦掉整条
则买家什么都收不到),把它说成"修好了金钱承诺问题"是不诚实的。

真正拦住需要在出话流水线里做**确定性改写或阻断**,涉及改写买家实际收到的字——单开
任务,不在这一轮顺手做。

### ㊲ 走查人工接管:队列单位错了,接管期间的对话丢了

#### 缺陷一:坐席队列的单位是"一次升级判定",不是"一个买家在等"

打开待接管队列:**50 条**。但按会话分组之后——

| | |
| --- | --- |
| 原始升级记录 | **50 条** |
| 实际在等的买家 | **7 位** |
| 其中一个会话独占 | **37 条**（跨度 08-02 ~ 08-12，intent 里 23 条是 return_request） |

后果:

- **队列深度失真 7 倍**,坐席看到 50 以为有 50 个人在等;
- `resolve` 按 handoff_id 逐条,**要点 37 次才能清掉一个买家**;
- 处理完一条同一个买家立刻又冒出来,看起来永远处理不完。

这与"324 条陈旧人工待办""30 条相同的假警报"是同一类:**计数单位错了 → 队列失去意义
→ 告警疲劳**。而 `SeatView` 的标题写的本来就是「**待接管会话**」——界面自己说的单位
就是会话。

改法:新增 `list_pending_sessions()` / `resolve_session()`,**升级记录逐条保留不动**
(那是审计轨迹,每次升级确实发生过),只改坐席从哪个视图工作。`/api/handoffs` 原样保留
为审计视图,新增 `/api/handoffs/sessions` 给工作台。

三个细节都不是随手定的:

- **排队看最早那次升级,不是最近一次**。用最近一次会让"等了 10 天、刚又问一句"的买家
  排到最后——而他恰恰最该先处理。
- **`escalations` 要显示出来**。反复升级本身就是优先级信号,聚合掉就不见了。
- **两个数分开报**:`waiting_buyers`(排班依据)与 `escalations_total`(质量信号)。
  混成一个数正是这次要修的那个错。

真库验证:**50 条 → 7 位买家在等**,等最久的 `vip1`(等自 07-20)排最前,
`c-291e78d3448d422d` 带着「升级 37 次」的标记。

#### 缺陷二:接管期间买家说的话不进历史

走完整闭环——AI 正常回 → 坐席切人工 → 买家再发一句 → Agent 正确停口 → 坐席人工回复
→ 切回自动。**功能全对**,但事后看买家历史:

    user       你好
    assistant  您好，我是并夕夕智能客服小夕…
    assistant  您好，我是人工客服小李，已接手您的问题。     ← 坐席那句在
    user       好的谢谢
    assistant  不客气～…

**接管期间买家说的「那我的订单呢」和那句 gate 回复都不在。**

对比很清楚:隔壁那道快路径门的注释明写着——"仍把这轮问答写进会话历史并落盘,
**保证刷新/切换后可回显**(不因走快路径而丢失)",而且它确实 append + save 了。
**只有接管这条路漏了。同一条纪律,隔壁做了,这条没做。**

后果按疼的程度排:

1. **坐席在工作台打开会话,看不到买家在等待期间说了什么**——而接管正是为了处理买家
   在说的事;
2. 买家刷新页面,自己刚说的话不见了;
3. 审计与复盘缺这一段。

改动要小心两点,都写进了代码注释:**这道门刻意跑在 `ensure_active` 之前**(注释解释过:
先换发会让接管被静默绕过),所以这里不能建会话、只能往已有的那个上追加,取不到就跳过
持久化——绝不能因为记历史失败而让接管这道门本身失效;另外与快路径同样先抢会话锁再改
`raw_messages`。

顺带把那句提示提成常量 `MANUAL_TAKEOVER_NOTICE`:它现在有两个用处(回给买家的文本 +
写进历史的那条),两处各写一遍字面量,改文案时漏掉一处,买家看到的和历史里记下的就会
对不上——那种不一致在复盘时最难解释,坐席会以为系统当时说了另一句话。

真库端到端复验,历史现在完整:

    user       我的订单 ORD-123 到哪了        ← 修复前不存在
    assistant  🎧 当前会话已转由人工客服处理…   ← 修复前不存在
    assistant  您好，人工客服已接手。

#### 走查中排除掉的一个"缺陷"

中途 `/api/admin/session/{id}/reply` 报「会话不存在」,一度以为是缺陷。实际是
`/api/chat` 会把客户端传的 `session_id` 规范化成 `c-xxxx`,而我探针用的是自造 id
——工作台拿到的本来就是规范 id,这条路没问题。记下来是因为:**用自造的标识去测一个
带规范化的系统,很容易把自己的测试错误当成产品缺陷。**

#### 顺带修掉一条红测试:它一直在读开发机的真实数据库

跑全量时 `test_chat_switches_profile_and_delegates` 失败,diff 是一段**店名不同**的
prompt(`并夕夕旗舰店` vs `并夕夕`)。

先确认不是自己弄红的:把本轮改动全部 `git stash` 掉,它照样失败——**与这轮工作无关**。

根因是测试没隔离数据库:它读开发机上真实的 `app/sessions/ecom.db`,而那里存着一份
自定义店铺语气(`shop_name='并夕夕旗舰店'`、正式语气、禁语「亲亲」,由某次
`updated_by='cleanup'` 在 08-08 写入)。画像 prompt 在构造时经 `load_profile()` 把
店铺语气渲染进去,于是逐字比较会因为**开发机的数据库内容**而失败。

`tests/test_growth_api.py` 早就为同一个问题写过隔离,注释也在那里——"get_db() 默认
是进程内单例、指向真实的 app/sessions/ecom.db…不隔离的话精确断言会被上一次运行/
别的会话留下的行污染"。这个测试没跟上,补上同一份口径。

一个细节:隔离用 `monkeypatch.setattr(app.db, "_DB", db)` 而不是 `set_db(db)`——
**复位才有保证**。`set_db` 改的是模块全局,测试结束后不会自己还原,会把污染带给同
进程里后面跑的测试文件,而那种污染表现为"另一个文件里的测试莫名其妙地失败",排查
成本极高。

### ㊳ 走查知识库写入侧:链路通,但一句提示会把人指去重启健康的服务

上传一篇内容独特、可验证命中的文档(带随机暗号 `ZQTESTEBC298`),走完 上传 → 索引 →
检索。

**链路本身是通的**:上传 24.4 秒返回,索引异步建完
(`status=COMPLETE`、`vector_index_status=ACTIVE`、`fulltext_index_status=ACTIVE`),
随后检索 `试衣间怎么预约` 命中了它(来源 `试衣间预约规则.md`)。

#### 缺陷:"超时"被当成"连不上",提示指向了错误的动作

上传之后的一段窗口里,`/api/admin/kb/documents` **连续 30 秒超时失败**,界面提示:

> 知识库服务**连不上**，请确认 ApeRAG 已启动

而 ApeRAG **当时是活着的**——同一时段直连它的文档列表接口 **0.5 秒返回 200**。它只是
在忙着建刚上传那篇的索引。

这句提示会**把人指去重启一个健康的服务**,而正确的动作是等几十秒再刷新。根因是
`aperag_writer.list_documents` 用一个 `except Exception` 把超时与连接失败塌成同一个
`None`,调用方无从区分。

改法:新增 `KnowledgeBaseTimeout`,超时抛异常而不是继续返回 None(**做成异常而不是多
一种返回值**——既有调用方全都写着 `if docs is None`,新增一种假值会让它们悄悄错判);
端点接住它给 **503 + "通常是刚上传的文档正在建索引,请稍等几十秒后刷新"**,而不是 502 +
"请确认 ApeRAG 已启动"。真连不上时仍然说"连不上",有测试两个方向都钉。

这是这一整轮同一个模式的又一次:**把"暂时办不到"当成"办不到"**,而且这次给出的提示
直接指向了错误的运维动作。

#### 顺带量到一个硬数据:检索超时配置在生产上必然降级

同一次走查里量到 ApeRAG 检索耗时:

| 查询 | 耗时 |
| --- | --- |
| 试衣间怎么预约 | **4258 ms** |
| 爽约几次会被停权 | **23450 ms** |

而 `settings.aperag_timeout_s = 6.0`。也就是说**第二个问题在当前负载下必然超时降级**
——买家会得到一个没有政策依据的回答,而看板上的知识库降级率会持续偏高。

这一条**没有改**:调大超时会让买家等更久(首字已经 3~6 秒),调小则降级更频繁,真正的
解法是查 ApeRAG 为什么慢(ES/qdrant 负载、embedding 往返、rerank 开销)。那是独立的
一项工作,而且我今天加的冷却已经让降级的**代价**从"每轮重付一次超时"降到了"每 30 秒
一次"——问题本身仍在。

#### 走查中被排除的一个"缺陷"

中途 `/api/admin/kb/documents` 连续 30 秒失败,一度怀疑是刚加的可达性/口径改动引起的。
直接调 `list_documents()` 只要 0.7 秒、返回 10 篇,而同一时刻走 HTTP 端点 30 秒失败
——由此定位到是**上传后的窗口期**,不是代码路径。**同一个函数,进程内直调与经 HTTP
调用给出不同结果时,先怀疑时序而不是代码。**

### ㊴ 走查议价:底价守得住,但谈成的价格不会作用于订单

**这一条是整轮走查里对买家伤害最直接的。**

#### 好的一半:底价是硬边界

四轮压价——「能便宜点吗」→「700 能卖吗」→「老客户了，600，不然去别家」→
「500 最后一次，不同意我就投诉」——**一次都没跌破底价 750**(标价 899)。

原因是 `compute_offer` 是纯函数,带一条显式不变量:

```python
price = round(max(price, F), 2)  # 不变量：永不破底
```

工具层面没有话术能绕过它。13 条测试把这一半钉住了(任意出价、任意轮次、无
floor_price 时按比例推导),防的是后来者"顺手"改坏它。

#### 坏的一半:话术承诺了系统兑现不了的事

第一轮客服自己说:

> 该价格为平台授权的最优让利，**下单时将自动生效**。

而事实是:

- `negotiate_price` 成交时只把价格写进 `bargain_sessions.last_offer`,**不创建订单、
  不设任何价格锁**;
- 下单路径 `POST /api/order` 对议价状态的引用次数是 **0**,它按
  `total = round(p["price"] * qty, 2)`(app.py:521)**直接用商品标价**结算;
- `bargain_sessions` 全仓只被三处读:议价工具自己(算轮次)、`growth.py`(把未成交议价
  当商机)、`session_manager.py`(会话结束时清除)。**没有任何下单/支付路径读它。**

**买家谈到 ¥750 之后直接下单,会被按 ¥899 收钱。**

这比之前抓到的"平台承担换货运费"更硬——那句还只是费用归属,**这句是买家实际付多少**。

#### 这次只把话说实了,没让它生效

两处改动:

1. `_build_confirm_reply` 的 deal_close 分支不再说"已锁定成交价 / 即将为您生成订单",
   改成"已记录…**需客服核价后生效,直接下单会按标价结算**";
2. `negotiate_price` 的返回值加 `price_effect` 字段,明确禁止模型说"自动生效/已锁价"。
   **放进返回值而不是只写 prompt 规则**——这个项目自己验证过 prompt 保得住动作、保不住
   话术,而模型脑补出来的恰恰就是"下单时将自动生效"。

真正让价格生效,难点是**两套商品标识**:议价用本地 `products.product_id`
(`SHOE-270-BK-42`),下单用 hmdp `item_id`(`1`)——与 ㊱ 记的是同一个命名空间问题。
而且订单实际建在 hmdp 侧,hmdp 未必接受外部指定价格。这是一次数据架构改动,单开任务。

留了一条**哨兵测试** `test_order_path_really_ignores_bargain`:它断言下单路径里不出现
`bargain / last_offer / 成交价`。哪天有人真接上了议价价格,这条会失败——**那时应当回来
把成交话术改回"已锁定",而不是删掉断言**。

### ㊵ 商品服务连不上,被说成"商品下架了"

被问"全部体验完了吗"时如实回答"没有",顺手查了一下还没走的商城——**它当时就是坏的**,
而且暴露出一个真缺陷。

hmdp 挂掉的那一刻,两个**相邻**端点对同一个故障给出了两种说法:

    /api/products    → {"products": [], "degraded": true, "reason": "商品服务连不上(ConnectError)"}
    /api/product/1   → {"product": null}                    ← 没有任何降级标记

而 `/api/products` 的 docstring 有一整段专讲这条纪律:

> **降级必须可区分**。改造前失败时 `return {"products": []}`,前端因此无法分辨"这家店
> 真的没有商品"和"商品服务连不上"——页面显示"0 件商品",没有报错、没有日志。
> **买家看到一个空店铺,运维看到一切正常。**

12 行之下的 `/api/product/{item_id}` 却写着"失败/无返回 null",把两件事并列得像是理所
当然。更值得记的是 `_fetch_hmdp_product` 自己的注释——它**早就点明了后果**:

> 返回 None 与"商品不存在"同形,调用方分不出来——所以失败必须留日志,否则一次代理/
> 网络故障会在界面上呈现为"这个商品下架了"。

它选的缓解是"失败必须留日志"。**日志不是给买家的出口**:买家看到的仍然是下架。
**一个缓解措施只有覆盖到受害者能看到的那一层,才算数。**

#### 最疼的一处:点了「立即购买」之后

`create_order` 把同一个 None 翻成 `404 商品不存在或已下架`。**网络抖一下,就告诉一个
正要付钱的买家这件商品没了**——而他不会再回来试。503(暂时不可用、值得重试)与
404(这件商品没了)对应的买家行为完全不同。

#### 改法

新增 `ProductServiceUnavailable`,`_fetch_hmdp_product` 失败时抛它而不是返回 None
(**抛异常而不是多加一种返回值**:三个调用方现在都写着 `if not p`,新增一种假值会被
悄悄当成"不存在"——那正是要修的这个错本身)。三个调用方各自给出正确的说法:

| 调用方 | 故障时 |
| --- | --- |
| `/api/product/{id}` | `product=null, degraded=true, reason=...`(与列表接口同一口径) |
| `POST /api/order` | **503「商品服务暂时不可用，请稍后再试」**,不再是 404「已下架」 |
| `GET /api/cart` | 行保留 + `product_missing`(行为不变)+ 响应级 `degraded` |

购物车那处的注释本来就承认"商品下架、商品服务抖动都可能查不到"并共用一个
`product_missing`——对购物车而言**行为**确实一致(保留行、不显示价格),所以那个字段不
动;但加了响应级 `degraded`,否则买家看到满车"无法定价"会以为自己加的东西全下架了。

前端同步:`getProductDetail` / `getCartPayload` 透出 degraded,购物车页加降级横幅
(与商城页 `shop-degraded` 同一条口径)。老的 `getProduct` / `getCart` 保留为薄封装,
不惊动现有调用点。
