# 二次开发规划：从教学 Demo 到「真实可上线的电商客服系统」

> 设计文档 · 2026-07-19（2026-07-20 升级目标：从"demo 生产化"扩展为"真实可上线可生产使用"）
> 目标岗位：Agent 应用开发（1-3 年经验跳槽）
> 投入预期：约 5-6 周系统打磨
> 路线：**A（产品化）为主 + 吸收 B（评估回归）+ 真实数据层 + Web 客服接入**

## 0. 为什么要做这次二次开发（目标已升级）

当前项目是一个**技术栈非常完整的教学 demo**，已覆盖 Prompt 工程 / 结构化输出 → 多轮对话管理 → ReAct + Function Calling → MCP → RAG → Multi-Agent → Memory → Skill → 评估体系。技术广度足够，但存在三个"简历硬伤"：

1. **形态是 CLI**。真实 Agent 应用都是服务（API + 流式 + 前端）。面试官看到 `python main.py` 输入对话，会默认这是练习作品。
2. **生产篇全没做**。README 自己预告了 Guardrails / Human-in-the-Loop / 可观测性，但一个都没实现。而这三块恰恰是「toy Agent」和「敢上线的 Agent」的分水岭，也是 Agent 岗的**高频面试题**。
3. **数据是 mock**。所有订单/商品/物流都是写死的 dict（`app/agent/tools/mock_data.py`），一眼假。

### 目标升级：从"生产化"到"真实可上线可生产使用"

对标 XianyuAutoAgent 后明确：它的"真"来自**接入真实平台（逆向闲鱼私有协议）**，但那条路对求职者是坑——**违反平台条款、账号封禁风险、合规负资产、性价比极差**。因此本项目**不模仿其平台逆向**，而是用一条更干净、同样"真"的路线达到"可上线可生产使用"：

- **真实数据层**：用 SQLite 建真实的商品/订单/物流/用户库 + 种子数据，把 mock 工具改成查真库（数据真实在库里流动、可被后台改动）。
- **真实合法通道**：以 **Web 聊天组件**为接入形态（可嵌入的在线客服），完全自主可控、零外部依赖、零合规风险。
- **生产级工程**：安全护栏、全链路可观测、人机协作、评估回归、鉴权/限流/成本上限、容器化部署。

即：**「工程真实」而非「平台真实」**——达到和 Xianyu 一样能上线、能用，但没有它的风险，还完整保留本项目的企业级技术栈优势。

### 一句话叙事（简历/面试主线）

> 独立将电商客服 Agent 落地为**真实可上线的在线客服系统**：SQLite 真实数据层 + FastAPI 流式服务 + 可嵌入 Web 客服组件，叠加**安全护栏、全链路可观测性、人机协作**，以**评估回归**守住每次迭代的线上质量，并完成鉴权限流与容器化部署——形成"真实业务数据 → 线上 Trace → 离线评估 → 护栏/转人工兜底"的生产级质量闭环。

## 1. 架构策略：不动核心，只做加法

现有 `EcomAgent`（`app/agent/chat.py`）与 `orchestrator`（`app/multi_agent/orchestrator.py`）是干净、内聚的核心，**本次改造保持其核心逻辑不动**，只在外层包裹新层次。这样做的好处：核心可复用、可回滚、风险可控——本身就是一个能讲的工程决策。

```
┌─ Web 前端（极简流式聊天页 + 可观测性/护栏看板）
│

│
├─ 治理层【本次新增，四大亮点】
```

## 2. 四大亮点模块详细设计

每个模块都对应一道高频 Agent 面试题，设计时优先保证"能讲透原理 + 能现场演示"。

### ① Guardrails 安全护栏

**要解决的面试题**：*"你们的 Agent 怎么防 prompt injection？怎么保证不泄露敏感信息、不胡说八道？"*

- **架构**：可插拔管道。请求进入 Agent 前跑一遍「输入护栏」，回复返回用户前跑一遍「输出护栏」。每个 Guard 实现统一接口 `check(context) -> GuardResult(passed, action, reason)`，action ∈ `{pass, block, sanitize, degrade}`。
- **输入侧护栏**：
  - Prompt Injection / 越狱检测：**双层**——先用规则/关键词/正则做快速筛（如"忽略以上指令""你现在是…"），命中可疑再用轻量 LLM 分类器确认。命中则拦截并返回安全兜底话术。
- **输出侧护栏**：
  - 敏感信息脱敏：正则识别手机号、身份证、银行卡、详细地址等并打码。
  - 幻觉/来源校验：对回答中的事实性断言，校验是否有本次 RAG 检索结果支撑；无支撑的断言标记为"低可信"，可触发转人工（与模块③联动）。
- **可演示性**：看板实时展示"拦截率、拦截类型分布"；面试现场可输入一句注入攻击，展示被拦截。

### ② Observability 可观测性

**要解决的面试题**：*"你怎么知道 Agent 在线上表现好不好？出问题怎么定位？"*

- **数据模型**：一次会话/一轮请求 = 一条 **Trace**；Trace 内含多个 **Span**（每次 LLM 调用、每次工具调用、每道护栏、每次转人工），记录：名称、开始/结束时间、耗时、token（prompt/completion）、成功/失败、错误信息、护栏事件。
- **埋点方式**：用**上下文管理器 / 装饰器**在服务层与工具调用处埋点，**不侵入核心 `chat.py` 逻辑**（呼应"不动核心"原则）。
- **持久化**：SQLite（零运维、可随项目提交、便于演示查询）。
- **看板指标**：P50/P95 延迟、token 成本估算、工具调用成功率、意图分布、错误 Top-N、护栏拦截统计。
- **可演示性**：`dashboard.html` 直接看图表；能点开单条 Trace 看完整 ReAct 调用链。

### ③ Human-in-the-Loop 人机协作

**要解决的面试题**：*"Agent 拿不准 / 越界了怎么办？怎么跟真人客服交接？"*

- **复用现有能力**：结构化输出里已有 `confidence` 与 `requires_human` 字段，本模块把它们真正接上闭环。
- **升级触发器**（任一命中即转人工）：置信度低于阈值 / 输入或输出护栏命中 / 敏感意图（如投诉升级、退款纠纷）/ 连续 N 次工具调用失败。
- **交接上下文包**：生成结构化 handoff bundle = 会话摘要 + 相关长期记忆 + 关键订单/物流信息 + 触发原因，推入人工队列。
- **人工坐席面板**：前端一个简单页面，展示待接管会话队列 + 上下文包，坐席可"接管"。
- **YAGNI 边界**：不做真实坐席实时聊天系统，只做"转人工的判定 + 上下文交接 + 队列可视化"——这已足够讲清设计，避免过度工程。

### ④ Eval 回归（吸收路线 B）

**要解决的面试题**：*"改了 prompt / 加了工具，你怎么保证没把之前 work 的场景改坏？"*

- **升级点**：把现有 `app/evaluation`（当前是"跑一次出报告"）升级为**质量门禁**。
- **回归门禁**：跑黄金测试集 → 与已保存的 baseline 指标对比 → 任一维度掉点超过容差则 `exit 1`。可接入 pre-commit / CI，也可手动 `python -m app.scripts.run_eval --regression`。
- **闭环亮点（本项目灵魂）**：线上 Trace 中**被转人工或被护栏拦截的真实对话**，一键回流（`trace_to_case.py`）成新的评估用例——线上暴露的问题自动沉淀为回归测试，下次迭代不再翻车。

## 3. 数据流：闭环是这个项目的灵魂

```
用户 → 输入护栏 → Agent(ReAct + 工具 + RAG) → 输出护栏 → 用户
         │              │  每一步埋 Span                │
         └──────────────┴──────→ Trace (SQLite) ←───────┘
                                    │
                    低置信 / 护栏命中 → HITL 转人工队列
                                    │
                    问题 Trace ──回流──→ Eval 黄金集 → 回归门禁
```

这个闭环是面试时最出彩的地方：它证明你理解 Agent 不是"写完 prompt 就完事"，而是一个需要**度量、兜底、持续回归**的工程系统。

## 4. 需要提前认清的技术难点（体现"想清楚了"）

1. **流式 + 工具调用 + 结构化提取三者共存**
   现有 `_react_loop` 是非流式的（`chat.completions.create` 一次性返回）。SSE 化后需要：边思考边推 token、工具调用阶段推送"正在查订单…"进度事件、最后补一条结构化元数据事件。这是本项目工程量最集中、也最能讲的部分。
2. **护栏的延迟成本**
   输出侧幻觉校验若也用 LLM，会让每轮延迟翻倍。设计上让轻量规则优先，LLM 校验做成异步 / 抽样 / 仅对高风险意图触发。
3. **可观测性的侵入性**
   必须用装饰器 / 上下文管理器埋点，严禁把埋点逻辑写进核心 `chat.py`——否则破坏"不动核心"原则，也污染可读性。

## 6. 验收与"简历可写"标准

完成后应能做到（每条都是面试可展示的证据；目标是**真实可上线、可用、可测、可部署**）：

- [ ] Agent 查询的订单/商品/物流来自**真实 SQLite 库**（非 mock），且后台改数据后对话结果随之变化
- [ ] 本地/公网启动服务后，浏览器打开 Web 客服组件即可与 Agent 流式对话
- [ ] 现场输入一句 prompt injection，被护栏拦截并给出安全兜底
- [ ] 看板上能看到实时延迟、token、工具成功率、拦截率
- [ ] 触发一次低置信度场景，Agent 自动转人工，坐席面板出现带上下文的待接管会话
- [ ] 未带凭证/超频调用被鉴权与限流拦截（成本兜底生效）
- [ ] 故意改坏一个 prompt，`run_eval --regression` 报错拦截（掉点被发现）
- [ ] 把一条线上问题 Trace 一键回流成评估用例
- [ ] `docker compose up` 一键起服务（容器化部署）
- [ ] README 有架构图 + 每个模块的设计动机 + 一份面试逐字稿

## 7. 已确认决策

### 7.1 首轮决策（2026-07-19 拍板）
1. **四大亮点全做**：Guardrails + Observability + HITL + Eval 回归，一个不砍。
2. **前端形态**：极简流式聊天页 + 可观测性/护栏看板（不做完整客服工作台，精力留给后端 Agent 能力）。
3. 前置提醒：联调需保证 OpenAI API 可达（`OPENAI_BASE_URL` 配好可用的中转/代理），否则模型调不通。

### 7.2 目标升级决策（2026-07-20 拍板，覆盖首轮中"不上线"的定调）
4. **目标升级为"真实可上线可生产使用"**：参考 XianyuAutoAgent，但走"工程真实"而非"平台真实"。
5. **不接入任何第三方电商平台、不做协议逆向**（合规/封号/负资产/性价比差，且非简历主线）。
6. **新增真实数据层（W1.5）**：用 SQLite 建真实商品/订单/物流/用户库 + 种子数据，把 `mock_data.py` 工具改为查真库；提供一个后台改数据的入口。**这是下一步要做的模块。**
7. **接入通道 = Web 聊天组件**：完全自主可控、零外部依赖、零合规风险，接续 W1 的流式聊天页。
8. **新增生产加固（W3.5）**：鉴权 + 限流 + 成本上限 + 规则/LLM 混合路由。
9. **本轮要部署上线**：W4 完成容器化（Docker / docker-compose）并部署，拿到可访问入口。
10. **排期**：升级为约 5-6 周，按第 5 节新表执行。
