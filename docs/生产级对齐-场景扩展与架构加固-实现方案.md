# 生产级对齐:场景扩展 + 架构加固 — 实现方案

> **执行方式**:每个 Phase 可独立用 subagent-driven-development 落地(TDD + 每阶段离线全绿 + 端到端冒烟 + 开关兜底 + 独立提交)。
> **目标**:在不推倒现有架构的前提下,把电商客服 Agent 覆盖到生产级核心场景,并补齐生产要素(handoff / 会话 checkpoint / guardrail 分层 / PII / 成本控制 / 可观测)。
> **路线**(已拍板):加固现有手写编排(不引入 LangGraph 重依赖)+ 电商核心场景全覆盖(不做 SaaS 故障排查 / 预约工单)。

---

## 0. 现状基线(已具备,不重复造)

- **引擎**:单 Agent(EcomAgent)硬化 `_react_loop`(空回复/畸形降级、落盘指针、token 预算、tool_call 自愈);多 Agent 编排复用同一引擎(router→画像)。
- **安全**:consent 授权门(refund/deal_close/cancel_order/change_address)+ 服务端确认重放 + HITL 转人工。
- **数据**:SQLite(orders/products/order_items/shipments/logistics_events/users)+ 长期记忆(按 user_id 隔离)+ RAG 知识库。
- **加固**:限流 / 每日成本预算 / admin 鉴权 / fast-path / 配置热更 / trace 可观测看板 / 评估回归门禁。
- **工具(15)**:query_order/list_user_orders/query_logistics/query_product/negotiate_price/query_coupons/apply_refund/cancel_order/change_address/expedite_shipping/issue_invoice/search_knowledge/recall_user_memory/load_skill/read_tool_result。

## 0.1 目标场景 × 现状缺口

| 场景 | 现状 | 缺口 |
|---|---|---|
| 订单与物流(含催单) | ✅ query_order/logistics/expedite | 发货/送达时间话术、催单闭环(skill) |
| 退换货/退款 | ✅ apply_refund + process-return skill + 政策RAG | **资格判断**(七天无理由/质量问题判定)、**换货**动作 |
| FAQ/政策(RAG) | ✅ search_knowledge | 知识库**内容补全**(运费/保修/会员/发票/七天无理由) |
| 账户/账单 | ❌ 无 | **新子系统**:余额/积分/会员、账单明细、改联系方式(密码走官方渠道) |
| 售前商品咨询/导购 | ✅ query_product/coupons/negotiate + recommend skill | 导购转化话术(skill 增强) |
| agentic 可执行动作 | ✅ 退款/取消/改地址/成交 | **改约配送**、**退订/取消续费**、**换货** |
| — SaaS 故障排查 / 预约工单 | — | **本方案不做**(偏离电商主线) |

# 第一部分:场景扩展(电商核心全覆盖)

## Phase S1 — 知识库补全(FAQ/政策 RAG)  ⭐⭐

**目标**:政策类问题(运费/保修/会员权益/发票规则/七天无理由)能被 RAG 稳定命中并如实作答。

**改动文件**
- 新增 `app/agent/rag/knowledge/` 下文档:`shipping_fee.md`(运费/包邮/偏远地区)、`warranty.md`(保修/质保)、`membership.md`(会员等级与权益)、`invoice.md`(发票规则/类型/时效)、`return_policy.md`(七天无理由/质量问题/不可退品类)。
- 重建索引:`app/scripts/build_kb_index`(或现有 KB 构建入口)。

**关键点**:每篇文档结构化小节(便于分块检索);`search_knowledge` 已返回来源,回复须标注出处;不覆盖的政策要如实说"暂无该政策,转人工"。

**验收**:对 5 类政策问题各问 1-2 句,RAG 命中且回答带出处;全量离线绿(KB 内容不影响离线测试)。**工作量**:~0.5 人日。

## Phase S2 — 账户/账单子系统  ⭐⭐⭐

**目标**:支持"余额/积分/会员等级、账单明细、修改联系方式";密码/登录类**引导官方安全渠道**(不代操作,合规红线)。

**改动文件**
- `app/db/database.py`:users 表补列 `balance REAL, points INTEGER, membership_level TEXT, phone TEXT, email TEXT`(旧库 ALTER 迁移,沿用现有范式);新增 `bills` 表 `(bill_id, user_id, amount, type, status, created_at)`;新增读方法 `get_account(user_id)` / `list_bills(user_id)` / 写方法 `update_contact(user_id, field, value)`。
- 新增 `app/agent/tools/account_ops.py`:
  - `query_account(user_id)` → 余额/积分/会员等级(只读)。
  - `query_bills(user_id)` → 账单明细列表(只读)。
  - `update_contact(user_id, field, value)` → 改手机/邮箱(**risk 动作,接 consent**;`field` 限 phone/email)。
  - `reset_password_guide()` → **不代操作**,返回官方找回密码指引(合规)。
- `app/agent/consent.py`:`RISK_ACTIONS` 增 `update_contact`;`pending._RISK_TOOLS` 同步。
- `registry.py`:注册 4 工具 + schema。
- 种子:`mock_data` 给用户补账户/账单样例。

**验收**:query_account/query_bills 返回正确;update_contact 未授权→need_confirm、授权后落库;问"改密码"→返回官方渠道指引而非代改。**工作量**:~1.5 人日。

## Phase S3 — agentic 动作补全 + 退换资格判断  ⭐⭐⭐

**目标**:补齐电商高频可执行动作,并让退款/退货带**资格判断**。

**改动文件**
- `app/agent/tools/order_ops.py` 增:
  - `reschedule_delivery(order_id, new_date)` → 改约配送日期(仅已发货/待派送;**risk,接 consent**;DB 加 `delivery_date` 列或写 note)。
  - `exchange_item(order_id, reason, new_sku)` → 换货(**risk,接 consent**;创建换货单/改状态)。
  - `unsubscribe(user_id, kind)` → 退订营销/取消自动续费(**risk,接 consent**;`kind` 限 marketing/auto_renew)。
- 新增 `app/agent/tools/eligibility.py`:`check_return_eligibility(order_id)` → 据签收时间 + 品类 + 政策,返回 `{eligible, reason, window_days_left}`(只读,供模型在发起退款前判定)。`apply_refund` 内部也先跑一遍资格,不合格给明确原因而非直接受理。
- consent/pending/registry 同步登记新 risk 动作(reschedule_delivery/exchange_item/unsubscribe)。
- `streaming._build_confirm_reply` 已泛化(用工具真实 message),新动作自动适配。

**验收**:各 risk 动作两轮(need_confirm→确认→执行)e2e 通过;`check_return_eligibility` 对"已过 7 天"/"生鲜不可退"给正确判定;`apply_refund` 对不合格订单拒绝并说明。**工作量**:~2 人日。

## Phase S4 — 路由/画像/技能接入  ⭐⭐

**目标**:新场景接入多 Agent 路由与技能,单/多 Agent 都能用。

**改动文件**
- `app/multi_agent/router.py`:意图集扩为 `presale/postsale/account/complaint`(新增 **account** 画像);`ROUTER_PROMPT` 增账户/账单意图描述。
- `app/multi_agent/agents.py`:新增 `account` 画像(prompt + 工具子集:query_account/query_bills/update_contact/reset_password_guide/search_knowledge/load_skill);postsale 画像并入 reschedule_delivery/exchange_item;presale 并入 unsubscribe(会员续费)。
- `app/prompts/agents.py`:新增 `ACCOUNT_PROMPT`。
- 新增技能 `app/agent/skills/definitions/`:`account-service`(账户账单指引)、`return-eligibility`(退换资格判定流程)、增强 `product-recommend`(导购转化话术)。
- 单 Agent 系统提示词(`customer_service.py`)工具清单同步补全。

**验收**:路由到 account 画像正确;新技能可 load 并按流程执行;全量离线绿 + 端到端冒烟四类意图。**工作量**:~1 人日。

# 第二部分:架构加固(生产要素)

## Phase P1 — Handoff 形式化 + 转人工闭环  ⭐⭐

**目标**:把"换画像"升级为可观测、可跨轮的**显式交接(handoff)**,并让转人工成为一等公民。

**关键点(轻量,不引框架)**
- 已有 per-turn 路由 = 隐式 handoff;形式化为:每轮记录 `handoff{from, to, reason}` 事件(已有 `route` 事件,补 from/reason),写入 trace。
- 支持**同轮内交接**:引擎可调用一个 `transfer_to(profile)` 伪工具表达"这超出我职责,转 X 画像"——编排器捕获后切画像重跑一次(上限 1 次,防抖)。
- 转人工:复用现有 HITL,补充"Agent 主动请求转人工"的动作(low-confidence / 敏感投诉 / 连续失败),并在 trace 标注 handoff-to-human。

**改动文件**:`orchestrator.py`(handoff 事件 + transfer_to 捕获)、`streaming.py`(handoff 事件透传)、`hitl/*`(主动转人工原因)。
**验收**:跨域消息触发一次同轮交接;trace 能看到 from→to→reason;转人工事件带原因。**工作量**:~1.5 人日。

## Phase P2 — 会话 checkpoint(可中断 / 恢复 / 重放)  ⭐⭐⭐

**目标**:解决"服务中途重启则本轮丢失/记忆不巩固"——让**每一步**都可持久化、可恢复。

**关键点**
- 现状:`chat()` 仅在**回合末**落盘;ReAct 循环中途崩溃则本轮 raw_messages 丢失。
- 升级:在 `_execute_tool_call` 之后**增量 checkpoint**(把当前 raw_messages 落盘),回合末再做完整 save;进程重启后从最后 checkpoint 恢复未完成回合(标记 `in_flight`)。
- 借鉴 LangGraph checkpointer 思路,但用现有 `storage.save_session` 轻量实现(加一个 `step_seq` 字段 + `in_flight` 标记)。

**改动文件**:`storage.py`(checkpoint 字段)、`chat.py`(每步 checkpoint + 恢复逻辑)、`session_manager.py`(装载时识别 in_flight)。
**验收**:模拟回合中途 kill,重启后该会话历史/上下文不丢;单测覆盖 checkpoint 写入与恢复。**工作量**:~2 人日。

## Phase P3 — Guardrails 分层 + PII 脱敏  ⭐⭐⭐

**目标**:把护栏理清为**输入门 / 动作门 / 输出门**三层,并补 PII 脱敏(合规红线)。

**关键点**
- 分层:**输入门**(注入/违规拦截,已有)→ **动作门**(consent,已有)→ **输出门**(finalize 变换,已有);本阶段把三者显式命名、可独立开关,并补:
- **PII 脱敏**:新增 `app/guardrails/pii.py`:落盘长期记忆前、写日志前,对手机号/身份证/卡号做 redact(正则);记忆巩固管道接入。
- **记忆注入防御**:长期记忆内容进 prompt 前做一次无害化(防"记忆投毒")。

**改动文件**:`guardrails/pipeline.py`(三层结构 + 开关)、新增 `guardrails/pii.py`、`memory/curation.py` 或 `long_term.py`(写入前脱敏)。
**验收**:含手机号的对话巩固后,记忆文件里手机号被 redact;三层门可独立开关;全量离线绿。**工作量**:~1.5 人日。

## Phase P4 — 成本/预算控制强化 + 分级模型路由  ⭐⭐

**目标**:从"每日请求数上限"升级为**按会话/回合的 token 成本控制** + 简单意图走更便宜模型。

**关键点**
- 现状:CostGuard 只数请求次数;fast-path 规则秒回。
- 升级:trace 已记 token → 汇总**每会话/每日 token 成本**,超阈值降级(转人工/提示);**分级模型路由**:router 判为简单意图(查单/FAQ)可指定便宜模型,复杂/agentic 用主模型(复用 Phase1 的 per-call model 覆盖能力)。

**改动文件**:`hardening/cost_guard.py`(token 维度)、`orchestrator.py`/`router.py`(意图→模型档位)、settings 增模型档位配置。
**验收**:简单意图用便宜模型、agentic 用主模型(trace 可见);会话 token 超限触发降级。**工作量**:~1 人日。

## Phase P5 — 可观测补全  ⭐

**目标**:trace/看板能按**画像 / 工具 / 成本 / 延迟**下钻,支撑运营与调试。

**关键点**:每次 route 记 span(画像、命中意图);每个工具记延迟/成功;每回合记 token 成本;看板加"按画像分布""工具耗时 Top""每会话成本"卡片。

**改动文件**:`observability/*`(span 补字段)、`webui` 看板卡片。
**验收**:看板能看到画像分布、工具耗时、成本;全量离线绿。**工作量**:~1 人日。

# 第三部分:对照生产"四层 + 两总线"补强(2026-07 增补)

> 依据一份生产级参考架构("接入层 / 理解决策层 / 工具执行层 / 数据知识层 + 可观测总线 + 数据总线")做差距分析。
> **我们已领先的点**:写操作闭环(提案→确认→执行)= consent 门 + 服务端重放;超时/重试/熔断/降级 = resilience;双向内容护栏 = guardrails;链路追踪看板 = tracer;线上问题回流 + 评估回归 = reflow/eval。
> 下面只列**此前方案没覆盖、且值得做进本项目**的新点。

## 对照差距表

| 生产架构要素 | 本项目现状 | 处置 |
|---|---|---|
| 接入层:多渠道 + API 网关(OAuth/限流/熔断) | 单 FastAPI + 限流 + admin 鉴权 | 抽象**渠道适配层**(N3);网关/多协议属基建,见附录 |
| NLU:问题改写/指代消解 | 无 | **做**(N2) |
| NLU:情感分析 → 转人工触发 | HITL 有,无情绪触发 | **做**(N1) |
| 对话状态:显式槽位/DST | 隐式在 ReAct | 可选(N4) |
| RAG:混合检索(向量+关键词) | 仅向量 | **做**(S5) |
| 执行层:状态机保障关键流程 | 纯 ReAct | 可选/高阶(N5) |
| 写操作闭环:提案→确认→执行 | ✅ consent + 重放 | 已具备 |
| 数据飞轮:点踩反馈 + 未知问题反哺 KB + 微调 | 有 reflow/eval,缺反馈闭环 | **做反馈+反哺**(F1);微调见附录 |

## Phase N1 — 情感分析 → 转人工触发  ⭐⭐

**目标**:检测强负面情绪(愤怒/辱骂/威胁投诉),作为**主动转人工**信号,先安抚再交接。

**改动文件**:新增 `app/nlu/sentiment.py`(先规则词典 + 可选轻量 LLM 判定,返回 `{label: neutral/negative/angry, score}`);`hitl/manager.py` 的 `evaluate` 增"情绪"触发项;`streaming` 在负面情绪时补安抚话术 + handoff。
**关键点**:规则优先(脏词/连续负面)秒判,模糊的交小模型;避免误判把正常抱怨都转人工(设阈值)。
**验收**:连续辱骂/"投诉你们"→触发转人工并安抚;普通抱怨不误触发;离线单测覆盖规则判定。**工作量**:~1 人日。

## Phase N2 — 问题改写 / 指代消解  ⭐⭐

**目标**:把口语化、依赖上下文的输入还原成完整查询("那个上周买的"→"上周购买的 Nike 运动鞋订单")。

**改动文件**:新增 `app/nlu/rewrite.py`:`rewrite_query(user_input, recent_history) -> str`,一次轻量 LLM 调用把指代/省略补全;在 `chat()` 进 ReAct 前对本轮输入改写(改写结果仅用于工具检索/路由,原文仍展示给用户)。开关 `nlu_rewrite_enabled`,失败降级用原文。
**关键点**:只在有指代/省略迹象时改写(省成本);改写不改变用户可见消息,只喂给引擎。
**验收**:多轮场景"它什么时候到""那个能退吗"能正确关联到上文订单;失败降级不影响主流程;单测用 fake client。**工作量**:~1 人日。

## Phase S5 — 混合检索(向量 + 关键词)  ⭐⭐

**目标**:RAG 从纯向量升级为**向量(模糊语义)+ 关键词(精准命中型号/专有名词)** 混合,提召回准确率。

**改动文件**:`app/agent/rag/*` 检索器:并行跑向量检索与关键词(BM25/字面包含)检索,分数归一化后融合(RRF 或加权),再取 Top-K;`search_knowledge` 复用。开关 `rag_hybrid_enabled`。
**关键点**:关键词检索对"SHOE-270-BK-42""七天无理由"这类精确词特别有效;融合避免单一召回漏检。
**验收**:含精确型号/专有名词的政策问题命中率优于纯向量(用固定问句集对比);全量离线绿。**工作量**:~1 人日。

## Phase F1 — 数据飞轮:反馈 + 未知问题反哺 KB  ⭐⭐

**目标**:让系统"越用越聪明"——补齐**点踩反馈**与**未知问题→知识库**的闭环(你已有 reflow/eval,这是最后一环)。

**改动文件**:
- 前端:每条回复加 👍/👎;`POST /api/feedback{session_id, turn, vote, comment}` 落库。
- `observability`:标记点踩会话;看板"点踩会话"列表(复用 reflow 思路)。
- 新增 `app/scripts/kb_gap.py`:扫描"命中兜底话术/低置信/点踩"的问题,聚类出**知识盲区候选**,导出供运营补充 KB 切片;补充后重建索引即"永久学会"。
**验收**:点踩可记录并在看板可见;kb_gap 能从日志产出盲区候选;补 KB 后同类问题被命中。**工作量**:~1.5 人日。

## Phase N4 / N5(可选·高阶)

- **N4 显式对话状态/槽位(DST)**:为多步业务(退货/换货)维护 `{intent, filled_slots, missing_slots}` 对象,缺参数强制追问。~1 人日。
- **N5 状态机保障关键流程**:对"退货/工单"等关键流程用状态机强制步骤顺序(大模型只提供跳转输入),防止步骤被跳过/错乱。~2 人日。

## 附录:基建级扩展(超出单机 demo,文档说明生产会怎么做)

这些属于分布式/运维基建,单机 demo 不实现,但要能讲清生产做法:

- **多渠道接入 + API 网关**:Web/App/微信/抖音 Webhook/电话 SIP → 渠道适配层归一;网关做 OAuth2、限流熔断、路由(Spring Cloud Gateway/Kong)。**本项目可做轻量版**:抽一个 `ChannelAdapter` 接口(N3),把现有 HTTP/SSE 作为其一种实现。
- **数据总线(消息队列)**:会话结束事件 → Kafka/SQS → 后台 worker 做记忆巩固/画像更新(异步解耦);本项目现为进程内 idle-reaper(思想一致的单机版)。
- **微服务拆分**:gateway / nlu / agent / tool 各独立服务;本项目单体,注明生产会按此拆。
- **弹性伸缩**:K8s 按 QPS/GPU 利用率自动伸缩。
- **数据层**:向量库(Milvus/Qdrant)、知识图谱、Redis 缓存、对象存储归档。
- **可观测标准**:对齐 **OpenTelemetry**(现自研 tracer 可导出 OTLP)。
- **模型微调**:积累数万条优质真人对话后,用于场景微调话术/专业度。

# 第四部分:企业级方案再借鉴(知识工程 + 测试护栏 + 运营)(2026-07 增补)

> 依据 3 份企业级建设方案(瓴羊 Quick Service、大模型客服实战全流程、CRM/工单集成)再借鉴。只列可落地本项目的增量,已有的不重复。

## Quick Wins(当天可做,零风险)

- **降低温度**:客服要确定性,`TEMPERATURE` 从 0.7 → **0.2**(参考普遍建议 0.1–0.3);`max_output_tokens` 保持 500–1000 级、已启用流式。
- **提示词加否定约束**:禁止"我猜/可能/应该是"等不确定措辞 + 低置信统一兜底话术模板(呼应"结果如实汇报")。
- **工作量**:~0.3 人日,立竿见影。

## 知识工程规范(强化 S1/S5)

- **三类知识分层**(瓴羊):公开知识(官网/FAQ)、业务知识(价格/售后政策)、**过程知识(优秀坐席回复)**——分别建索引、查询按意图加权。过程知识最值得做:把标注为"优质"的历史坐席回复入库,让 AI 学金牌话术。
- **加工黄金流程**(实战):清洗 → 切片(**500–800 token,重叠 50–100**)→ 增强(每片生成 **2–3 种问法**做 query 扩展)→ 标注(售后/物流/支付/账号)→ 向量化。
- **知识-行动双向绑定**(瓴羊):KB 切片 metadata 加 `suggest_tools` 字段,检索片段附带**可调用工具/工单模板**(如"物流政策"→带 `query_logistics` + 催单模板),注入 prompt 让模型从"只答"到"答+办"。

## RAG 调优(强化 S5)

在混合检索基础上再加(实战):**Reranker 重排**(Top-K=10 召回 → 交叉编码器重排 → 取 Top-3)、**相似度阈值**(<0.7 视为未命中 → 兜底/转人工,不硬凑)、**HyDE**(复杂问题先生成假设答案再检索)、**对话摘要压缩**(多轮先压缩历史再检索,与 N2 协同)。

## Phase K1 — 知识库健康度检查(新)  ⭐⭐

**目标**:上线前量化 KB 质量,不靠感觉。
**改动**:新增 `app/scripts/kb_health.py`:固定问句集(≥100 条真实问题+标准答案)评估 **召回率(Top-3 含答案)≥90%、精准率(Top-1 直接相关)≥80%、歧义率(矛盾/过时)≤5%**;不达标列出问题切片。
**验收**:三项达标或产出整改清单。~1 人日。

## Phase G1 — 输出接地护栏 grounding(强化 P3)  ⭐⭐⭐

**目标**:输出里涉及**退款金额/时效承诺/订单状态/政策**的断言,必须有**知识来源或工具返回**支撑,否则拒绝生成/降级——把"禁止谎报"系统化。
**改动**:输出门增 `grounding_check`:检测回复含金额/日期/承诺类断言 → 校验本轮是否有对应工具返回/检索来源;无支撑 → 替换为"请稍等,我为您核实/转人工"。
**验收**:诱导"无来源却报退款金额"→被拦截;有来源照常输出。~1 人日。

## Phase A1 — 工具调用审计日志(合规,强化 P3)  ⭐⭐

**目标**:每次工具调用留**可追溯审计**(谁/何时/调了什么/入参出参/成败),满足权限追溯与合规。
**改动**:`tools/manager.execute_tool` 前后写审计表 `tool_audit(id, session_id, user_id, tool, args, result_brief, ok, ts)`;失败/异常自动标记待人工确认;看板加审计查询。
**验收**:每次工具调用可在审计表追溯;异常被标记。~1 人日。

## Phase T1 — 影子模式灰度(新)  ⭐⭐

**目标**:上线前真实流量"影子"验证,不回用户、与人工/基线对比。
**改动**:影子开关:复制入站请求给 Agent 生成回复但**不返回用户**,落库供对比,跑 3–5 天收集失败案例。
**验收**:产出影子对比报告(AI vs 人工/基线)。~1 人日。

## 运营强化(强化 F1)

- **知识热度分析**:标记"高频命中但满意度低"(需重构)、"从未被检索"(冗余可删)的知识。
- **人机评分卡**:每条回复输出**满意度预测 + 置信度**,低置信优先转人工,定期产"人机对比报告"。
- **主动学习闭环**:人工坐席修正过的对话,脱敏后回流为(可选)few-shot/微调语料。

## 两条验收铁律(全局,CRM/工单方案)

1. **一条需系统调用的请求,AI 能否独立完成?**(如"上次报修的空调修好没"→识别意图→查客户→查工单→输出,全程无需人工)。
2. **转人工后,客户是否需要重复描述?**(坐席应直接看到意图+已采集参数+查询结果——本项目 HITL 已传 `recent_context`,**基本达标**)。
每个可执行场景验收都要过这两条。

## 附录补充:集成模式 + 落地三阶段

- **集成模式**:高频简单查询走 **API 直连**;多步骤条件分支走**低代码编排(Flow)**;高吞吐异步走**消息中间件**。本项目 = API 直连 + 手写编排(等价 Flow)。
- **落地三阶段**(瓴羊):① 试点(单一高频低风险,如发票指引,定基线转人工率<30%)→ ② 扩展(售前/工单,人机协同:模型预答+人工确认)→ ③ 全量(全渠道+主动学习+运营团队)。
