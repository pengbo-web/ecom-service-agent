# 生产级智能客服长期记忆 — 架构参考

> 目的:记录"生产可落地"的客服 Agent 长期记忆完整做法,作为本项目(ecom-service-agent)后续改造的参考蓝本。
> 现状对照与改造路线见文末第 10、11 节。

---

## 1. 一句话认知

生产级长期记忆**不是一个文件**,而是一套 **分层存储 + 异步巩固 + 混合召回 + 合规治理** 的子系统。
"能跑的 demo"和"敢上线的系统"的差距,主要就在**身份隔离、异步管道、合规、语义召回**这几处。

---

## 2. 分层记忆模型(先分清"记什么")

工业界/学术界通用的记忆分类,客服场景映射:

| 记忆类型 | 存什么 | 客服例子 | 生命周期 | 典型后端 |
|---|---|---|---|---|
| 工作记忆 (working) | 当前会话上下文 | 这通对话说过的话 | 秒~分钟 | 上下文窗口 / Redis |
| 情景记忆 (episodic) | 过往对话事件 | "上周三投诉过物流延迟" | 数月~数年 | 向量库 + 对象存储 |
| 语义记忆 (semantic) | 提炼出的稳定事实 | "钻石会员、偏好红色运动鞋" | 长期 | 关系库 / CRM |
| 程序记忆 (procedural) | 处理套路/规则 | "该类退款走极速通道" | 长期 | 规则库 / prompt 模板 |

> 本项目当前的 `facts[]`(语义)+ `interaction_summaries[]`(情景摘要)= 这套模型的**单文件简化版**。

## 3. 存储架构(多后端组合,不用扁平 JSON)

```
                 ┌──────────────────────────────────────────┐
                 │            Agent 运行时                    │
                 └───────┬───────────────┬───────────────────┘
       读 结构化档案       │               │   读/写 语义片段
        (权威)            ▼               ▼
        ┌──────────────────────┐   ┌──────────────────────┐
        │ 关系库 / CRM          │   │ 向量库                │
        │ Postgres / Salesforce │   │ pgvector/Milvus/      │
        │ / Zendesk / Intercom  │   │ Pinecone/Weaviate     │
        │ 身份·等级·联系方式    │   │ 过往对话片段 embedding │
        └──────────────────────┘   └──────────────────────┘
        ┌──────────────────────┐   ┌──────────────────────┐
        │ Redis / KV(热状态)  │   │ 对象存储/数仓         │
        │ 会话缓存·限流·锁      │   │ 原始对话全文归档(审计)│
        └──────────────────────┘   └──────────────────────┘
```

各后端职责:

- **关系库 / CRM** — 存**结构化档案**(身份、会员等级、联系方式、标签)。CRM 常是**权威数据源 (system of record)**,Agent 只读或受控回写。
- **向量库** — 存过往对话片段的 embedding,支持**语义召回**("找出该用户历史上所有退货相关对话")。
- **Redis / KV** — 热会话状态、缓存、限流、并发锁。
- **对象存储 / 数仓** — 原始对话全文归档,用于审计、离线分析、训练。

## 4. 数据模型示例

**语义档案(关系库,结构化 + 可查询 + 可审计)**:

```sql
CREATE TABLE user_memory_facts (
    id            BIGSERIAL PRIMARY KEY,
    user_id       TEXT NOT NULL,           -- 认证用户 ID(非会话 ID)
    tenant_id     TEXT NOT NULL,           -- 多租户隔离
    category      TEXT,                    -- identity/preference/behavior/issue
    content       TEXT NOT NULL,
    confidence    REAL DEFAULT 0.8,        -- 置信度(冲突消解/衰减用)
    source        TEXT,                    -- 来源会话/坐席/CRM 同步
    created_at    TIMESTAMPTZ,
    updated_at    TIMESTAMPTZ,
    last_used_at  TIMESTAMPTZ,             -- 召回时刷新,支持"最近使用"衰减
    pii_level     TEXT DEFAULT 'none',     -- none/low/high,决定加密与展示策略
    expires_at    TIMESTAMPTZ              -- 保留期(合规)
);
CREATE INDEX ON user_memory_facts (tenant_id, user_id);
```

**情景片段(向量库)**:每条记录 = `{embedding, user_id, tenant_id, text, summary, session_id, ts, metadata}`。

## 5. 写入路径:异步巩固管道(关键)

**原则:绝不在对话请求线程里同步做 LLM 抽取**——会拖慢响应、失败污染主流程。

```
会话结束 / 空闲超时 事件
        │
        ▼
   消息队列 (Kafka / SQS / Redis Stream)   ← 削峰、解耦、可重试
        │
        ▼
   后台 Consolidation Worker:
     1) LLM 抽取候选事实 + 生成摘要
     2) PII 脱敏(卡号/身份证/手机号 redact)
     3) 去重 + 冲突消解(见下)
     4) 写关系库(档案) + 向量库(片段) + 数仓(原文)
     5) 记录审计日志
```

**冲突消解策略**:
- 同字段矛盾 → 规则"最新覆盖"或按 **置信度** 取舍;
- 高风险字段(如会员等级、账户状态)→ 进**人工复核队列**,不自动改;
- 近义重复 → 合并(可用 LLM 或 embedding 相似度阈值)。

**触发方式**:session-end 显式事件;无结束信号时用**空闲超时**近似(本项目 idle-reaper 即此思想的单机版)。

---

## 6. 读取路径:混合召回 + 预算注入

新对话/新一轮开始时组装记忆上下文:

1. **结构化档案** — 直接查关系库(身份/等级),**权威、必注入**;
2. **语义召回 top-k** — 对当前 query 做 embedding,向量库检索最相关的历史片段;
   - 排序 = **语义相似度 + 关键词命中 + 时间衰减**(hybrid);
3. **最近摘要** — 最近 N 条交互摘要;
4. **token 预算裁剪** — 按预算合并/截断后注入 prompt(本项目 Phase 2 的上下文预算/落盘即此层)。

> 记忆量小时可"全量注入";量一大必须转 **语义 top-k 检索**,否则撑爆上下文且稀释重点。

---

## 7. 生产分水岭:身份与合规(最不能省)

客服记忆涉及真实用户 PII,这几条是"上线红线":

| 关注点 | 做法 |
|---|---|
| **身份解析** | 记忆必须绑定**已认证的正确用户**;绝不能把 A 的记忆泄漏给 B。多租户下再加 `tenant_id` 隔离 |
| **PII 处理** | 存储前脱敏(卡号/证件/手机 redact)、静态加密、必要时字段级加密 |
| **合规 (GDPR/CCPA/个保法)** | 被遗忘权(一键删除某用户全部记忆)、数据保留期 `expires_at`、用户同意、数据驻留 |
| **审计** | 每条记忆可追溯来源/时间/修改历史(可用 DB 审计表或 git 版本化) |
| **访问控制** | 坐席/系统/Agent 分权,记忆读写全程留痕 |
| **安全** | 记忆内容进 prompt 前做注入防御(记忆本身可能被恶意用户"投毒") |

## 8. 质量 / 可观测 / 评估

- **置信度与衰减**:低置信或长期 `last_used_at` 未刷新的事实,降权或淘汰。
- **人工复核**:高风险字段改动进坐席复核。
- **反馈闭环**:坐席可纠正/删除错误记忆,回流为负样本。
- **评估**:定期跑"记忆召回准确率 / 事实正确率"离线评估(呼应本项目的 eval 回归门禁思路)。
- **指标**:巩固延迟、召回命中率、记忆条数/用户、误召回率。

## 9. 现成方案(不必全自研)

- **记忆专用框架**:Mem0、Zep、Letta(原 MemGPT)、LangMem(LangChain)——封装抽取/存储/召回。
- **托管记忆**:Anthropic memory tool / memory stores、OpenAI memory。
- **向量库**:pgvector(最省事,复用 Postgres)、Pinecone、Weaviate、Milvus、Redis。
- **CRM 集成**:Salesforce、Zendesk、Intercom(往往是档案权威源)。

选型建议:中小规模优先 **Postgres + pgvector** 一套搞定(结构化 + 向量同库,少一个组件);超大规模再上专用向量库。

## 10. 对照本项目现状

| 能力 | 本项目现状 | 生产级 | gap 严重度 |
|---|---|---|---|
| 存储 | 单 JSON `app/sessions/memory/default.json` | 关系库 + 向量库 + CRM | 中 |
| **身份隔离** | `user_id` 写死 `default`,所有会话共享 | 认证用户绑定 + 多租户 | **高(最大 gap)** |
| 巩固触发 | 同进程 idle-reaper | 事件 → 队列 → 后台 worker | 中 |
| 冲突消解 | LLM 策展合并/纠正 | 置信度 + 规则 + 人工复核 | 中 |
| 召回 | 全量注入 | 语义 top-k 混合检索 | 记忆多时高 |
| 合规 | 无 | PII 脱敏 + 删除权 + 审计 + 保留期 | **高** |
| 版本/审计 | 无(直接覆盖) | DB 审计表 / git 版本化 | 中 |

## 11. 分阶段改造路线(投入产出排序)

> 面向"本地能跑 + 面试可讲",不盲目上重基建。

**阶段 A — 补最大 gap(小改动、大意义)**
- A1. **真实用户 ID 隔离**:把写死的 `default` 换成会话绑定的认证用户标识,一人一档;接口/前端"记忆"Tab 按用户查。
- A2. **PII 脱敏**:巩固写入前对手机号/卡号/证件做 redact。
- A3. **"删除我的记忆"接口**:`DELETE /api/memory`(合规被遗忘权),前端加按钮。

**阶段 B — 存储升级**
- B1. 长期记忆从 JSON 迁到 **SQLite/Postgres 表**(复用项目已有 SQLite),带 `confidence/created_at/last_used_at/expires_at` 字段。
- B2. 冲突消解加**置信度**,高风险字段(会员等级)改动进复核。

**阶段 C — 语义召回**
- C1. 引入 **pgvector / sqlite-vec**,过往对话片段向量化。
- C2. 读取路径从"全量注入"升级为 **语义 top-k + 时间衰减** 混合检索。

**阶段 D — 异步与治理**
- D1. 巩固改为**队列 + 后台 worker**(先用进程内队列,再上 Redis Stream)。
- D2. 审计日志 + 保留期清理定时任务。

## 12. 面试 Talking Points(30 秒版)

> "客服长期记忆我按**分层**来做:结构化档案进关系库/CRM(权威),过往对话进向量库(语义召回),热状态进 Redis。写入走**异步巩固管道**(会话结束事件→队列→后台 worker 做 LLM 抽取+PII 脱敏+冲突消解),绝不阻塞对话。读取是**混合召回 + token 预算注入**。生产最难的是**身份隔离**(不能串号)和**合规**(PII 脱敏、被遗忘权、审计)。我自己的项目做了单机简化版(JSON + LLM 策展 + 空闲巩固),清楚知道到生产要补身份隔离、向量召回和合规这三块。"
