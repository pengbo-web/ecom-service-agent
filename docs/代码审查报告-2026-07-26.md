## 一、总体结论

项目工程质量高:确认流(consent 前置授权门 + pending 确定性重放 + ownership 归属校验)整体是 **fail-closed** 的正确设计,风险动作(退款/成交/取消/改地址)只走服务端确定性重放,不赌模型重调工具;身份从签名 token 解出、限流按鉴权 user、订单归属校验无视大小写堵他单号——这些防线都对。

本次审查发现 **1 个会导致退款静默不执行的确认流缺陷** 和 **1 个双重退款路径**,均已修复并补回归测试;另修复 3 个防御性/工具性问题和 1 个陈旧测试。其余为已知设计边界(教学演示的鉴权默认值)或需要较大改造的并发加固项,已列出建议,未在本次改动。

**前端验证**:`run_api.py` 启动后,登录 → 路由售前 Agent → `query_product` 工具调用 → 出话评估/重写流水线 → 渲染回复,全链路正常;MCP 常开连接成功(发现 5 个工具);浏览器控制台无报错。

## 二、已修复的问题(含回归测试)

### [P1] 确认绑定的 30 字长度门会误杀"含挂起单号"的正常确认 → 退款静默不执行
- **文件**:`app/agent/consent.py` `confirm_targets_pending`
- **根因**:原逻辑第一步就 `if len(text) > 30: return False`,把长度门放在了"精确单号匹配"之前。而订单号本身占 16 字,叠加确认语极易超 30 字。于是像 `确认 ORD-20240115-001 退款吧,原因是不想要了`(31 字)这类**明确带挂起单号**的确认会被判为"不绑定" → `pending` 置空 → 不走重放 → 用户以为确认了,退款实际没执行(静默失败,最危险)。
- **复现**:确定性复现(无需网络),并由新测试 `tests/test_replay_e2e.py::test_owner` 暴露(该测试原本失败)。
- **修复**:把"提到别的单号→不重放"(错目标防线)和"精确挂起单号匹配→强绑定"两步**提到长度门之前**;长度门只保留给"无单号、仅凭确认词"的弱路径,用于过滤附带闲聊。精确单号是最强、最难伪造的信号(16 位几乎不可能误含),不应被长度门误杀。
- **回归**:`tests/test_consent.py::test_confirm_binding_allows_long_message_with_target_order`,并使 `test_replay_e2e.py` 两例转绿。

### [P1] 取消订单后仍可再次退款 → 双重退款
- **文件**:`app/agent/tools/refund.py`
- **根因**:`cancel_order` 对已付款的 `pending` 订单取消时已承诺"款项原路退回"(状态→`cancelled`);而 `apply_refund` 只拦 `refund_processing`,**不拦 `cancelled`**。两工具用不同工具名、幂等键不同,互不去重。于是"先取消、后退款"同一单会退两次。
- **修复**:`apply_refund` 增加对 `cancelled` 状态的拦截,提示"已取消,款项将原路退回,无需重复申请"。
- **回归**:`tests/test_order_ops.py::test_refund_blocked_after_cancel`。

### [P2] `change_address` 未校验新地址非空 → 收货地址被覆盖成空
- **文件**:`app/agent/tools/order_ops.py`
- **根因**:模型解析失败/误传空串时直接 `set_shipping_address(order_id, "")`,导致无法发货。
- **修复**:确认前增加新地址非空(strip 后)校验。回归:`test_change_address_rejects_empty`。

### [P2] 商品模糊搜索对 name/category 为 NULL 的行会崩溃
- **文件**:`app/agent/tools/product.py` `_searchable_text`
- **根因**:直接索引 `product["name"]/["category"]`,而 DB schema 中 `category` 可为 NULL;遇脏数据行 `" ".join([...None...])` 抛 `TypeError`,整个 `query_product` 对该关键词不可用。当前 mock 种子都填了 category,属潜在崩溃。
- **修复**:统一 `(... or "")` 兜底。

### [工具] 开发环境启动配置指向不存在的 ASGI 对象
- **文件**:`.claude/launch.json`
- **根因**:`ecom-agent` 配置用 `uvicorn app.api.app:app`,但 `app/api/app.py` 只有 `create_app()` 工厂,无模块级 `app`,直接启动会报"attribute app not found"。
- **修复**:改为 `run_api:app`(该模块有 `app = create_app()`)。

### [测试] `test_session_lock::test_chat_returns_busy` 为陈旧测试(非产品 bug)
- **文件**:`tests/test_session_lock.py`
- **根因**:测试用未注册的 `session_id="s1"` 直接请求,`ensure_active` 把未知会话换发成新 ID(响应里 `status:"rotated"` 可证),锁键随之改变,测不到忙路径。忙时提示功能本身正常。
- **修复**:测试先 `create_conversation("default")` 建一个 open 会话再请求,恢复该覆盖。

## 二之补、第二轮修复(原"已报告未改动"项已落地)

以下为第二轮针对第三节所列问题的修复,均补了测试并跑绿(合计 282 项相关用例通过),
并做了并发压测与实机验证。

### API / 会话 / 并发
- **生产 fail-closed(AUTH_SECRET / ADMIN_TOKEN)**:新增 `environment` 配置与
  `verify_production_secrets`。`ENVIRONMENT=production` 且鉴权开着却用默认/空密钥 → **拒绝启动**;
  dev(默认)不校验,教学/本机零配置照跑。`create_app` 启动即调用。
  文件:`app/config/settings.py`、`app/api/app.py`;测试 `tests/test_prod_secrets.py`。
- **管理令牌常量时间比较**:`x_admin_token != token` → `hmac.compare_digest`,消除计时侧信道。
  文件:`app/hardening/auth.py`。
- **限流器 / 成本闸线程安全**:各加 `threading.Lock`,消除线程池并发下 check-then-append 的
  阈值突破/多扣漏扣。文件:`app/hardening/rate_limit.py`、`app/hardening/cost_guard.py`。
- **限流键坍缩**:auth 关闭时改按 `session_id` 限流(原按恒为 "default" 的自报 user_id →
  所有匿名用户共用一个桶)。文件:`app/api/app.py`。
- **快路径锁竞争静默丢历史**:抢不到会话锁时改为返回"处理中"忙提示,不再照发未落盘的回复。
  文件:`app/api/app.py`;测试 `tests/test_fast_path_history.py`(并修复该处依赖会话换发的陈旧断言)。
- **手动 /consolidate 与在途 chat 的锁不一致**:改为与 chat 用同一把会话锁,在锁内快照
  `raw_messages` 再于锁外做慢巩固——既消除边写边读竞态,又不长期持锁阻塞用户(与 reaper 同哲学)。
  文件:`app/api/app.py`。`manager.get_lock` 在生产已无调用方(仅测试),`SessionManager._locks` 不再增长。

### 记忆 / 召回
- **LTM `facts` 并发读写**:`LongTermMemory` 增可重入锁,串行化 `add_facts/_merge_facts/save/load/reset/
  build_prompt_section`,并在遍历前快照,彻底消除 "list changed size during iteration" 与事实丢失。
  2 秒并发压测(写+存+双读)0 报错。文件:`app/agent/memory/long_term.py`。
- **原子写固定 tmp 名 → 并发损坏清零**:tmp 名加 `pid+uuid` 唯一后缀,`os.replace` 原子替换,
  末尾清理残留。文件:`app/agent/memory/long_term.py`。
- **FTS 每实例独立连接**:改为进程级 `get_fts_store(db_path)` 共享单例(单连接+单锁),并加
  `PRAGMA busy_timeout=5000` 兜底,消除跨实例并发写的 "database is locked"。
  文件:`app/agent/memory/fts_store.py`、`app/agent/memory/long_term.py`。
- **numpy 向量索引非原子写**:改 tmp+`os.replace`,防构建中断/并发留下截断 JSON。已单测原子写+重载。
  文件:`app/agent/rag/backends/numpy_backend.py`。
- **extraction 对 `content=None` 崩溃**:STM/LTM 两处 `.content.strip()` → `(... or "").strip()`。
  文件:`app/agent/memory/extraction.py`。

### 工具层
- **议价被幂等冻结**:`negotiate_price` 移出 `_WRITE_TOOLS`(其报价依赖逐轮递减的 rounds,不属
  "需去重的副作用")。文件:`app/agent/tools/registry.py`;测试
  `tests/test_idempotency.py::test_negotiate_price_not_frozen_by_idempotency`。
- **退款中订单仍可开全额发票**:`issue_invoice` 增 `refund_processing` 拦截。
  文件:`app/agent/tools/order_ops.py`;测试 `test_issue_invoice_blocked_for_refunding`。
- **校验白名单缺口**:`issue_invoice`/`expedite_shipping` 纳入 `_ORDER_ID_TOOLS`。
  文件:`app/agent/tools/validation.py`;测试同步扩展。

### 仍作为"已知取舍"保留(未改,附理由)
- **reaper 巩固不持会话锁**:项目有显式测试 `test_consolidation_runs_without_holding_session_lock`
  与对应提交,刻意用"慢巩固不持会话锁"换取"用户回来不被最长约 60s 阻塞"。这是作者自觉的
  延迟/一致性权衡,强行反转会重新引入其修掉的阻塞 bug,故保留。残余的"空闲临界点 split-brain"
  概率受 idle_ttl(默认 1800s)约束,窗口极小;彻底消除需"分离态巩固+独立巩固锁"的较大改造。
- **LocalSessionLock._locks 缓慢增长**:安全清理需处理"清理与等待者竞态"(否则同键出现两把锁的
  并发漏洞),风险高于收益;多实例生产用 RedisSessionLock 无此本地字典。故保留并说明。

## 三、已报告、本次未改动的问题(建议后续处理)

> 注:本节多数项已在上方"第二轮修复"落地;保留原始记录以备追溯,末尾两项(reaper、Local 锁字典)
> 为经权衡后有意保留的已知取舍。

### API / 会话 / 并发
- **[边界] 默认 `AUTH_SECRET="dev-secret-change-in-prod"`**:`.env` 未覆盖时任何人可离线伪造 token 冒充任意用户。代码 docstring 自述为教学演示边界,但该实例 `auth_enabled=True` 且带真实 Key。**生产必须强制注入随机密钥,缺失即拒绝启动。**
- **[边界] 默认 `ADMIN_TOKEN=""` 时管理端点零鉴权**:`/api/memory`、`/api/config/reload`、`/api/session/reset|consolidate|takeover`、`/api/traces` 等对匿名开放。生产需强制配置;并把 `x_admin_token != token` 改成 `hmac.compare_digest`(防计时侧信道)。
- **[P1] 两套互不协调的会话锁**:`/api/chat` 用模块级 `get_session_lock()`,`/consolidate` 用 `manager.get_lock()`(另一把 `threading.Lock`);redis 部署下二者永不互斥,并发改同一 `agent.raw_messages` 有损坏/丢消息风险。
- **[P1] reaper 回收不持会话锁**:空闲临界点与在途 `/api/chat` 竞态,极端下同一会话出现两个活实例、落盘 last-writer-wins 丢整轮对话。
- **[P2] 限流器/成本闸非线程安全**:线程池并发下 check-then-append 无锁,阈值可被突破或误杀。
- **[P2] auth 关闭时限流键坍缩为 `"default"`**:所有匿名用户共用一个桶,可互相拖累(仅 auth-off 模式)。
- **[P2] 锁字典无界增长**:`LocalSessionLock._locks`、`SessionManager._locks` 按 session_id 建锁从不清理,进程存活期内缓慢内存泄漏。
- **[P2] 快路径锁竞争时静默不落盘**:命中快路径但抢锁失败仍返回回复,该轮问答未入历史,刷新/多端回显缺失。

### 记忆 / 召回
- **[P1] `LongTermMemory.facts` 无锁并发读写**:后台记忆线程 append/重绑 与 主线程 `save_user_memory`(不持 `_bg_lock`)/`build_prompt_section` 遍历 交错 → `list changed size during iteration` 崩溃或事实静默丢失。
- **[P1] 原子写用固定 `.json.tmp` 名**:同一用户两个并发 `save()` 写同一 tmp,内容交错被 `os.replace` 提升 → 下次 `load()` JSON 解析失败被吞 → 该用户长期记忆静默清零。
- **[P1] FTS 每实例独立连接同一 db 且无 `busy_timeout`**:多用户并发 `save()` → `database is locked`。建议 FTS 改共享单例连接(对齐 `profile.py`)或加 `busy_timeout`。
- **[P2] numpy 向量索引写入非原子**:`write_text` 直接整覆盖,中断/并发 → 截断 JSON,后续检索全崩,无自愈。建议同 `long_term` 用 tmp+`os.replace`。
- **[P2] `extraction.py` 对 `message.content=None` 未兜底**:部分兼容模型可能返回 None → LTM 巩固路径 `AttributeError`(STM 路径被 try/except 吞)。

### 工具层
- **[P1/条件] redis 幂等下议价被冻结**:`negotiate_price` 幂等键不含议价轮次 `rounds`,`buyer_offer` 相同的连续"便宜点"命中缓存 → 阶梯让价失效。建议把 `rounds` 纳入幂等键或将其移出 `_WRITE_TOOLS`(默认 file 后端不触发)。
- **[P2] `issue_invoice` 对 `refund_processing` 订单仍开全额发票**:金额/凭证与实际收款不符,建议退款中订单禁开或按实退调整。
- **[P2] 硬校验白名单遗漏 `issue_invoice`/`expedite_shipping`**:二者同为 order_id 参数却未纳入 `validation._ORDER_ID_TOOLS`,绕过统一格式纠错(无越权风险,一致性缺口)。
