# 对标报告:Customer-Agent(JC0v0)vs 本项目(ecom-service-agent)

> 对标对象:https://github.com/JC0v0/Customer-Agent(v1.1.0),一个 **PyQt6 桌面版拼多多 AI 客服**。
> 本报告基于对其源码的系统深读(Agent 层 17 py / 渠道层 21 py / 消息层 13 py),逐项对比两个项目的架构选择,标注**它强的地方(值得借鉴)**和**我们强的地方**。

## 一、定位差异(先看清不是同类竞品)

| | Customer-Agent | 本项目 ecom-service-agent |
|---|---|---|
| 形态 | PyQt6 **桌面应用**(PyInstaller 打包 .exe) | **Web**(FastAPI + SSE + React) |
| 落地目标 | 直接接**真实拼多多**店铺客服,商用工具 | 生产级教学/求职项目,自建业务闭环 |
| 核心价值 | **真渠道接入 + 真商品同步** | **Agent 工程纵深 + 可观测 + 防线** |
| LLM | OpenAI SDK → 火山引擎 Ark | OpenAI SDK → dashscope/兼容 |

一句话:**它赢在"接了真实世界",我们赢在"Agent 内功和工程硬化"**。两者几乎正交,互补性极强。

---

## 二、它值得借鉴的地方(按价值排序)

### ★1 真实渠道接入(我们完全没有,文档对照表里 ✖ 的那栏)
- **WebSocket 长连** `wss://m-ws.pinduoduo.com/?access_token=…&role=mall_cs`,token 从 cookie 换取
- **Playwright 驱动本机 Chrome/Edge 登录**采集 cookie,4 级启动兜底(persistent context → channel → CDP over port → 内置 Chromium),带反自动化检测标志
- **完整连接韧性栈**:指数退避重连(5 次,2→60s)+ WS ping 心跳(30s,3 次失败判死)+ **两层 cookie 自愈**(主动 5 分钟健康检查 + 被动 43001 触发重登,per-account 互斥 + 60s 冷却)
- **借鉴点**:这是"多渠道部署"那一栏的真实范本。即便我们不接拼多多,**连接韧性栈(退避重连/心跳/会话自愈)的设计模式**对任何长连接集成都通用。

### ★2 商品知识自动同步 + 多模态提取(直接呼应我们刚修的商品编造 bug)
- 两阶段:①拼多多 API 拉商品列表(增量,跳过已存)→ ②逐个拉详情 + **把商品图 `thumb_url` 喂给多模态 LLM(gpt-4o)提取结构化知识**(brand/ingredients/spec/usage/faq),`response_format=json_object`,并发限 3、可取消、失败降级纯文本
- 存入 `product_knowledge.extracted_content`,jieba 分词 + LIKE 检索
- **借鉴点**:我们的 products 表是静态 6 列(刚因此闹了商品编造 bug)。它的"API 拉真实商品 → 多模态提取 → 入库"管线,让商品数据**是同步来的、带图理解的、不会编**。这比我们的静态库更"活",且天然规避编造。

### ★3 goods_id 反捏造的运行时护栏(比我们的提示词约束更狠)
- `send_goods_link` 工具**函数体里** `if goods_id < 1000: return 纠错提示`——直接在代码层拒绝 LLM 传"列表序号 1/2/3"而非真实商品大数 ID,并返回纠错信息让它重选
- **借鉴点**:我们刚修的商品编造是**提示词层**约束(软)。它这种**工具函数运行时硬校验 + 纠错回传**是更可靠的防线——LLM 传了假 ID 直接被工具挡回,不依赖它自觉。可用于我们的 query_order/apply_refund 等关键工具。

### ★4 工具参数的 dependencies 注入(防会话身份被 LLM 编错)
- `execute_tool` 的合并策略:LLM 给的参数优先,**session 上下文(shop_id/user_id)只填空缺**——LLM 想编错 shop_id 也编不了,真实值兜底注入
- **借鉴点**:和我们的 ctx_user_id 透传思路一致,但它做成了通用的"依赖注入填空",更优雅。

### ☆5 消息去重 + 短路处理器链
- asyncio.Queue + **去重**(优先 `mid:<msg_id>` 防 WS 重投,退化到 `u:channel:uid:content`)+ 处理器链(KeywordDetection → AIReply → CatchAll,首个 success 短路)
- **借鉴点**:去重键设计(msg_id 优先、内容哈希退化)值得抄;处理器链短路和我们的回复流水线选择器异曲同工。

## 三、我们强的地方(它没有或更弱)

| 能力 | 本项目 | Customer-Agent |
|---|---|---|
| **检索** | ApeRAG 向量+全文混合检索 + 三级降级 + 域过滤 | **仅 jieba 分词 + SQL LIKE**(无向量/语义) |
| **查询理解** | 统一 QU 节点(意图/路由/门控/改写一次出) | 无,直接进 function-calling |
| **接地防线** | 强制检索 + 来源引用 + EVALUATOR 校验 + 回复流水线(评估→重写→润色) | 靠预注入商品列表 + 提示词,**无出话后评估重写** |
| **转人工** | 四路触发(纯短句短路/QU意图/重复N次/负面情绪)+ 状态同步 | 关键词表匹配(转人工/退款/投诉…),LLM 也可调工具 |
| **可观测** | 自研 tracer + Langfuse 全链路 span | loguru 日志,无链路追踪 |
| **记忆** | STM/LTM(FTS5)+ profile 用户画像,按用户隔离 | SQLite 会话历史 + tiktoken 摘要压缩(无长期画像) |
| **会话压缩** | 历史压缩 + 工具结果落盘指针 | tiktoken 估算 70% 窗口触发 LLM 摘要(**这点我们可互鉴**) |
| **业务闭环** | 订单/物流/退款/议价/优惠券真工具 + 归属校验 + consent 门 | 商品推荐 + 转人工为主,交易类工具少 |

**关键差距点**:它的检索是纯词法(jieba+LIKE),我们是语义混合检索——**这是我们相对它最大的技术优势**,也印证了我们接 ApeRAG 的方向对。反过来,它的**多模态商品提取**和**真渠道接入**是我们的空白。

## 四、可落地的借鉴清单(供后续决策)

按"性价比 × 与本项目契合度"排序:

1. **工具运行时硬校验 + 纠错回传**(借鉴★3):把关键工具(query_order/apply_refund)的 ID/金额参数做函数体校验,非法直接挡回并回传纠错——比提示词约束可靠。**小改动,高价值。**
2. **连接韧性栈设计模式**(借鉴★1):虽不接拼多多,但退避重连/心跳/会话自愈的模式可沉淀成通用能力(如果未来接任何外部长连服务)。**中等,看是否真要接渠道。**
3. **商品知识多模态同步**(借鉴★2):若想让商品库"活"起来,可做一个"商品图 → 多模态 LLM 提取 → 入库"的离线管线。**较大,但演示效果强(多模态 + 数据飞轮)。**
4. **tiktoken 摘要压缩**(互鉴):它的 70% 窗口触发 LLM 摘要,和我们的历史压缩可对照优化。**小。**

## 五、面试叙事价值

对标本身就是素材:"我调研了同领域的开源桌面客服 Customer-Agent,它的强项是真实渠道接入(拼多多 WS + Playwright)和多模态商品同步,我的项目强项是 Agent 工程纵深(语义混合检索、查询理解门控、多层接地防线、全链路可观测)。两者正交——**它证明了'接真实世界'的工程复杂度,我的项目证明了'Agent 内功'的深度**。我从它借鉴了工具运行时硬校验的思路,补强了我的商品接地防线。"

这段话展示的是**技术判断力**(看得懂别人的架构、说得清优劣、知道该借什么),比多写一个功能更值钱。
