## 1. 项目定位与技术演进

一个**教学性质的「从 0 到 1 企业级电商客服 Agent」**：以虚构电商「并夕夕」为背景，客服代号「小夕」，通过 **CLI 交互**。项目按「期数」逐步叠加现代 Agent 技术栈，每期对应一个 git commit/tag：

| 期 | 主题 | 代码落点 |
|---|---|---|
| 1 | 纯 Prompt + **结构化输出** | `prompts/customer_service.py`、`schemas/response.py` |
| 2 | **多轮对话管理**（摘要压缩 + JSON 持久化） | `chat.py._compress_history`、`summarizer.py`、`storage.py` |
| 3 | **ReAct + Function Calling** | `chat.py._react_loop`、`tools/registry.py` |
| 4 | **MCP 集成**（Streamable HTTP） | `mcp_server/`、`mcp_client/`、`tools/manager.py` |
| 5 | **RAG**（政策/FAQ 知识库，双后端） | `agent/rag/`、`tools/knowledge.py` |
| 6 | **Multi-Agent**（Router + 售前/售后/投诉） | `multi_agent/` |
| 7 | **Memory**（短期 STM + 长期 LTM） | `agent/memory/` |
| 8 | **Skill**（Agent Skills 标准，渐进式披露） | `agent/skills/`、`tools/skill_tool.py` |
| 9 | **评估体系**（沙箱 + 过程/结果双层指标 + LLM judge） | `app/evaluation/`、`scripts/run_eval.py` |

**架构一致性强**：每期都以「配置开关 + 新模块」叠加，核心 `chat.py` 的 ReAct 循环几乎不动；记忆/技能/评估都作为可插拔组件挂在 Agent 上。

## 2. 技术栈

- **语言**：全 Python，约 6500 行有效代码，模块粒度小、职责单一。
- **依赖极少（仅 6 项）**：`openai`、`pydantic`、`pydantic-settings`、`python-dotenv`、`mcp`、`chromadb`。**没有 LangChain/LangGraph 等重量级 Agent 框架，一切手写**（教学透明，双刃剑：利于讲原理，但简历写不了热门框架关键词）。
- **大模型**：统一用官方 `openai` SDK，通过 `base_url` 支持任何 **OpenAI 兼容接口**（README 推荐 gpt-4o-mini；本地 `.env` 实际接的是**阿里通义 DashScope 兼容模式**，`qwen-plus` + `text-embedding-v3`）。
- **无关系型数据库**：持久化全走 JSON 文件；RAG 默认 numpy 后端（零依赖）。

## 3. 整体运行流程

### CLI 入口（`main.py`）
- 启动时按 `settings.multi_agent_enabled` 分流：`EcomAgent`（单 Agent）或 `MultiAgentOrchestrator`（多 Agent）。
- REPL 主循环：读输入 → 内置命令（`quit`/`reset`/`skills`/`memory`）不进 LLM → 普通输入调 `agent.chat()` → 打印回复 + `[意图 | 置信度 | 转人工]` 元信息。

### 一次 `chat()` 的完整链路（`app/agent/chat.py`）
```
用户输入 → 追加 user 消息
  → _react_loop()  跑 ReAct，拿最终自然语言文本
  → _extract_structured_response()  二次 LLM 调用，提取意图/置信度/是否转人工
  → memory_manager.update_short_term(最近6条)  抽取短期记忆
  → 结构化结果(JSON) 作为 assistant 消息入历史
  → 超过 history_threshold(10) 则 _compress_history() 摘要压缩
  → save_session() 持久化
  → 返回 CustomerServiceResponse
```
设计特点：**「生成回复」与「打结构化标签」两段式解耦**——主链路回复自由发挥，元数据由低温二次调用稳定抽取。

## 4. ReAct 循环

核心 `EcomAgent._react_loop()`：

- **循环上限** `max_react_steps`（默认 5）。
- 每步：`_build_messages()` 拼装（system prompt + 技能目录 + 记忆段 + 历史摘要 + 消息）→ 调 `client.chat.completions.create(..., tools=tool_manager.tool_definitions)`。
- **终止条件**：模型不再返回 `tool_calls` → 输出即最终 Answer。
- 有工具调用时：把带 `tool_calls` 的 assistant 消息按 OpenAI 规范写入历史 → 逐个执行工具 → 把结果以 `{"role":"tool","tool_call_id":...,"content":...}` **写回历史**（Observation）→ 继续下一步。
- **兜底**：跑满 max_steps 仍无最终答案 → 再做一次**不带 tools** 的调用强制收口，避免死循环。
- 终端可视化 Thought(💭)/Action(🔧)/Observation(📋)。

## 5. 工具系统

### 注册与调度
- **`registry.py`**：`_TOOL_MAP`（工具名→函数）+ `TOOL_DEFINITIONS`（OpenAI Function Calling schema）+ `execute_tool()`（分发执行，结果转 JSON 字符串）。
- **`manager.py::ToolManager`**：统一管理本地 + MCP 工具，支持 `allowed_tools` 白名单（多 Agent 工具隔离）；`use_mcp` 决定工具从本地还是 MCP Server 来；MCP 连接失败自动降级本地。

### 八个工具

| 工具 | 功能 | 数据源 |
|---|---|---|
| `query_order` | 按订单号查详情 | mock |
| `query_product` | 商品模糊搜索（命中计数 + 随机兜底） | mock |
| `query_logistics` | 物流轨迹 | mock |
| `apply_refund` | 申请退款（敏感操作，调用前需确认） | mock |
| `list_user_orders` | 列出用户全部订单（无单号时兜底） | mock |
| `search_knowledge` | RAG 政策/FAQ 检索（top_k 1-5） | 向量库 |
| `recall_user_memory` | 查用户短期/长期记忆 | 记忆系统 |
| `load_skill` | 加载技能完整指令 | 技能系统 |

> 业务数据全为内存 mock（`mock_data.py`：5 订单 / 6 商品 / 3 物流轨迹）。这正是二次开发要接真实数据的地方。
> 记忆/技能工具用「模块级单例 + `set_xxx_manager()` 注入」模式，让无状态工具函数访问有状态 Manager。

## 6. 结构化输出

Schema `app/schemas/response.py::CustomerServiceResponse`：`intent`（9 类意图枚举）、`confidence`（0-1）、`reply`、`requires_human`、`follow_up_question`。

提取方式（`chat.py`）：
1. 主路径 `_extract_structured_response()`：对 ReAct 最终文本**再做一次 LLM 调用**，用 `client.beta.chat.completions.parse(response_format=CustomerServiceResponse)`（OpenAI 原生 Structured Output），`temperature=0.0`，要求 `reply` 原样保留。
2. 降级 `_extract_structured_fallback()`：不支持 `response_format` 的兼容接口时，用普通 chat + 手写 JSON prompt + `model_validate_json`。

## 7. MCP 集成

### MCP Server（`mcp_server/server.py`）
- `FastMCP("ecom-tools", host="127.0.0.1", port=9123)`，传输 **Streamable HTTP**，地址 `http://127.0.0.1:9123/mcp`。
- 暴露 **5 个**工具（`query_order`/`query_product`/`query_logistics`/`apply_refund`/`search_knowledge`），都是对本地函数的薄包装；入参 schema 由 FastMCP 从类型注解自动推导。
- `list_user_orders`/`recall_user_memory`/`load_skill` **不做成 MCP**（依赖进程内状态）。

### MCP Client（`app/mcp_client/`）
- **`client.py::MCPClient`**：核心设计是**后台线程 + 独立事件循环，把异步 MCP 连接封装成同步接口**，让同步的 Agent 代码零改造调用。连接后保活常驻；`call_tool` 用 `run_coroutine_threadsafe` 投递到后台循环；异常包成 `{"error":...}` 不抛（保证 Agent 不崩）。
- **`converter.py`**：MCP 的 `inputSchema` 本就是 JSON Schema，与 OpenAI `parameters` 一致，只需换外层信封。

### 开启 `MCP_ENABLED` 后的变化
同一行 `execute_tool(...)`：MCP 关时 → 进程内直接调本地函数；MCP 开时 → 后台线程 → Streamable HTTP → 9123 Server → Server 内再调本地函数。**同一份 ReAct 代码，工具从「进程内函数」透明切换为「跨进程 RPC」**——这正是 MCP 解耦的价值。

## 8. RAG 检索系统

目录 `app/agent/rag/`，链路：**分块 → 向量化 → 后端存储 → 检索**，由 `search_knowledge` 工具暴露。

- **分块（`chunker.py`）**：按 Markdown 二级标题 `## ` 切；文档开头单独成「概览」chunk；超 1200 字按空行贪心打包；chunk 文本带 `【文档 · 章节】` 前缀保留来源。
- **Embedding（`embedder.py`）**：封装 OpenAI Embeddings，默认 `text-embedding-3-small`（可配），批量 64 分批。
- **检索（`retriever.py::KnowledgeRetriever`）**：query → 向量 → 后端 Top-K；`load()` 时校验索引的 embedding_model 与当前一致，否则报错要求重建（防「换模型没重建索引」的隐蔽 bug）。
- **双后端（`backends/`）**：
  - `NumpyBackend`：手写余弦 + JSON 持久化，零依赖，O(n) 全量打分，适合 <1k chunks（教学透明）；
  - `ChromaBackend`：嵌入式 Chroma + HNSW 索引，亚线性查询（生产代表）；延迟 import，未装不影响 numpy 路径。
  - 由 `settings.rag_backend` 单开关切换，对上层透明。
- **知识库**：4 篇 md（退换货政策 / 配送说明 / 会员权益 / 常见问题 FAQ）。
- **构建脚本 `build_kb_index.py`**：扫描切分 → 批量向量化 → `upsert` 持久化；支持 `--backend` 参数。

## 9. 记忆系统（STM + LTM）

目录 `app/agent/memory/`，由 `MemoryManager` 统一管理，单/多 Agent 共用。

- **短期记忆 STM（`short_term.py`）**：会话内 `facts: list[str]`，每轮用 LLM 从最近消息抽取用户身份/偏好/情绪，去重合并；随 session 序列化。
- **长期记忆 LTM（`long_term.py`）**：**按 user_id 分文件**存 `app/sessions/memory/{user_id}.json`；`MemoryFact`（content/category/created_at/source_session）；**去重**（content 小写判重）、**裁剪**（超 `max_facts=50` 保留最近）、**原子写入**（`.tmp` → `os.replace`）、容错加载。
- **提取（`extraction.py`）**：STM 逐行抽取；LTM 要求输出 JSON（facts + interaction_summary），`temperature=0.0`。
- **注入**：`build_memory_prompt_sections()` 返回 LTM 段 + STM 段，插在 system prompt 之后；另有 `recall_user_memory` 工具让 Agent 在 ReAct 里主动查记忆。
- **读写节奏**：每轮更新 STM 并存 session；LTM 只在 `close()` 时统一巩固落盘。

## 10. 技能系统（渐进式披露）

目录 `app/agent/skills/`，基于 Anthropic Agent Skills 标准。

- **定义**：`definitions/<skill>/SKILL.md` = YAML frontmatter（name + description）+ Markdown 正文（操作流程）；frontmatter 用正则手写解析（不依赖 PyYAML）。
- **加载（`loader.py::SkillManager`）**：初始化只扫描解析 frontmatter 拿 name+description，正文**懒加载**。
- **渐进式披露三阶段**：
  1. 发现：`build_catalog_prompt()` 只把 name+description（约 100 tokens/skill）注入 system prompt；
  2. 激活：Agent 调 `load_skill(name)` 工具才读入完整正文；
  3. 执行：按 instructions 用现有工具处理。
- **三个内置技能**：`track-order`（订单跟踪）、`process-return`（退货退款）、`product-recommend`（商品推荐）。

## 11. 多 Agent 编排

目录 `app/multi_agent/`，由 `settings.multi_agent_enabled` 开关（默认关）。

- **Router（`router.py`）**：LLM 三分类（presale/postsale/complaint），带最近 4 条上下文，默认回退 postsale。
- **三子 Agent + 受限工具集（`agents.py`）**：

| 子 Agent | allowed_tools |
|---|---|
| 售前 presale | query_product、search_knowledge、list_user_orders、load_skill |
| 售后 postsale | query_order、query_logistics、**apply_refund**、list_user_orders、search_knowledge、load_skill |
| 投诉 complaint | query_order、search_knowledge、load_skill |

> **退款仅售后可用**——通过 `ToolManager` 的 `allowed_tools` 白名单实现权限最小化，避免售前误触发退款。

- **编排器（`orchestrator.py`）**：对外接口与 `EcomAgent` 完全一致（可无缝替换）；为每个子 Agent 建独立 ToolManager，但**统一持有一个 MemoryManager 和 SkillManager**（子 Agent 共享记忆/技能，路由切换不丢记忆）；`chat()` 流程：路由 → 用子 Agent prompt 构建消息 → 子 Agent ReAct → 结构化提取 → 更新 STM → 存 session。

## 12. 评估体系

目录 `app/evaluation/`。分工：**Sandbox 只采集、Evaluator 只评分、metrics 是纯函数**。

- **Sandbox（`sandbox.py`）无侵入插桩**：
  - 隔离：每用例独立临时 session，强制关掉 memory/mcp（保证可复现 + 幻觉检测有确定 ground truth）；
  - 插桩（monkeypatch，不改业务代码）：包裹共享 client 的 `create`/`parse`（采集 token/工具/延迟/model）、`ToolManager.execute_tool`（采集工具入参/返回=幻觉 ground truth）、多 Agent 的 `router.route`（采集路由）；`finally` 全部还原；
  - **绝不调 `agent.close()`**（避免触发记忆巩固的 LLM 写入，既污染又烧钱）。
- **指标 2×2 矩阵（`metrics.py`）**：{过程, 结果} × {代码规则, LLM judge}
  - 代码规则：tool_accuracy、tool_efficiency、token_cost_pass、route_match、intent_match、keyword_coverage、requires_human_match；
  - LLM judge：judge_answer_quality（回答质量 1-5）、judge_faithfulness（幻觉检测）、judge_process_soundness（工具序列合理性 1-5）；
  - **设计亮点**：未指定的维度返回 `None`，聚合时**跳过 None 而非记 0**，避免无工具/无关键词的用例拖垮均值。
- **黄金测试集（`cases.json`）**：10 条用例，紧扣 mock 数据 ground truth，覆盖订单查询、物流、边界（未发货无运单号）、缺货、退款（故意 `expected_tools=[]` 要求先确认）、RAG 政策、强投诉→转人工、纯问候、多轮、列全部订单。
- **脚本（`run_eval.py`）**：`--no-judge`（只跑代码规则，快、免费）/ 全量 / `--mode multi` / `--output`。

## 14. 工程质量与许可

**质量（高于一般教学项目）**：
- 全量搜索 `TODO/FIXME/NotImplementedError/stub` **零命中**，无空壳；

## 附：二次开发的高价值切入点

（作为学习/改造参考）代码质量已经很好，二次开发的价值不在补代码质量，而在补「真实性/生产化」：
1. **接真实数据层**：把 `mock_data.py` 换成 SQLite/Postgres；
2. **服务化**：现在只有 CLI，加 FastAPI + 简单前端；
3. **补生产篇**（README 预告但未实现，`strategies/` 空目录）：Guardrails 安全护栏 / Human-in-the-Loop / Observability 至少一项；
4. **RAG 升级**：加 rerank 重排、混合检索（可结合 RAG 背景发挥）。
