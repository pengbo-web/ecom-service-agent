# 首字延迟与回复质量 实施方案（第二轮）

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development.

**Goal:** 把首字时间从「热会话 14.8 秒 / 冷启动 37.6 秒」压到企业级可接受的量级，同时修掉体验诊断里剩下的回复质量问题。

**方法:** 每一条都来自**实测**，不是推测。

---

## 实测基线（2026-08-08）

同一句 `我买的鞋子尺码不对,想退货,怎么弄?`：

| 指标 | 冷启动（新会话） | 热会话 |
|---|---|---|
| 总耗时 | 40.0 s | 15.7 s |
| **首字时间** | **37.6 s** | **14.8 s** |
| 增量帧 | 28 | 12 |

分解：
- 进程级首次会话构造 **5.94 s**；之后每个新会话 **0.86 s**；热会话 **0 s**
- trace 内：查询理解 3.2 s + ReAct 11.7 s（内含一次生成 2.5 s）
- **trace 记 17.2 s，客户端测 40 s —— 约 23 s 发生在观测之外**

---

## 根因：向量能力整体空转（本轮最重要的发现）

`.env` 用的是**阿里云 DashScope 兼容端点**（`https://dashscope.aliyuncs.com/compatible-mode/v1`），而 `settings.embedding_model` 写的是 OpenAI 的 `text-embedding-3-small`。

实测该端点返回 **404 model_not_found**；端点上可用的是 `qwen3.7-text-embedding`（1024 维，实测 0.5 s/次）。

后果：

1. **FAQ 语义缓存从来没命中过。** 它号称「零 LLM 秒回」，实际每轮先发一次注定 404 的请求，再走 fail-soft 返回未命中——**纯粹是延迟负担，没有任何收益**。
2. **知识库预召回每轮白跑一次。** trace 里 `recall:kb` 显示 0 ms 正是因为它在异常路径上直接返回了。
3. **没有任何人发现**，因为两处都是 fail-soft：异常被吞、日志被淹没在正常噪音里。

> 这是「fail-soft 用对了地方、但缺少可见性」的典型代价：系统没崩，但一个完整的子系统静默死亡了很久。

---

## Global Constraints

1. **不动安全边界**：consent 门、工作流守卫、HITL 升级、人工审批、E1b 的护栏改动一律不改。
2. **换 embedding 模型必须连带处理索引维度**。已建索引是 1536 维，新模型 1024 维——直接换会让检索崩溃或静默返回错误结果。必须重建，且要有维度校验，**维度不匹配时明确报错而不是继续跑**。
3. **fail-soft 必须留痕**：本轮凡是"失败后降级"的路径，都要发出可观测事件并计数，不能再出现"整个子系统死了没人知道"。
4. 所有性能改动可回退（开关或配置）。
5. 中文 UI 文案与注释；只在 `feature/w1-service-streaming` 提交，不建分支不推送。

## Task L1: 修复向量子系统（最高优先）

**Files:** `app/config/settings.py`、`.env`、`app/agent/rag/embedder.py`、`app/agent/faq_cache.py`、`app/agent/recall/`、`app/scripts/build_kb_index.py`、测试

**要点：**
- `embedding_model` 改为端点实际可用的模型；模型名必须来自配置，不写死。
- **维度校验**：索引落盘时记录建索引所用的模型与维度；加载时若与当前配置不一致，**明确失败并提示重建**，绝不静默用错维度检索。
- 重建 KB 索引。
- **给 fail-soft 加可见性**：embedding 调用失败时发观测事件（含错误摘要）并计数；连续失败超过阈值时在管理端可见。这条比换模型本身更重要——它保证下次再坏能被发现。
- FAQ 缓存与 KB 召回都要有"本轮是否真的用上了"的观测标记，让 trace 能区分「命中 / 未命中 / 子系统不可用」三种情况（现在后两者不可区分）。

**验收：** FAQ 缓存能真实命中并秒回；KB 召回返回非空；trace 能区分三种状态；故意把模型名改错时，索引加载**报错**而不是静默降级。

## Task L2: 冷启动预热

**Files:** `app/api/app.py`（启动钩子）、`app/api/session_manager.py`、测试

**要点：**
- 进程级首次会话构造 5.94 s，落在**第一个真实用户**头上。改为服务启动时预热：MCP 连接、RAG 索引/检索器、embedder、skill 目录扫描。
- 预热必须**不阻塞启动完成**（后台线程/启动任务），且失败不影响服务可用——预热是优化不是依赖。
- 每个新会话仍有 0.86 s 的构造成本，评估其中哪些是可共享的（工具管理器、检索器通常可跨会话复用），能共享的提到进程级。**注意线程安全**：本项目已有过"多 agent 并存时记忆工具串户"的教训，共享对象前先确认无状态或已隔离。

**验收：** 服务启动后第一个真实请求不再承担进程级构造；预热失败时服务仍正常；并发两个会话不串状态。

## Task L3: 首字前的串行链路压缩

**Files:** `app/agent/chat.py`、`app/agent/understanding.py`、`app/api/streaming.py`、`app/config/settings.py`、测试

**要点：**
- 现状串行：查询理解（3.2 s）→ FAQ 缓存 →（skill 预加载）→ KB 召回 → 生成。买家在这之前一个字都看不到。
- 可做的：
  1. **查询理解与 KB 召回并行**——召回只依赖用户原句（`kb_query` 改写是优化项，可先用原句发起、拿到改写后若差异大再补一次）。
  2. **查询理解降级**：短输入已有规则快筛；评估能否把更多常见句式纳入规则，避免为一句"退货怎么弄"付 3.2 s。
  3. **给慢轮次先发进度**：生成开始前，向前端发一条明确的「正在为您查询订单…」类进度帧（**不是假装在打字**，要如实说明在做什么）。这条最能改善体感，且零风险。
- 每一项都要有开关。

**验收：** 首字时间（热会话）显著下降并给出前后对比数字；并行不改变任何一方的结果；进度提示如实反映当前阶段。

## Task L4: 回复不泄漏内部实现 + 能查的先查（原 E3+E4）

**Files:** `app/prompts/agents.py`、`app/config/shop_profile.py`、`app/agent/skills/definitions/process-return/SKILL.md`、`app/agent/reply_pipeline.py`、测试

**实测证据**（买家真实看到的原文）：

> 根据当前**已加载的「process-return」技能流程**，我将按标准步骤为您办理：
> **第一步：确认订单信息**
> 请您提供要退货的订单号…若您暂不确定订单号，我也可以先**调用工具**列出您全部订单供您确认。

三个问题：
1. 把 skill 名、"技能流程"、"调用工具"讲给买家听——真人客服不会说"根据我加载的流程"。
2. 有 `list_user_orders`、也知道买家是谁，却让买家自己报订单号，还"提议"可以帮他查——**多一个来回**。
3. 风格约束没压住：语气设定写着"1~3 句、不用标题"，实际输出加粗小标题 + 分点 + 6 句。

**要点：**
- 安全规则块加硬规则：不得提及 skill 名、"技能流程"、"调用工具"、内部字段名。
- 售后/售中画像与 `process-return` 流程改为：**买家描述了商品但没给订单号时，先查再问**（查询是只读的，守卫本来就允许）。
- 加一道出话检查：命中 skill 名或内部术语表时记观测事件（先可见，不阻断）。术语表里的 skill 名从 `SkillManager.skill_names` 取，不手抄。
- 风格没压住的原因要在报告里说明，并给出实际措施。

**验收：** 同一句问话，回复不含内部词汇、且主动列出候选订单让买家确认。

## Task L5: 会话存储降级（原 E5）

**Files:** `app/session/store.py`、`app/config/settings.py`、测试

**实测**：Redis 未启动 → `store.load()` 抛 `ConnectionError` → `/api/session/{id}/history` **直接 500**，聊天不可用。`load()` 里只有 `except (ValueError, TypeError)` 兜 JSON 解析，无任何连接失败兜底。

**要点：**
- 连接失败/超时时降级到本地文件存储，发明确告警（观测事件 + 日志），不把异常抛给请求。
- 降级**每次操作独立判断**，Redis 恢复后自动用回来。
- 告警文案必须说清**降级期间多实例部署会话不共享**——不能静默降级让人以为一切正常。
- 不吞真正的数据错误（坏 JSON 仍按既有方式处理）。

**验收：** Redis 不可达时聊天仍可用；发出降级事件；恢复后重新使用 Redis。

## 验收（做完我再跑一次真实体验对比）

1. 同一句"鞋子尺码不对想退货"，**热会话首字时间**给出前后对比；冷启动不再承担进程级构造。
2. FAQ 缓存真实命中一次并秒回。
3. 回复不含 skill 名/"调用工具"，且主动列候选订单。
4. 停掉 Redis 聊天仍可用且有明确降级提示。
5. 把 embedding 模型名改错 → 索引加载明确报错，不静默降级。
6. 全量 pytest 与基线一致；前端全绿 + build 干净。
