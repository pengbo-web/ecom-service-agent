# 体验对齐企业级 实施方案（第一轮）

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development.

**Goal:** 把买家侧的实际体验从「盯 46 秒空屏、然后整段文字弹出」拉到企业级客服的水准：**首字快、过程可见、话术不露内部实现、能办的事直接办**。

**方法:** 这一轮的每一条都来自**真实跑一轮**的观测数据，不是推测。

---

## 实测基线（2026-08-08，一条真实售后请求）

买家输入：`我买的鞋子尺码不对,想退货,怎么弄?`

**端到端 46.6 秒**，自研 trace 记录的分解：

| 阶段 | 耗时 | 说明 |
|---|---|---|
| `llm.chat.create` | 2,664 ms | 查询理解（域/意图/情绪/检索门控） |
| `stage:react` | 11,624 ms | ReAct 循环，内含一次 5,197 ms 的 LLM |
| `llm.beta.parse` | 4,889 ms | **结构化提取——单独一次 LLM，只为把已生成的回复拆成 intent/confidence** |

**一条消息 = 3 次串行 LLM 往返**，纯模型时间约 12.8 秒。

买家实际看到的回复（节选）：

> 根据当前**已加载的「process-return」技能流程**，我将按标准步骤为您办理：
> **第一步：确认订单信息**
> 请您提供要退货的订单号（例如 ORD-20260728-xxx）…
> 若您暂不确定订单号，我也可以先**调用工具**列出您全部订单供您确认。

## 诊断出的 6 条问题（按严重度）

### P0-1 没有流式输出，买家全程空屏

全代码**零处 `stream=True`**（实测 grep）。所谓「SSE 流式」流的是过程事件（`route`/`thought`/`stage`），**回复本身是模型全部生成完后一次性** `{"type":"reply","content": 整段}` 发出。

企业级客服的关键指标是**首字时间（TTFT）**，不是总时长。46 秒有字在动 vs 46 秒空屏，是两种产品。这一条单独就决定了「像不像真人客服」。

### P0-2 结构化提取白白多花一次 LLM

`_extract_structured_response`（`app/agent/chat.py:500`）在回复已经生成之后，**再调一次模型**，只为得到 `intent` / `confidence` / `requires_human`，且 prompt 明写「reply 字段直接使用原文，不要修改」。

实测这一步 **4,889 ms**，占端到端的 ~10%，而它产出的信息完全可以在主生成时一次拿到，或用零成本方式得到。

### P0-3 回复把内部实现讲给买家听

「已加载的**「process-return」技能流程**」「我也可以先**调用工具**」——skill 名、"调用工具"都是内部词汇。真人客服不会说"根据我加载的流程"。这直接破坏"像真人"的感觉。

### P1-4 能查的不查，多问一轮

买家说"我买的鞋子尺码不对"。系统有 `list_user_orders`，也知道当前买家是谁。企业级做法是**先查再问**：「您最近有两笔鞋类订单，是哪一笔？」。现在是让买家自己报订单号，还"提议"可以帮他查——**多一个来回，且把本可自动完成的事推回给买家**。

### P1-5 风格约束没生效

当前生效语气写着「非常正式、用您、不用 emoji」，默认风格块还写着「1~3 句、不用标题、不大段加粗」。实际回复有 **加粗小标题**、分点、约 6 句。说明风格指令在长回复场景下压不住。

### P2-6 Redis 不可用时整站 500

实测：Redis 未启动 → `store.load()` 抛 `ConnectionError` → `/api/session/{id}/history` 直接 500，聊天不可用。`store.load()` 里只有 `except (ValueError, TypeError)` 兜 JSON 解析，**无任何连接失败兜底**。

企业级系统不会因为会话缓存层挂了就整体不可用——至少应降级到本地/内存并明确告警。

## Global Constraints

1. **不可逆动作的人工闸、consent 门、工作流守卫一律不动。** 本轮只改体验，不碰安全边界。
2. **流式化不得削弱既有的输出护栏与 HITL 升级。** 护栏当前在完整文本上做变换；改流式后必须保证「护栏要改写的内容不会已经吐给买家」——这是本轮最需要想清楚的一处。
3. **所有改动必须可回退**：流式走开关，关掉即回到现状。
4. **观测不能倒退**：本轮刚接好的 trace/Langfuse 覆盖必须继续有效，流式后要能看到首字时间。
5. 中文 UI 文案与注释。
6. 只在 `feature/w1-service-streaming` 提交，不建分支不推送。

## Task E1: 回复流式化（P0-1）

**Files:** `app/agent/chat.py`、`app/api/streaming.py`、`app/config/settings.py`、`webui/src/components/ChatView.tsx`、`webui/src/components/MessageBubble.tsx`、`lib/api.ts`、对应测试

**要点：**
- ReAct 循环的**最后一次**生成（产出给买家的那次）改 `stream=True`，逐块 `_sink({"type":"reply_delta","content": chunk})`。
- 保留既有 `{"type":"reply"}` 作为**终帧**（全文），前端以它为准做最终校正——这样旧前端/旧测试不破。
- **护栏与流式的冲突是本任务的核心**：输出护栏会改写文本。方案：护栏分两类——「变换类」（改写措辞）必须在流式**之前**决定是否启用；若本轮命中需要改写的护栏，则**降级为非流式**（先全量生成、改写、再一次性发）。宁可这一轮不流式，也不能把要被改写的内容先吐出去。在代码里把这条写清楚。
- 开关 `stream_reply_enabled`（默认 True），关掉即回到现状。
- 前端：逐块追加渲染，光标态；终帧到达时以终帧全文覆盖（防止丢块）。

**测试：** 流式时前端能收到多个 `reply_delta` 且拼接结果 == 终帧全文；命中改写类护栏时**不发** `reply_delta`；开关关闭时行为与现状逐字节一致；trace 里能看到首字时间。

## Task E2: 去掉结构化提取的额外 LLM 调用（P0-2）

**Files:** `app/agent/chat.py`、`app/schemas/response.py`、测试

**要点：**
- 现状：主生成产出纯文本 → 再调一次 `beta.chat.completions.parse` 提取 intent/confidence/requires_human。
- 目标：**一次调用同时拿到回复与元数据**。做法二选一，实施者按代码实际情况定并在报告里说明：
  - (a) 主生成直接用结构化输出（response_format / tools），一次拿到 `{reply, intent, confidence, requires_human}`；
  - (b) 保留纯文本生成，元数据改为**零 LLM** 推导：intent 用已有的查询理解结果（`_turn_qu.intent`，本来就判过了）、requires_human 交给既有 HITL 规则层（它本来就会独立判定并覆盖）。
- **注意 (b) 与流式天然兼容，(a) 与流式的结构化输出要一起验证。** 若两者冲突，优先保流式。
- 必须保持 `metadata` SSE 帧的字段与取值域不变（前端与既有测试依赖它）。

**测试：** 一轮对话只发生**一次**面向买家的生成调用（用打桩客户端计数）；`metadata` 帧字段与取值域不变；HITL 规则升级仍能覆盖 `requires_human`。

## Task E3: 回复不得泄漏内部实现（P0-3 / P1-5）

**Files:** `app/prompts/agents.py`、`app/config/shop_profile.py`、`app/agent/reply_pipeline.py`、测试

**要点：**
- 在安全规则块里加一条硬规则：**不得向顾客提及 skill 名、"技能流程"、"调用工具"、"系统提示"、内部字段名**；要说就说人话（"我先帮您查一下订单"）。
- 风格约束加强：明确"不使用加粗小标题、不分点罗列步骤"（当前默认风格已写"不用标题"，但实际没压住——实施者需在报告里说明为何没压住，以及采取了什么措施）。
- 加一道**出话检查**：回复中若出现 skill 名或内部术语，记一条观测事件（不阻断，先可见）。用现成的 skill 名清单（`SkillManager.skill_names`）与一个小的内部术语表。

**测试：** 给定一段含 `process-return` 与"调用工具"的草稿，检查函数能标出；prompt 中含该硬规则；术语表来自 skill 名单一来源，不手抄。

## Task E4: 能查的先查，不要多问一轮（P1-4）

**Files:** `app/prompts/agents.py`、`app/agent/skills/definitions/process-return/SKILL.md`、测试

**要点：**
- 售后/售中画像的 prompt 与 `process-return` skill 流程里明确：**买家描述了商品但没给订单号时，先调 `list_user_orders` 用候选让他确认，而不是要求他提供订单号**。
- 这是话术与流程问题，不是新能力——工具早就有。
- 注意不要与"不代客下单"和工作流守卫冲突：查询是只读的，守卫本来就允许。

**测试：** skill 正文含"先列订单再确认"的步骤；改动后 `process-return` 仍通过既有的工作流守卫校验与 skill 校验器。

## Task E5: 会话存储降级（P2-6）

**Files:** `app/session/store.py`、`app/config/settings.py`、测试

**要点：**
- Redis 后端在**连接失败/超时**时降级到本地文件存储，并记一条明确告警（观测事件 + 日志），而不是把异常抛给请求。
- 降级必须是**每次操作独立判断**，不能一次失败就永久切换（Redis 恢复后要能自动用回来）。
- 明确边界：降级期间多实例部署会话不共享——这一点必须在告警文案里说清，不能静默降级让人以为一切正常。

**测试：** Redis 不可达时 `load`/`save` 不抛异常且走文件路径；发出降级观测事件；Redis 恢复后重新使用 Redis；降级不吞真正的数据错误（坏 JSON 仍按既有方式处理）。

## 验收（做完后我会再跑一次真实体验）

1. 同一句"鞋子尺码不对想退货"，**首字时间 < 3s**，回复逐字出现。
2. 回复中**不出现** skill 名、"调用工具"等内部词汇。
3. 回复主动列出该买家的候选订单，而不是要求他报订单号。
4. trace 里能看到首字时间，且**面向买家的生成只有一次**。
5. 停掉 Redis，聊天仍可用，且界面/日志有明确降级提示。
6. 关掉流式开关，行为回到现状。
7. 全量 pytest 与基线一致；前端全绿 + build 干净。
