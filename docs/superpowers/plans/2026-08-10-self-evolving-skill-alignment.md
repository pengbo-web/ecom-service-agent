# 自进化 Skill 对齐方案（对标多客三条宣称 + 7 步闭环）

**Goal:** 让「Skill 商店即装即用 / 一键蒸馏 / 自进化沉淀」这三条在产品里真的成立，
而不是只有 CLI 里成立。

**实测结论（不是读代码推断）：闭环断在最后一环。** 前 5 步全自动，第 6 步要人敲
命令，第 7 步连命令都得在服务器上敲——而界面上已经躺着 7 个候选，产品内没有任何
办法让它们上线。

---

## 一、实测基线

| 宣称 | 实测 |
|---|---|
| ① Skill 商店海量即装即用、**一键启用** | ⚠️ 4 个预置技能；❌ **无转正/驳回/回滚端点**，候选只进不出 |
| ② 上传资料**一键蒸馏** | ⚠️ 端点在、注入围栏在、校验在；❌ 实测失败且**原因不可读** |
| ③ 自进化**无需人工干预** | ⚠️ 合成/门禁/灰度/看门狗全有；❌ **无任何调度器**，全靠手敲 CLI |

7 步闭环：①识别 ✅ ②推理 ✅ ③执行 ✅ ④校验 ✅ ⑤转人工 ✅ ⑥蒸馏 ⚠️手动 ⑦沉淀 ❌断开

### ② 失败的精确原因（进程内复现得到）

上传一份发票 SOP，端点返回一句三选一的笼统话：
「LLM 产物未通过校验（frontmatter 不全 / 工具名不真实 / 名字非法）」。

真因是 LLM 引用了 `escalate_to_human`——**这个工具不存在**（转人工由 HITL 层按
置信度自动判定，不是 Agent 可调工具）。而产物其余部分完全正确：`name`、
`description`、五步流程、正确用了 `query_order`。

三个问题叠加：

1. `doc_distill.distill_from_doc` 里 `if not report["valid"]: return None`
   ——**校验报告连同精确原因被整个丢掉**，端点只能报一句"或"的组合。
2. 95% 正确的产物因**一个工具名**被整份丢弃，LLM 的钱也白花。
3. **没有重试**。把"`escalate_to_human` 不存在，可用工具是这 19 个"回喂给模型
   再来一次，极可能就过了。

## 二、Global Constraints

1. **转正是不可逆的线上变更，必须保留全部既有关卡。** 复用
   `promote_skill.promote()`（快照 → 校验 → 门禁 → 风险门 → 备份 → 装机），
   不在端点里重写一套简化版。那个函数已经处理过 TOCTOU：校验与装机认的是
   同一份快照字节。
2. **高危档不能被"一键"顺手放行。** `risk=high` 的候选前端必须二次确认并显示
   风险来源；`policy` 由后端给，前端不自己判。
3. **驳回不是删除**。候选目录移进 `_rejected/` 而不是 `rm -rf`——被驳回的候选是
   下一轮改进的输入，也是"为什么当时没上"的证据。
4. **蒸馏失败必须可行动**：下发 `unknown_tools` / `errors` 原文 + 可用工具清单。
5. 全部可开关、可回退；中文注释；补齐回归。

## Task P0：打通闭环（候选能从界面上线）

**Files:** `app/api/app.py`、`webui/src/lib/api.ts`、`webui/src/components/SkillsView.tsx`、测试

- `POST /api/admin/skills/{name}/promote` — 复用 `ps.promote(...)`，`force` 可选
- `POST /api/admin/skills/{name}/reject` — 移进 `_rejected/<name>-<时间戳>/`
- `POST /api/admin/skills/{name}/rollback` — 复用 `ps.rollback(...)`
- 前端：候选卡片加「转正 / 驳回」，现行技能加「回滚」；高危二次确认

**验收**：界面上把一个校验通过的候选转正 → 现行技能列表出现它 → 回滚 → 恢复原状。
全程不碰命令行。

---

## Task P1：蒸馏可用性（失败要能行动）

**Files:** `app/agent/skills/doc_distill.py`、`app/api/app.py`、前端、测试

1. `distill_from_doc` 失败时返回 `{"ok": False, "report": ..., "content": ...}`
   而不是 `None`——精确原因不能在中途被丢掉。
2. **一次自动修复重试**：把 `unknown_tools` 与真实工具清单回喂给模型重生成一次。
   只重试一次（不做无限循环烧钱），且第二次仍失败就如实报错。
3. 端点下发 `unknown_tools`、`errors`、`available_tools`，前端渲染成
   「资料里提到的 X 不是本店可用工具，可用的是：…」。

**验收**：上传那份提到 `escalate_to_human` 的 SOP，要么自动修好并生成候选，
要么明确告诉店主哪个词不对、可用的是什么。

---

## Task P2：预置技能与自动化（本方案先不做，条件写清）

- **Skill 商店**：现在 4 个预置技能。要"海量"需要一批经过验证的行业模板，
  这是**内容工作而非架构工作**——先把 P0 的上架通路打通，模板才有落点。
- **自动调度**：`synthesize_skills` 目前 CLI-only。要"无人工干预"需要一个调度器
  （或复用协作 worker 的 `--loop`）。**但前置条件是语料干净**：当前
  `skill_traces` 里 37 条 `track-order` 失败全部来自已修复的基础设施问题
  （见交付对照表 ⑭），在它们滚出窗口之前开自动合成，等于让系统去"修"一份
  没写错的流程文档。
- 因此 P2 的启动条件是：**① P0 已上线；② 失败轨迹里基础设施占比 < 20%。**

## 实施结果（P0 + P1 已完成并实跑验收）

### P0 闭环打通

新增三个端点 + 界面按钮，全部**复用 CLI 既有函数**（`ps.promote` / `ps.rollback`）：

| 动作 | 实测 |
|---|---|
| 转正（不 force） | 400 `缺少门禁结果,拒绝转正（未跑评测门禁）` —— **fail-closed，不静默绕过门禁** |
| 转正（校验未过的候选 + force） | 400 `校验未通过: 引用了未知工具: product_diagnostics` —— **force 不放行校验** |
| 非法名字 | 404（路径穿越拒） |
| 转正 `track-order` | 200 · risk=low · policy=canary_ab · **已备份** · 候选出队 7→6 |
| 驳回候选 | 200 · 归档到 `_rejected/`（**不删**）· 队列 6→5 |
| 回滚 | 200 · 从 `_archive/track-order/<stamp>/` 恢复 |

**顺带修掉一个既有缺陷**：`promote()` 刻意不清理候选目录。CLI 下可以容忍，但候选目录
同时是**产品里的"待审队列"**——已转正的候选一直躺在队列里，运营分不清哪些还要处理，
重复点一次只会把版本号无意义地又推一格。新增 `archive_candidate()`，**CLI 与端点共用
同一个函数**（本项目已多次因"一半做对、另一半漏了"出问题，所以不在端点里单独实现）。

### P1 蒸馏可用性

同一份发票 SOP，修复前后：

| | 修复前 | 修复后 |
|---|---|---|
| 结果 | `created: false` | **`created: true`** |
| 原因 | 一句三选一的「frontmatter 不全 / 工具名不实 / 名字非法」 | 生成 `invoice-issuance`（risk=high, policy=manual） |
| 真因可见性 | 需要进程内手动复现才知道是 `escalate_to_human` | 自动带精确原因重试一次并**修好了** |

失败时改为返回 `{"ok": False, unknown_tools, errors, available_tools, attempts}`，
前端渲染成「资料里提到的 X 不是本店可用工具」+ 可展开的 19 个可用工具清单。
只重试**一次**，不做无限循环烧钱。

### 端到端串通（P0 + P1）

> 上传 SOP → 蒸馏（首次引用不存在的工具 → 自动修正重试）→ 候选入队（risk=high）
> → 界面点转正 → `invoice-issuance` 上线 → 候选出队并归档到 `_promoted/`

**全程没有碰命令行。** 7 步闭环的第 ⑥⑦ 步至此在产品内闭合。

## 三、交付后能说的一句话

> 自进化闭环七步全部在产品内可完成：会话执行与校验自动跑，失败/转人工轨迹自动
> 归档，蒸馏产出候选并强制过校验与风险分档，人在界面上一键转正或驳回，转正后带
> 版本与备份、可一键回滚；灰度期由看门狗按真实轨迹判转正或回滚。**不需要登进
> 服务器敲任何命令。**
