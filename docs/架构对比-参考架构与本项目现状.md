## 1. 参考图解读:它画了什么

参考图自上而下分五层,外加左右两个"数据飞轮"挂耳:

```
┌─ 存储/能力层(顶排)─────────────────────────────────────────────────────┐
│ [Memory 长期]        [Conversation 短期]   [Skill自动化生成]      [工具中心]   │
│  用户base profile     商品、订单、物流单      skill记忆:Agent自主    spuId查档案  │
│  用户行为标签         对话状态               判断什么值得记忆        身高体重荐码  │
│  跨天对话信息         同Session对话上下文     用户建模:从行为捕捉偏好  spuId查详情  │
│  工单流转信息                                FTS5召回:SQLite全文索引  身高体重→尺码范围│
│  知识库                                      创建Skill:识别重复模式   互联网搜索引擎 │
│                                             生成markdown skill文件  商品属性问答  │
│                        (进化循环 居中)        Skill自进化:失败时自动进化 鞋长→鞋码   │
│                                                                     spuId→衣长胸围 │
│                                                                     袖长肩宽;其他   │
│                                                                     [订单物流/商品] │
├─ 管理层(中排)──────────────────────────────────────────────────────────┤
│ 记忆管理(Memory Manager)      上下文引擎(Context Engineering)            │
│   SQLite WAL 数据库读写          上下文压缩、轨迹压缩                       │
│   +FTS5全文索引                                                        │
│ Skills管理        Tools/MCP管理        人机协同(HITL)                     │
├─ 核心层───────────────────────────────────────────────────────────────┤
│ 总控Agent: ReAct机制 | 记忆管理 | 业务流程执行权限(物流、赔付、升级等) | 生命周期管理 │
├─ 子Agent层────────────────────────────────────────────────────────────┤
│ 售前物品查询Agent | 售后差价问询Agent | …… | 售前尺码查询Agent | 售前客服咨询Agent │
├─ 数据层(底排)─────────────────────────────────────────────────────────┤
│ 真实满意对话样本非标数据 | Agent执行日志 | top5客服意图/回复话术/回复策略标注      │
│ 回复正确性标注数据 | 优秀客服回复色调数据                                     │
└──────────────────────────────────────────────────────────────────────┘
 左挂耳:数据飞轮(PE自动化)          右挂耳:数据飞轮(Agentic RL训练)
```

**参考图的设计哲学**(读图结论):

1. **垂直域客服**:工具中心 9 个工具里 7 个围绕 spuId/尺码/身高体重/鞋长——这是一个**鞋服垂直域**的客服架构,尺码推荐是核心场景。
2. **数据飞轮驱动**:左右两个飞轮(PE 自动化 = prompt/skill 从数据自动迭代;Agentic RL 训练 = 用数据训模型)是整张图的发动机,数据层五种**人工标注**数据资产是燃料。
3. **总控 + 垂直子 Agent**:总控 Agent 持有 ReAct/记忆/权限/生命周期四能力,下挂多个按**业务域**切分的子 Agent(物品查询/差价问询/尺码查询/客服咨询)。
4. **Skill 自动化生成是独立闭环模块**:六个块(skill 记忆 → 用户建模 → FTS5 召回 → 创建 Skill → 自进化,中间一个"进化循环"),强调"Agent 自主判断什么值得记忆"。
5. **管理层五件套**作为存储层与总控之间的粘合层:记忆管理、上下文引擎、Skills 管理、Tools/MCP 管理、HITL。
6. **安全治理几乎不可见**:整张图里"业务流程执行权限(物流、赔付、升级等)"只是总控 Agent 内的**一个盒子**,没有独立的授权门/归属校验/上线门禁/回滚机制。

## 3. 逐层详细对比

### 3.1 Memory(长期)

**参考图五项**:用户 base profile / 用户行为标签 / 跨天对话信息 / 工单流转信息 / 知识库。

**本项目现状**:结构化档案 `UserProfile(base/tags/tickets)` 独立 `profile.db`(`profile.py:25-32,72-80,182`)+ 长期记忆 `facts/interaction_summaries` 落 `memory.db`(`long_term.py`, `memory_store.py`)。**行为标签的生成机制也有**:`user_modeling.py` 从归档会话样本 LLM 归纳偏好标签写入档案(MAX_TAGS=5 / MAX_TAG_CHARS=10,fail-soft 校验坏输出跳过;docstring 明确"半自动铁律不适用:标签是低风险追加式操作,去重无覆盖,可直接落库")——这一块与参考图"用户建模:从行为捕捉偏好"**字面对应**。

**两处设计分歧(不是缺口,要能讲清)**:

1. **知识库不放在长期记忆里**。参考图把"知识库"列为长期记忆的一项;本项目刻意"存储隔离、召回统一"(`recall/kb.py` docstring):用户记忆一人一份、可写、含隐私(所以要过归属过滤),知识库全局共享、只读(所以失败方向、注入围栏各自不同)。混在一起会让"念不念这条记忆"的隐私判据无处安放。
2. **记忆带隐私治理,参考图没有**。读取侧归属过滤 fail-closed、写入侧 fail-open 的不对称(`long_term.py:281-285,190-194`)、49/62 画像污染事故链与存量清理(`clean_leaked_memory.py`)——参考图的 Memory 盒子没有任何越权/泄漏防线。

### 3.2 Conversation(短期)

**参考图三项**:商品、订单、物流单 / 对话状态 / 同 Session 对话上下文。

**本项目现状**:

- **商品**:`product_context.py` 按 item_id 每轮拉详情拼"当前商品"块,位置放在最后一条用户消息之前保 recency 指代消解(`chat.py:1067-1074`),任何失败降级 None 不注入。
- **订单/物流单**:不做会话级快照,走工具实时查询(单一事实源);被提及的订单号/运单号会进 LTM facts 并由归属过滤看管(`ownership_filter.py`)。
- **对话状态**:这是本项目**超出参考图**的地方——`PendingAction`(被 consent 拦下、等待确认的风险动作:动作/工具名/真实参数/确认问题)**随会话状态持久化**,重启不丢(`pending.py` docstring:"consent 保证未确认不执行,本机制保证确认后必执行,两者互补");consent 授权按轮 ContextVar 用后复位(`consent.py:15-42`)。参考图的"对话状态"是静态枚举,没有"挂起的待确认动作"这种一等公民。
- **同 Session 上下文**:SessionStore 历史 + `_compress_history` 超预算压缩(保留最近 3 条,`settings.py:373`)+ LLM 摘要失败退确定性 `fallback_summary`(实测修过 content=None 抛 AttributeError 与超时毁回合两个缺陷,`chat.py:1276-1312`)。

### 3.3 Skill 自动化生成(参考图六个块)

| 参考图块 | 本项目对应 | 差异与超出 |
|---|---|---|
| skill 记忆:Agent 自主判断什么值得记忆 | `attribution.py` 三分类归因,**离线**判断哪些失败值得学,仅 knowledge_gap 回流 | **刻意分歧**:不让 Agent 在线"自主判断"。实证:41 条错误里绝大多数是归属校验正确拦截,真知识缺口 0(`attribution.py:10-12`)——"自主判断"会把不可修信号编码成知识。参考图这块是本项目归因要替代的东西 |
| 进化循环 | 自进化三回路:运行(毫秒,fail-soft)/ 离线(分钟,可重跑)/ 放行(fail-closed) | 参考图一个环,本项目三个时间尺度不同的环,且写明"埋点失败静默放过、放行判定静默拒绝"的不对称 |
| 用户建模:从行为捕捉偏好 | `user_modeling.py`(归档会话 → 标签 → 档案) | 完全对应;参考图把它画在 Skill 生成框内,本项目挂在自进化离线回路(H3.4) |
| FTS5 召回:SQLite 全文索引检索 | 记忆召回有 FTS5+jieba(`memory_store.py`);**skill 生成采样不用 FTS**,用轨迹(强证据)+ 关键词(弱证据)两源且强弱分开报数 | 形态不同:参考图用全文检索捞历史;本项目认为"采样可以启发式、裁判尺不能",关键词只挑会话不做断言(`case_synthesis.py:36-46`) |
| 创建 Skill:识别重复模式,生成 markdown skill 文件 | `clustering.py` 贪心语义聚类(SIM_THRESHOLD=0.75,簇心=首成员向量保可复现)+ `synthesizer.py` LLM 合成 → `_candidates/<name>/SKILL.md` | 超出:`validate_candidate`(实测拦过 LLM 编的 `order_list`/`coupon_query`)、安全路径名校验(防 `../` 逃出候选目录覆盖线上)、半自动铁律(只写候选目录,靠目录深度对 `_discover` 隐身) |
| Skill 自进化:失败时自动进化 | `improve_skill` 仅对 knowledge_gap 失败样本改进 + 看门狗实战成绩自动回滚 | 超出:改进要过五道闸才能上线;参考图的"自动进化"没有上线门禁 |

**一句话**:参考图六个块本项目**块块有对应**,但参考图的环是"生成导向"(怎么长出来),本项目的环是"放行导向"(怎么保证长坏的上不去)——这正是要对齐时**不能丢**的部分。

> 本节的逐块对照是摘要版。**逐块机制级深挖、两架构流水线并排图、放行/收口阶段的结构差、以及 Skill 部分的差距与对齐项,见 §8 附录 A《Skill 自进化专项对比》**。

### 3.4 工具中心

**参考图 9 工具**:spuId 查档案 / 身高体重荐码 / spuId 查详情 / 身高体重→适用尺码范围 / 互联网搜索引擎 / 商品属性问答 / 鞋长→鞋码 / spuId→衣长胸围袖长肩宽 / 其他[订单物流/商品]。

**本项目现状**:registry ~30 个业务工具(商品/订单/物流/退款/议价/券/购物车/店铺分析五件套/商机与草稿…),MCP Streamable HTTP 统一接入、进程内↔跨进程透明切换。

**差距**:① **无互联网搜索引擎工具**(参考图有,我们没有);② **无鞋服垂直尺码工具**——这是域差异:参考图是鞋服垂直客服,本项目是通用电商,尺码表/身高体重荐码不在业务面。**不必为对齐而补垂直工具**,但"工具中心 = 扁平清单"这个形态要对齐成我们的"registry + 安全分类":

**超出(参考图完全没有)**:`TOOL_TRAITS` 每工具打 `mutating`/`seller_only` 双标签、穷尽性测试兜底(新工具不补分类就红,`registry.py:601-657`);写工具 Redis 幂等键防重复退款;consent 门控;workflow 守卫;**schema 描述本身就是防线**(`add_to_cart` 描述明写"不代结算、禁止代替买家下单")。参考图的工具中心只有能力没有治理。

### 3.5 管理层五件套

| 参考图 | 本项目 | 匹配与超出 |
|---|---|---|
| 记忆管理:SQLite WAL 读写 + FTS5 全文索引 | `memory_store.py`:WAL + busy_timeout 5000ms、FTS5/jieba 分词/LIKE 三后端运行时探测、facts+summaries+索引**单事务**写入、`fact_id=md5[:12]` 幂等、进程级共享单例消 "database is locked"、索引条数不符自愈 reindex、`VACUUM INTO` 一致性备份 | ⬛ **字面完全对上**,且每项都有实测事故背书(中文 MATCH 恒 0、两步写崩溃漂移) |

### 3.7 子 Agent 层

**参考图**:总控下挂多个**垂直域子 Agent**(售前物品查询/售后差价问询/售前尺码查询/售前客服咨询…),形态是"总控分发 → 子 Agent 各自干活"。

**本项目**:**薄编排**——买家 3 画像(presale/midsale/aftersale)+ 卖家 2 画像(analyst/growth)**共享同一个硬化引擎**,切换只改两行 `system_prompt`/`tool_manager`(`orchestrator.py:193-194`);买卖分流由**端点**确定性决定,不让 LLM 猜。

**这是形态分歧而非缺口,要能讲清权衡**:不做 N 个 ReAct 循环 = 复用全部硬化(consent/记忆/事件流/持久化)、延迟成本低、加域零边际成本;代价是画像数膨胀到几十个时配置会变胖(见 §5-6)。同时本项目还有参考图**完全没有**的第二套多智能体:**事件总线异步协作**(`signal.anomaly → 参谋归因 → 营销起草 → 人工审批 → 闭环回写`,路由表 + 消费闸 + 三轴仲裁),参考图的子 Agent 只有会话内同步分发,没有跨 Agent 异步链。

### 3.8 双数据飞轮

- **PE 自动化(左)** ↔ 本项目自进化闭环就是 PE 自动化的完整实现,且多出门禁治理:蒸馏/合成/改进 → 零 LLM 用例合成 → 影子目录离线评测(劣化 >5% 拒)→ 五道闸转正 → 会话哈希 50% 灰度 A/B → 看门狗自动转正/回滚(sanity floor 0.3 防基础设施故障期误放行)。**匹配度 ⬛**。
- **Agentic RL 训练(右)** ↔ **本项目完全没有**(`⬜`)。没有任何训练/梯度回路;最近的替代物是评估基线 + 回归门禁——用"评分选择压力"替代"梯度",只淘汰候选 skill,不更新模型权重。**这是参考图与本项目最大的单项差距**,也是对齐路线图里唯一需要立项的大件(§6-P2)。

## 7. 结论

参考图是一张**垂直域(鞋服)、数据飞轮驱动**的客服架构图:强在数据资产编目、人工标注厚度、以及把 Agentic RL 写进闭环的野心;弱在**治理层几乎不可见**——权限是一个盒子,Skill 自进化没有门禁,飞轮没有防脏数据的口径。

本项目是一张**治理驱动的通用自进化地基**:参考图 34 个组件块中 22 个已有对应且多数超出(记忆管理字面对上 WAL+FTS5;Skill 生成六块块块有对应且各加一道闸;HITL/工具管理/生命周期全面更深),真正的缺口只有三个:**Agentic RL 飞轮、互联网搜索工具、(域差异的)垂直尺码工具**;另有两处叙事缺口(上下文引擎显式化、数据层编目)。

一句话对齐策略:**补飞轮与工具,不拆治理;补叙事,不改形态。** 参考图的发动机(数据飞轮)装进来时,必须先穿过本项目的口径纪律——否则等于把"拿压测数据回滚好 skill"那个实测事故,以训练数据的形式再犯一次。

## 8. 附录 A:Skill 自进化专项对比(机制级深挖)

> 本节是 §3.3 的展开版:把参考图"Skill 自动化生成"盒子(六个块 + 进化循环)与本项目自进化闭环放到**机制级**逐块对照,并补上参考图没画但闭环必需的"放行与收口"阶段对比。全部 `file:line` 对当前工作区实核。

### A.1 两个架构里"自进化"分别长在哪

**参考图**:Skill 自动化生成是能力层(顶排)里的一个**独立虚线盒**,内部六块围绕一个居中的"进化循环":

```
            ┌────────────── Skill自动化生成 ──────────────┐
            │        [skill记忆] Agent自主判断什么值得记忆   │
            │           ↑                          ↓      │
   [用户建模]←──── ( 进化循环 ) ────→ [创建Skill]           │
   从行为捕捉偏好                     识别重复模式,          │
            ↑                       生成markdown skill文件 │
            │                          ↓                  │
   [FTS5召回] SQLite全文索引检索 ←── [Skill自进化] 失败时自动进化│
            └──────────────────────────────────────────────┘
                       ↓(产物交)管理层 Skills管理 → 总控Agent
   左挂耳:数据飞轮(PE自动化) 为其供能;数据层五种资产为其供料
```

**本项目**:自进化不是一个盒子,是**三个时间尺度不同的回路**,横跨 `app/agent/skills/` 22 个模块 + 4 个 CLI 脚本 + `app/evaluation/`:

```
① 运行回路(毫秒级,fail-soft):matcher 确定性预加载 → loader 三处同源加载
   → workflow 守卫拦跳步 → skill_traces 落轨迹(带 variant/版本/指纹/流量来源)
② 离线回路(分钟级,可重跑,fail-soft):
   轨迹 → attribution 三分类归因 →(仅 knowledge_gap)→ improve_skill
   归档会话 → clustering 语义聚类 → synthesizer 合成 / golden_corpus / doc_distill
   归档会话 → user_modeling 标签 → profile
   全部 → validate_candidate → _candidates/(目录深度隐身,绝不自动生效)
③ 放行回路(错一次=线上事故,fail-closed):
   case_synthesis 零LLM裁判尺 → gate 影子目录离线评测 → promote 五道闸
   → canary 会话哈希灰度 → watchdog promote/rollback/wait → _archive 备份=下轮 S₀
```

**结构差的第一性描述**:参考图的循环是**开环加生成器**(判断→生成→用→再判断),产物从盒子下缘直接交给"Skills 管理";本项目的循环是**带刹车的闭环**——生成端与放行端物理分离(`_candidates/` vs `definitions/`),中间隔五道闸,上线后还有看门狗与回滚。**参考图全图没有任何门禁/灰度/回滚组件**,这是两架构在自进化上的最大结构差(详见 A.4)。

### A.2 六块逐块机制对照

#### 块 1 · skill 记忆:"Agent 自主判断什么值得记忆" vs 离线归因判据表

| 维度 | 参考图 | 本项目 |
|---|---|---|
| 判断时机 | **在线**,Agent 运行时自主判断 | **离线**,对已落库的失败轨迹批量归因(`attribution.py:157-231`) |
| 判断主体 | 模型自主 | **能用确定性规则判的绝不问模型**:七条判据从确定到不确定排序,先命中先返回(`attribution.py:161-223`);模型只在一处花一次调用——分辨人工回话是"可复用知识"还是"授权范围内的让步"(`attribution.py:234-243`) |
| 判断输出 | "值得记忆"的内容 | 三分类 + 第四类 `undetermined`:仅 `knowledge_gap` 回流;判不出**不回流但如实报数**(`attribution.py:46-56,300-306`) |
| 失败方向 | 未定义 | 模型判不出/调用失败 → 退回规则判定并标 `method=rule`,"归因失败绝不能编一个类别出来"(`attribution.py:243,258-259`) |

**为什么不做"自主判断"(用本项目实测数据回答)**:`skill_traces` 里 track-order tool_error 38 / success 15,41 条错误里绝大多数是同一句「未找到订单 ORD-20240115-001」——查库该单存在、属于小明,发起者是压测/评测用户,**那是归属校验在正确工作**(`attribution.py:10-12`)。若按参考图形态让 Agent 在线自主判断"什么值得记忆",这 41 条会被判成值得学,往 SKILL.md 写一堆无用流程,还要走灰度、占审批位。论文(SkillEvo)的同一条警告:"没有归因筛选就驱动修订,会把不可修的信号错误编码成知识"。

**对齐叙事建议**:对外把 `attribution.py` 讲成"**skill 记忆的判断器**"——与参考图同 purpose,但判断权从"Agent 在线自主"收归"离线规则优先",并给出 41 条实证作为收权的理由。这不是功能缺失,是有实测背书的刻意分歧。

#### 块 2 · 进化循环:单环 vs 三回路 + fail 方向不对称

参考图一个居中"进化循环"。本项目拆成三个回路,关键在**fail 方向按时间尺度取反**(自进化文档 §1):

| 回路 | 触发频率 | 能不能出错 | fail 姿态 |
|---|---|---|---|
| ① 运行 | 每轮对话,毫秒 | 绝不能影响回话 | 全链 fail-soft,埋点异常一律吞(`chat.py:503` 旁路) |
| ② 离线 | CLI/cron,分钟 | 可以,重跑即可 | fail-soft,单组坏了跳过;embedding 挂回落关键词聚类**记 warning 不静默**(`clustering.py:61-73`) |
| ③ 放行 | 人点按钮/cron | 错一次=线上事故 | **fail-closed**,证明不了更好就不许上(`gate.py:8-9`) |

> 记住这条不对称:**同一个系统里,埋点失败要静默放过,放行判定要静默拒绝。** 参考图的单环没有表达这层不对称的位置。

#### 块 3 · 用户建模:"从行为捕捉偏好" vs user_modeling.py(对应但挂载点不同)

参考图把用户建模画在 Skill 生成盒**内部**(偏好捕捉服务于 skill 生成)。本项目 `skills/user_modeling.py` 机制完全对应——从该用户归档会话样本 LLM 归纳行为偏好标签写入结构化档案(`MAX_TAGS=5`/`MAX_TAG_CHARS=10`,坏输出 fail-soft 跳过,样本截断复用 synthesizer 的 `_truncate_sample`)——但**产物去向不同**:标签进 `UserProfile.tags` 影响**对该用户**的应答,不进 skill。

**为什么分离**:偏好是**逐用户**的,skill 是**全局**的流程文档;把某个用户的偏好写进全员执行的 SKILL.md,等于把个体记忆污染成公共政策。这与记忆侧"用户记忆 vs 知识库存储隔离"是同一条道理的两处应用。参考图把用户建模放进 skill 盒,在这个维度上是**混杂**的。

另:docstring 明确"半自动铁律不适用于本模块"——标签是低风险追加式操作(去重、无覆盖),可直接落库不需候选目录;**这是本项目"风险决定流程重量"原则的正面例子**,与 skill 合成的半自动铁律形成对照。

#### 块 4 · FTS5 召回:"SQLite 全文索引检索" vs 轨迹强证据 + 关键词弱证据

参考图在 skill 生成盒内放 FTS5 召回(为生成/进化捞历史素材)。本项目 FTS5 机器确实存在(`memory_store.py`:jieba 预分词 + bm25 + 子串保底),但**只用于记忆召回**;skill 生成侧的采样走两条源且**强弱分开记**(`case_synthesis.py:36-46,78-79`):

- `SOURCE_TRACE`(强):该 skill 确实在那一轮执行过——actor 与执行由事实保证;
- `SOURCE_KEYWORD`(弱):按 frontmatter 声明关键词捞归档会话;**只决定挑哪些会话,不决定任何一条断言**。

**为什么不用全文召回做这件事**:全文检索是模糊匹配,捞错的会话会变成**裁判尺的素材**;本项目的纪律是"**采样可以启发式,裁判尺不能**",且启发式采样的**边界**本身必须是硬的——实测教训:卖家 `refund-attribution` 的关键词路从只有买家会话的归档里捞到 5 条「我要退货,订单号 ORD-…」,门禁拿买家提问评参谋技能、用例跑在买家沙箱里该 skill 根本不会被加载,"**一条错的裁判尺比没有更糟**"(`case_synthesis.py:350-367`)。全文召回会放大这类跨域误捞且更难审计。

**对齐项(P1)**:可把 FTS5 作为**第三采样源**接入(复用 memory_store 的分词/索引机器),但保持"只采样不断言"+ 来源强度分开报数 + 卖家侧仍只走轨迹路。

#### 块 5 · 创建 Skill:"识别重复模式,生成 markdown skill 文件" vs 语义聚类 + 合成 + 四道防伪

| 子机制 | 参考图 | 本项目 |
|---|---|---|
| 识别重复模式 | 未画方法 | `clustering.py` 贪心阈值聚类,SIM_THRESHOLD=0.75;**簇心=首成员向量**(非动态平均)保可复现——同批样本换顺序必须聚出同结果,因为离线合成的输入端必须可复现(`clustering.py:39-44,83-86`);O(n·k) 不引 sklearn(样本量级/零依赖/可解释) |
| 为什么换掉关键词桶 | — | 旧 `INTENT_KEYWORDS` 四桶先中先得、只看首条消息,"鞋子穿着挤脚想换大一码"落不进任何桶,**而落桶结果直接决定合成出什么 skill——输入端失真一路传到产出**(`clustering.py:3-10`) |
| 生成 markdown | 生成 skill 文件 | `synthesizer.py` LLM 合成 → `_candidates/<name>/SKILL.md`;MIN_GROUP_SIZE=2(单例不构成重复模式) |
| 防伪 | 未画 | ① `validate_candidate`:工具名必须真实(实测拦过 LLM 编的 `order_list`/`coupon_query`,真实是 `list_user_orders`/`query_coupons`,`validator.py:3-6`);② `is_safe_skill_name`:候选名来自 LLM frontmatter、素材是可注入的顾客对话,`../x` 能逃出候选目录覆盖线上 skill(`validator.py:20-27`);③ 写盘前再兜底一次名校验("不能只依赖上游校验",`synthesizer.py:207-209`);④ 文档蒸馏注入防护三层:prompt 围栏 + 工具名校验 + 只落候选且带风险档(`doc_distill.py:6-13`) |
| 产物生效方式 | 交 Skills 管理(图上无门禁) | **半自动铁律**:只写 `_candidates/`,靠"`_` 前缀 + 目录深度"对 `SkillManager._discover` 隐身;全仓库唯一能写正式目录的是 `promote_skill.promote()`(`promote_skill.py:1-11`) |

#### 块 6 · Skill 自进化:"失败时自动进化" vs 归因过滤后的改进 + 全套收口

参考图:失败 → 自动进化。本项目:**失败 → 先归因 → 只有 knowledge_gap 进 `improve_skill` → 产物仍是候选 → 过五道闸才上线 → 灰度看门狗收口**。三层额外防护:

1. **基础设施失败不进化**:`is_infrastructure_failure` 只认"明说自己是连接/超时/不可用"的措辞,不做语义猜测(`execution_trace.py:24-55`)。实测 track-order 被 MCP 代理打断打到成功率 3%(success:1 · tool_error:37),**skill 一个字都没错**——照参考图"失败即进化",系统会去改一份没写错的流程文档(`execution_trace.py:44-46`)。
2. **守卫拦截不算失败**:`blocked` 不计入 tool_error——守卫拦住跳步、模型补齐后成功是守卫起作用;"若计入失败,守卫越有效灰度成功率越难看"(`execution_trace.py:241-248`)。
3. **进化产物不直接生效**:改进候选与新建候选走同一条放行链(见 A.3/A.4)。

### A.3 参考图没画的阶段:裁判尺从哪来

参考图的循环里**没有"评测"这个环节的位置**——skill 生成后直接交给 Skills 管理。本项目在生成与上线之间插了一整段"裁判尺工程":

| 环节 | 本项目实现 | 参考图 |
|---|---|---|
| 门禁用例 | `case_synthesis.py` **零 LLM** 合成:turns=买家原话逐字、expected_tools=该轮真实调用、expected_keywords=人工回复已知词表;id=`synth-` 前缀;与人工集物理分开、分别报数("只报总数是自动化最容易骗到人的地方") | 无 |
| 为什么零 LLM | "一条门禁用例是要被当作**裁判尺**用的,它自己必须先是确定的"——方案原稿是 LLM 抽取,真动手发现每项断言的事实来源仓库里都有(`case_synthesis.py:20-33`) | — |
| 离线评测 | `gate.py` 影子目录:正式技能集全量复制 + 候选覆盖目标,评"只换了这一个 skill"的完整技能集;比 pass_rate/过程分/结果分,容差 0.05;**fail-closed** | 无 |
| 三态披露 | `evaluable=False`(评不了)≠ 不达标;`underpowered`(n<3)结论是噪声级必须贴在结论上(`gate.py:74-78,179-184`) | 无 |
| 裁判独立性 | `independence.py` Generator≠Evaluator;自审如实标注("一个不知道自己在自审的 81 分,比一个标着'自审'的 81 分危险得多") | 无(飞轮默认自评) |

实测背书:`query-coupons` 真跑一次门禁 58s / 47.5k tokens,过程分 0.733→0.467 **判定拒绝**——门禁给出拒绝比给出放行更能说明它在工作。

### A.4 参考图没画的阶段:上线、监控与回滚(最大结构差)

参考图从"Skill 自动化生成"盒子到"总控 Agent"之间**没有任何治理组件**。本项目的放行回路逐件对照:

| 阶段 | 本项目 | 若按参考图开环直上会发生什么(均有实测背书) |
|---|---|---|
| 写入唯一入口 | `promote_skill.promote()`,先 TOCTOU 快照整棵树,校验/判档/安装只认快照(管理端上传接口能并发替换候选目录) | 校验过的字节与装上线的字节隔着可写窗口 |
| 静态闸 | 整树校验,编错工具名 `--force` 也不放行 | LLM 编的 `order_list` 直接上线,Agent 照指令调不存在的工具 |
| 事实闸 | 双锚点 S₀/S_{t-1}:只比上一版,"每轮删一点点,十轮后『超过7天不支持退货』不见了而没有一次被拦" | 多轮自改进累积丢硬事实(论文 Bloat 16.2% 的同族退化) |
| 风险闸 | 6 个高危工具引用即 high,**代码写死永远人工**;判档看整棵树 + workflow 声明侧 | "人畜无害正文 + 附件里写直接全额退款"被判低危走全自动 |
| 灰度 | `md5(skill:session)` 哈希 50% 分桶,同会话恒同版本;三处读取同源 `_resolve_root` | 同一通对话被两套流程处理;A/B 成绩被"候选指令+线上附件"接线压低 |
| 监控 | watchdog 三态 promote/rollback/wait;`AB_SANITY_FLOOR=0.3` 补 A/B 结构性盲区(live=0.03 时回滚条件等价于 `canary<-0.07` 永不成立→**任何候选自动转正**) | 基础设施故障期无条件放行任意候选(实测撞到过) |
| 回滚收口 | **只有动作真的成功才关闭灰度记录**;`NEEDS_HUMAN_ACTIONS` 让 cron 非零退出告警 | 差劲 skill 永久留在线上而库里记着"已回滚",监控静默停止 |
| 流量口径 | `source` 标记 + DECISION={live}/SAMPLING={live,unknown};压测/评测/模拟两边排除 | **拿压测数据决定线上技能生死**:track-order 全量 28% vs live 88%,一轮压测就能回滚一份好 skill |

### A.7 Skill 部分差距与对齐项(汇总,并入 §6 路线图)

1. **P1 · FTS5 采样源**:复用 memory_store 分词/索引机器,为 case_synthesis/golden_corpus 增第三采样源;纪律不变(只采样不断言、强弱分报、卖家侧只走轨迹路)。
2. **P1 · 进化循环可视化**:参考图有一个居中的"进化循环"符号;本项目三回路只在技术文档 §1 有图。建议在 README/架构页补一张三回路图,使"循环"在对齐叙事里可见。
3. **P1 · skill 记忆叙事对齐**:对外材料把 attribution 命名为"skill 记忆判断器(离线、规则优先)",保留 41 条实证作为"为什么不在线自主判断"的答案。
4. **P2 · Agentic RL 飞轮**:作为第四个候选来源接入闭环,reward 口径复用评估 2×2 与 business_metrics;离线起步,上线仍走五道闸(§6-P2 第 7 条)。
5. **共同缺口(两架构都没有,诚实标注)**:多轮评测。论文最有说服力的失败模式——"Agent 第一轮就说反了规则,但用户没放弃,因为答案看起来自洽"(错误的知识比缺失的知识更具欺骗性)——单轮 QA 几乎不可能触发;本项目评估集 10 条里仅 1 条多轮,参考图数据层 likewise 无多轮模拟资产。多轮用户模拟是两边共同的下一站(本项目卡在配额口径:估算 ~2500 次调用 vs 日预算 200)。

**附录结论**:Skill 自进化这一项上,参考图给出的是**循环的shape**(六块 + 进化循环 + 双飞轮),本项目给出的是**循环的brake**(归因、裁判尺、五道闸、灰度、回滚、口径)。对齐的正确姿势是把参考图的 shape 借来当叙事骨架(六块命名、进化循环符号、RL 飞轮立项),把本项目的 brake 原封不动保留——**一个没有刹车的飞轮,转得越快死得越快**,这句话可以直接用作面试里对这张参考图的点评。
