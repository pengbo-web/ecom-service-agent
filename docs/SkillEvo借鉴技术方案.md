# 把 SkillEvo 的思路落到本项目:技术方案

> 论文:*SkillEvo: Self-Renewing Evolution Gradients from Multi-Turn Interaction Feedback*
> (arXiv 2608.13120,腾讯云 Andon + 浙江大学,2026-08-13)
>
> 本方案只写**能落到本仓库的改动**,每条都标了具体文件与当前实测状态。
> 不照搬论文的规模(它有 9 个 Skill、98 个引用文件、2000 张工单;本项目 7 个 Skill、
> 单文件、评测集 10 条),照搬会得到一套跑不起来的架子。

---

## 0. 结论先行

本项目的自进化链路**结构是完整的**(蒸馏 → 候选 → 门禁 → 灰度 → 转正),
缺的不是环节,而是论文点破的那一件事:

> **反馈信号决定进化上限。** 编辑能力和迭代轮数都不是瓶颈。

对照下来有 **3 个真缺口 + 1 个死结**,以及 **4 处已经做对、不要动**的地方。

### 已经做对的(论文也是这么主张的,别改)

| 本项目做法 | 论文对应 |
|---|---|
| `action.drafts_ready` 永远投给人工闸,是唯一发送出口 | 「没有任何修订未经人工确认就进生产……这是**必要条件,不是可选保障**」 |
| 门禁 fail-closed:没有用例、评测崩了、无可比指标一律不放行 | 治理层对事实一致性采取硬约束、违反即拒 |
| `skill_traces` + `correlation_id` 全链路可回溯 | 设计原则 4:Auditability |
| 判定权不在模型(阈值扫描、状态序判定) | 归因只把 `Knowledge Gap` 回流,其余隔离 |

### 3 个真缺口

| # | 缺口 | 当前实测 | 论文对应 |
|---|---|---|---|
| **A** | 评测是单轮的,梯度第一轮后就衰减 | 评测集 10 条,**只有 1 条是多轮** | 单轮 QA 的 TSR 在 R2 饱和(66.4),多轮持续爬到 81.8 |
| **B** | 没有归因,失败直接进门禁 | `gate.py` 只比三个标量均值 | 无归因筛选会**把不可修的信号错误编码成知识** |
| **C** | 门禁是标量闸,能拒绝不能定位 | `compare_to_baseline` 比 pass_rate / avg_process / avg_result | 「标量分能拒绝一个退化候选,但既定位不了也修复不了结构性原因」 |

### 1 个死结(优先级最高)

**新蒸馏的 skill 永远无法转正。** 实测链条:

```
新建 skill 无对照组 → risk=medium → 策略 gate_then_watch
  → gate_then_watch 要求先过离线门禁
  → 离线门禁要求评测集里有用例在 related_skills 里点名它
  → 没有任何机制为新 skill 产生用例
  → --start-all 每轮都打 gate_unavailable,永远如此
```

评测集现状:**10 条用例,只有 3 条带 `related_skills`**
(`track-order` / `process-return` / `product-recommend` 各 1 条),
`draft-outreach-campaign` 等 4 个现行 skill **一条都没有**——它们连"改进后转正"也走不通。

**论文的框架里这个死结根本不存在**:它的"用例"是从**真实工单自动合成的场景**,
不需要有人预先手写门禁用例。

## 1. 本项目已有的材料(这是能低成本落地的原因)

改造前先确认手里有什么。本仓库**已经具备论文所需的全部数据源**,只是没接起来:

| 论文需要的 | 本项目已有 | 文件 |
|---|---|---|
| 升级到人工的工单(失败集) | 人工接管过的归档会话 | `app/agent/skills/golden_corpus.py` |
| 人工参考解法(human reference) | 坐席在工作台的人工回复(`intent="human_agent"`) | 同上 |
| 失败样本按 Skill 归属 | 按真实执行轨迹归到具体 skill | `app/agent/skills/failure_cases.py` |
| 每轮"加载了哪个 skill / 调了什么 / 结局如何" | `skill_traces` | `app/agent/skills/execution_trace.py` |
| 场景聚类 | 会话语义聚类 | `app/agent/skills/clustering.py` |

实测 `skill_traces` 的结局分布已经能直接用:

```
process-return    success 718 / tool_error 6
track-order       success  15 / tool_error 38   ← 失败率 71.7%,是最该被进化的
product-recommend success 144
```

> **`golden_corpus.py` 的语料来源与论文的工单集是同一个形状**:
> 「AI 没搞定、人救了」。论文全部的反馈信号都是从这种工单里合成的。
> 这意味着最关键的一步不需要新建数据管道。

## 2. 方案总览

按**投入产出比**排序,不是按论文章节顺序。每一阶段独立可上线,不做大爆炸式改造。

```
阶段一  解死结:门禁用例自动合成            ← 让旗舰能力先通电
阶段二  加归因:三分类,只让可修的信号回流    ← 防止把不可修的编码成知识
阶段三  多轮模拟:把评测从终点改成反馈发生器  ← 论文的核心贡献,收益最大也最贵
阶段四  治理层:双锚点事实一致性             ← 防退化,不涨分
```

阶段四之所以排最后:论文自己的消融显示**去掉治理只掉 3.2 分**(81.8 → 78.6),
它的价值在防退化(膨胀 +2.8% vs +16.2%),而本项目的 skill 目前**是单文件**,
结构退化(引用断裂、孤儿文件)在结构上还不成立。

## 阶段一:门禁用例自动合成(解死结)

### 问题

`app/agent/skills/gate.py::gate_case_ids` 只做一件事:

```python
return [c.id for c in filter_by_skill(load_dataset(dataset_path), skill_name)]
```

`filter_by_skill` 按 `related_skills` 精确匹配。新 skill 不可能出现在人工写的评测集里。

### 改法

**从真实失败会话合成门禁用例**,而不是要求人先写。数据源已有(`failure_cases.py`)。

新增 `app/agent/skills/case_synthesis.py`:

```
synthesize_gate_cases(skill_name, n=3) -> list[EvalCase]
    1. failure_cases.collect(skill_name)     # 已有:按轨迹取该 skill 的失败会话
    2. 若不足,退到 clustering 取同簇会话
    3. 每条会话 → LLM 抽成 EvalCase:
         turns            = 买家原话(逐字,不改写)
         expected_tools   = 该会话里人工/AI 实际调用过的工具(从 trace 取,不让模型猜)
         expected_keywords= 人工回复里的关键事实(golden_corpus 已有抽取逻辑)
         related_skills   = [skill_name]
    4. 过 validator:expected_tools ⊆ SKILL.md 声明的工具(validator 已有这能力)
    5. 落 app/evaluation/cases_synth/<skill>.json,**与人工集分开存**
```

### 三条必须守住的纪律

**① 合成用例与人工用例分开存,且在界面上标明。**
合成用例未经人审,把它混进 `cases.json` 会污染回归基线。
`gate_case_ids` 改成读**两个来源**并各自标记:

```python
def gate_case_ids(skill_name, dataset_path, *, include_synthetic=True):
    human = [...]                      # 现有逻辑,一字不改
    synth = load_synth_cases(skill_name) if include_synthetic else []
    return human + synth               # 但 readiness 里要分别报数
```

`gate_readiness()` 的返回增加 `human_count` / `synthetic_count`,
管理端把"3 条门禁用例(其中 3 条为自动合成、未经人工审核)"如实写出来。
**不能只报一个总数** —— 那会让人以为这个 skill 有人工把关过。

**② 断言项只能来自事实,不能来自模型自由发挥。**
`expected_tools` 从 `skill_traces` 取真实调用记录;
`expected_keywords` 从人工回复里抽(那是 human reference);
**模型只负责把会话整理成用例格式,不负责决定"正确答案是什么"**。

> 这一条对应论文的 bounded editing:「编辑器可以查看真实轨迹,但不得脱离证据」。
> 也对应本项目一贯的主张:判定权不在模型。

**③ 合成用例只用于门禁,不进回归基线。**
`app/evaluation/regression.py` 的 baseline 仍然只认人工集,
否则"基线"会随着自动合成而漂移,失去参照意义。

### 验收

- `invoice-issuance` 这类新蒸馏 skill 跑 `--start-all` 不再是 `gate_unavailable`
- `gate_readiness()` 对 `draft-outreach-campaign` 从 0 条变成 ≥3 条
- 新增测试:合成用例的 `expected_tools` 必须 ⊆ 该 skill 声明的工具(防幻觉工具名)
- 管理端显示"自动合成、未经人工审核"字样(有测试钉住)

### 工作量

新增 1 个模块(~200 行)+ 改 `gate.py` 两个函数 + 前端一处文案。**1–2 天。**

## 阶段二:归因分层(只让可修的信号回流)

### 问题

当前 `skill_watchdog` 把门禁失败一律折成 `gate_failed`(我上一轮已把"评不了"分出来成
`gate_unavailable`),但**失败原因本身没有分类**。而实测数据摆在那里:

```
track-order  tool_error 38 次 / success 15 次
```

`tool_error` 里有多少是"Skill 缺知识"、多少是"工具/权限限制"?现在**分不出来**。
论文明确警告:没有归因筛选就驱动修订,会**把不可修的信号错误编码成知识**,
产出文档膨胀和事实冲突。

> 我在走查时抓到过这个形态的实证:`track-order` 那 38 次 `tool_error`,
> 大量是**归属校验正确地拦住了跨用户访问**(用户问的是别人的订单号)。
> 那根本不是 Skill 的问题——把它当成知识缺口去补,只会往 SKILL.md 里
> 写一堆没用的东西。

### 改法

新增 `app/agent/skills/attribution.py`,三分类(**照搬论文的分法,它是对的**):

| 类别 | 判据(**确定性优先,模型兜底**) | 是否回流 |
|---|---|---|
| `knowledge_gap` | 人工回复里有稳定事实,而 AI 答漏/答错 | **是** |
| `capability_limit` | 归属校验拒绝、consent 未授权、工具超时、下游 503 | 否 |
| `evaluation_noise` | 会话过短、买家自己中断、意图未表达完整 | 否 |

**关键设计:能用确定性规则判的,绝不问模型。** 本项目手里的信号足够硬:

```python
# 这些不需要 LLM,直接从 trace / 异常类型判
if trace.tool_error_type in ("owned_order_denied", "consent_required"): → capability_limit
if isinstance(exc, httpx.TimeoutException):                            → capability_limit
if len(session.turns) < 2:                                             → evaluation_noise
# 剩下的才交给 LLM 对比「人工怎么答的 / AI 怎么答的」
```

同一轮里指向同一缺口的多个失败**按语义合并**成一条信号(论文用 Jaccard 0.3),
本项目 `clustering.py` 已有语义聚类能力,直接复用。

### 验收

- `track-order` 的 38 次 `tool_error` 能被分类,且**归属校验拒绝的那些不进 knowledge_gap**
- 归因结果落库并在 Skill 页可见(哪些失败被判为"不可修"、原因是什么)
- 新增测试:确定性规则优先于 LLM 判定(给一个 consent 失败,断言不调用模型)

### 工作量

新增 1 个模块(~250 行)+ 接进 `synthesizer.py` 的信号入口。**2–3 天。**

## 阶段三:多轮用户模拟(论文的核心贡献)

这是收益最大的一步,也是最贵的一步。**建议在阶段一、二稳定后再做。**

### 为什么值得做

论文最有说服力的案例:COS 流量包续费规则,Agent 在第一轮就**说反了**,
但用户没有放弃——因为答案**看起来自洽**——于是在错误前提上继续追问。

> **错误的知识比缺失的知识更具欺骗性。**
> 而这正是单轮 QA 几乎不可能触发的失败模式。

本项目有完全对应的实证:我走查时抓到客服说「已锁定成交价,下单时自动生效」,
而当时下单路径对议价的引用次数是 **0**。这条错误**单轮问答测不出来**——
它要买家真的走到下单那一步才会显形。

### 改法

新增 `app/evaluation/user_simulator.py`,三个部件:

**① 场景合成器** —— 从人工接管会话抽出:

```
opening_message   买家口语化的首句(只说症状与诉求,不透露解法)
behavior_facts    买家已有的信息、已做过的操作、看到的现象
emotion_trajectory 情绪走向(便于模拟"绕圈子就不耐烦")
intent_agenda     [{topic, priority: key|minor}]  ← 意图议程
expected_solution 人工参考解法(**只给 Verifier,绝不注入模拟用户**)
```

**② 受约束的模拟买家** —— 论文的 6 条行为规则可以直接抄,它们都合理:

1. 渐进式披露:开场只说一句主诉,追问才给细节
2. 消息碎片化
3. 配合但不越界:被要求做复杂操作时"我不会弄,你帮我看看"
4. 情绪随进展变化
5. 每轮只推进一个具体意图
6. 不发起超出 Agent 能力的请求(不主动要求转人工)

**③ 意图状态机** —— 跟踪每个意图"提没提 / 有没有被实质回应",
全部满足才允许正常结束;绕圈子则触发"放弃式结束"。

### 必须照抄的两条约束

**① Generator ≠ Evaluator。** 论文把它列为唯一的架构性要求
(编辑器 deepseek-v4-pro,Verifier/模拟用户/治理 minimax-m3),理由是**自审会造成循环依赖**。
本项目目前编辑与评测同模型,**必须改**。这是零成本的改动(换一个 `settings` 里的模型名)。

**② 双侧正交评估。** 模拟器侧和 Agent 侧分开算责任:

```
c_U = |已提出的关键意图| / |关键意图|
c_U < 1 的样本 → 判为 evaluation_noise,从 Agent 侧分母里剔除
```

**没暴露的能力不能被误读成 Agent 失败。** 少了这条,模拟器一旦跑偏,
所有结论都被污染,而你不会知道。

### 落地范围建议

论文跑 4 轮 × 每单 10 轮对话 × 2000 工单。本项目**不要照这个量级**:

| 参数 | 论文 | 本项目建议 | 理由 |
|---|---|---|---|
| 外层轮数 | 4 | **2** | 先验证梯度是否真的renew,再加 |
| 每单对话轮数 | 10 | **6** | 电商客服会话本来就短于云技术支持 |
| 每 skill 场景数 | ~200 | **10–20** | 手里的人工接管会话量级 |
| 通过阈值 | 60 | 60 | 直接沿用 |
| 意图权重 α | 0.7 | 0.7 | 直接沿用 |

**成本要算清楚**:一次完整跑 = 场景数 × 对话轮数 × 2(模拟器+Agent)次 LLM 调用。
按 15 场景 × 6 轮 × 2 = 180 次/skill/轮。7 个 skill × 2 轮 ≈ **2500 次调用**。
本项目 `collab_daily_llm_budget` 默认 200 —— **必须单独配额,不能共用**,
否则一次进化跑完,当天的协作 worker 就没预算了。

### 验收

- 意图覆盖率 `c_U` ≥ 90%(论文 98.9%,本项目场景更简单但语料更少)
- 能复现至少一个"单轮测不出、多轮能测出"的真实缺陷
- 两轮之间 TSR 有提升(哪怕只有几个点)——**如果没有,说明梯度没 renew,不要继续加轮数**

### 工作量

新增 2–3 个模块(~600 行)+ 评测管线改造。**1–2 周。**

## 阶段四:治理层(防退化,不涨分)

**优先级最低,但要知道什么时候该做它。**

论文的治理层针对三种退化:知识膨胀、引用断裂、事实过度泛化。
而本项目的 skill **目前是单文件**(`definitions/<name>/SKILL.md`,没有 `references/` 子目录),
所以"引用断裂"在结构上还不成立。

### 现在就该做的一小块:事实一致性双锚点

即使单文件,**多轮修订累积的事实丢失**这个问题是真实的。论文的双锚点设计很精妙:

| 锚点 | 检测什么 |
|---|---|
| `S₀`(生产基线) | 跨轮累积的**事实丢失** |
| `S_{t-1}`(上一轮) | 本轮**新引入的事实错误** |

> 单一 `S₀` 锚点区分不了这两者,**修复方向就是模糊的**。
> 修复时同时看两个 diff:`S₀→S_t` 的删除行定位"要恢复的丢失事实",
> `S_{t-1}→S_t` 的变更行**禁止回退到原样**——既补回丢的,又保住合法的新知识。

本项目 `versioning.py` 已有版本号与 `_archive/` 备份,拿到 `S₀` 和 `S_{t-1}` 是现成的。
新增 `app/agent/skills/fact_consistency.py`,把它作为**硬约束**接在 `promote()` 之前。

### 什么时候做完整治理层

当满足以下任一条:
- skill 开始有 `references/` 多文件结构(引用断裂才成立)
- 观察到 `Bloat`(相对 `S₀` 的行数增长)超过 **15%**(论文无治理时是 16.2%)
- 观察到跨轮回归率 `RegR` 上升

**在此之前,加治理层是在解决一个还不存在的问题。**

---

## 3. 建议不要照搬的部分

诚实标出来,免得按论文清单逐条实现:

| 论文做法 | 不建议照搬的理由 |
|---|---|
| 98 个引用文件的图结构治理 | 本项目 skill 是单文件,图结构不成立 |
| 2000 工单 / 每 skill 200+ 场景 | 本项目语料量级差两个数量级,强行凑会用合成数据充数,反而污染信号 |
| 4 轮 × 3 次编辑迭代 | 先跑 2 轮验证梯度是否 renew;论文自己也只验到 4 轮,没说何时饱和 |
| 把 TSR 当作主要汇报指标 | 论文的数据集**本身就是失败集**(初始 TSR 30%),+51.8 分不能读成"系统整体质量提升"。本项目若照此汇报会误导 |

## 4. 落地顺序与里程碑

| 阶段 | 内容 | 工期 | 解决什么 |
|---|---|---|---|
| **一** | 门禁用例自动合成 | 1–2 天 | **死结**:新 skill 永远转不了正 |
| **二** | 三分类归因 | 2–3 天 | 防止把不可修信号编码成知识 |
| **零成本** | Generator ≠ Evaluator | 半天 | 论文唯一的架构性硬要求 |
| **三** | 多轮用户模拟 | 1–2 周 | 梯度自我更新(核心收益) |
| **四** | 事实一致性双锚点 | 3–5 天 | 防跨轮事实丢失 |
| 四(完整) | 结构治理 | 暂缓 | 等 skill 变成多文件再说 |

**建议先做阶段一 + Generator≠Evaluator**:两者加起来 2 天多一点,
就能让"旗舰能力从结构上走不通"这件事消失,而且不依赖任何后续阶段。

---

## 5. 每一阶段都要守的两条

**① 人工审批闸不能因为自动化程度提高而放松。**
论文把它写进伦理声明:「没有任何修订未经人工确认就进生产……这是必要条件,不是可选保障」。
本项目的 `promotion_policy` 高危档强制人工,**保持不变**。
自动合成用例、自动归因、多轮模拟——它们提高的是**信号质量**,不是**放行权限**。

**② 每一处"自动产生的东西"都要在界面上标明来源。**
合成的门禁用例要写"未经人工审核",归因结论要写"由模型判定还是规则判定",
模拟对话要写"模拟用户,非真实买家"。

> 这是本仓库一贯的纪律(`anomaly_scope`、`degraded`、`data_scope` 都是这个形状),
> 也是论文治理层的精神:**把"这是什么"说清楚,比把数字做好看更重要**。
